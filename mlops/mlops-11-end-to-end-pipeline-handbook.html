Step 11 · Advanced · Putting it together

End-to-End MLOps Architecture

Here every earlier step is wired into one design: a worked churn-and-risk scoring platform you can adapt, plus a repeatable method for architecting new systems.

AdvancedReference architectureWorked example

Reference architecture

  SOURCES (apps, events, DBs)                    CODE (Git)  ---- PR ---->  CI: lint, unit, data + pipeline tests, image build/scan
      |                                                                      |
  INGEST (batch + streaming) -> LAKEHOUSE (Iceberg/Delta, versioned) -> DATA QUALITY GATES
      |                                   |                                  |
      |                         FEATURE PIPELINES -> OFFLINE STORE      TRAINING PIPELINE (orchestrator, GPU pool)
      |                                   |   \-> ONLINE STORE              |  train -> evaluate -> gates
      |                                   |                                  v
      |                                   |                          TRACKING + REGISTRY (aliases, model cards)
      |                                   |                                  |  approval
      v                                   v                                  v
  SERVING: batch scoring jobs | online endpoints (canary, shadow) | streaming consumers
      |
  MONITORING: system + data drift + model quality + business KPIs -> alerts -> retrain trigger (back to orchestrator)
  CROSS-CUTTING: IAM, secrets, lineage, audit log, cost tags, IaC (Terraform), GitOps (Argo CD)

Environments and promotion

EnvironmentDataPurposePromotion
DevSamples, syntheticExperiments, notebooks, small pipeline runsPR to main
StagingRecent masked copy or sampled prodFull pipeline run, integration, load, shadowAutomated gates
ProductionFull, access controlledScheduled training, serving, monitoringApproval plus canary

Code is promoted; models are registered once and promoted by alias. Training can run in production data access with the model artifact flowing downward (deploy models, not training code) when data cannot leave production.

Worked example: churn scoring

# 1. data + versions
dvc import-url s3://lake/curated/customers/snapshot=2026-10-27 data/customers   # or Iceberg snapshot id
# 2. dvc.yaml: validate -> features -> train -> evaluate
# 3. orchestrator run (weekly + on drift)
#    train.py logs to MLflow with tags: git_sha, data_snapshot, feature_view_version
# 4. gate (pipeline step)
assert challenger.auc >= champion.auc + 0.005
assert all(challenger.slice_auc[s] >= champion.slice_auc[s] - 0.01 for s in SLICES)
assert challenger.p95_latency_ms <= 50
# 5. register + alias challenger, GitOps PR updates serving revision to canary 10 percent
# 6. monitoring job (daily): PSI on top 20 features, score distribution, AUC on matured labels
# 7. promote on healthy canary: set alias champion, close the loop
  • Batch scores land in a table every night; online scoring is only for the call-centre screen.
  • Everything from step 2 on is containerised and uses the same configs across environments.

A method for architecting ML systems

  1. Frame: decision supported, metric, baseline, cost of errors, latency, volume, freshness.
  2. Data: sources, size and growth, labels and delay, privacy class, ownership.
  3. Choose serving pattern (batch, online, streaming, edge) from freshness and latency.
  4. Features: need a feature store? streaming features? skew risks?
  5. Training: compute need, distributed or not, retraining cadence and trigger.
  6. Gates and release: offline metrics, slices, shadow, canary, A/B.
  7. Monitoring and feedback: what drifts, how labels return.
  8. Platform fit: managed, open source or hybrid; team skills.
  9. Risk and compliance: classification, documentation, human oversight.
  10. Cost model and ADR: unit cost, scaling limits, alternatives rejected.

Sizing arithmetic

Training data: 2 B rows x 300 features x 4 B = 2.4 TB per full pass (columnar compression 3-5x on disk)
Online store: 80 M entities x 50 features x 8 B = 32 GB (x3 replication, plus indexes ~ 150 GB RAM-class)
Online QPS: 20k peak, p95 20 ms model + 30 ms feature fetch = 50 ms
  per replica 500 QPS -> 40 replicas + 30% headroom = 52; two regions N+1
Batch: 100 M scores nightly at 20k rows/s/worker -> 5,000 s per worker; 20 workers -> 4 min
