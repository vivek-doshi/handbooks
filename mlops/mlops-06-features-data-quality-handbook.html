Step 06 · Intermediate · Fix skew at the source

Feature Stores and Data Quality

Most production ML bugs are data bugs. This step covers keeping features consistent between training and serving and keeping data trustworthy.

IntermediateFeature storeData contracts

The skew problem

If training computes average spend in last 30 days in SQL and serving recomputes it in application code, the two will differ. Define each feature once and serve it both ways.

  • Offline store (warehouse or lake): large history for training.
  • Online store (Redis, DynamoDB, Bigtable, Cassandra): single-digit-millisecond lookups.
  • Registry: definitions, owners, versions, lineage.
  • Materialisation: jobs that compute and sync features offline and online.

Point-in-time correctness

Training rows must use feature values as they were at the event time, never later values, or you leak the future.

from feast import FeatureStore
store = FeatureStore(".")
train_df = store.get_historical_features(
    entity_df=events[["user_id", "event_timestamp"]],   # label timestamps
    features=["user_stats:spend_30d", "user_stats:txn_count_7d"]).to_df()   # as-of join

online = store.get_online_features(
    features=["user_stats:spend_30d"], entity_rows=[{"user_id": 42}]).to_dict()

Streaming and real-time features

  • Compute windowed aggregates in Flink, Spark Structured Streaming or Kafka Streams and write to the online store.
  • Use the same transformation definition for backfill (batch) and live (stream) paths.
  • Handle late and out-of-order events with watermarks, and track feature freshness as an SLI.
