Training Pipelines and Orchestration

A training pipeline turns versioned data into a validated, registered model with no manual steps. This step covers design rules and the orchestrator landscape, including Kubeflow.

IntermediateKubeflowDistributed training

Anatomy of a training pipeline

ingest -> validate data -> split -> feature transform -> train -> evaluate -> validate model (gates)
   -> register -> (trigger deployment pipeline)

Every stage: pure inputs -> versioned outputs, containerised, idempotent, logged to tracking
  • Idempotent and cached: re-running with the same inputs gives the same outputs and can reuse results.
  • Parameterised: dates, dataset version and hyperparameters are arguments, not edits.
  • Same code path for local, CI and cluster runs.
  • Fail early: data validation before expensive GPU stages.

Kubeflow Pipelines example

from kfp import dsl, compiler

@dsl.component(base_image="python:3.11", packages_to_install=["scikit-learn", "pandas"])
def train(data_uri: str, n_estimators: int, model: dsl.Output[dsl.Model], metrics: dsl.Output[dsl.Metrics]):
    import pandas as pd, joblib
    from sklearn.ensemble import RandomForestClassifier
    df = pd.read_parquet(data_uri)
    X, y = df.drop(columns="label"), df["label"]
    clf = RandomForestClassifier(n_estimators=n_estimators).fit(X, y)
    metrics.log_metric("train_acc", float(clf.score(X, y)))
    joblib.dump(clf, model.path)

@dsl.pipeline(name="churn-train")
def pipeline(data_uri: str, n_estimators: int = 300):
    train(data_uri=data_uri, n_estimators=n_estimators).set_caching_options(True)

compiler.Compiler().compile(pipeline, "churn.yaml")   # then submit to the KFP server

Kubeflow is a set of projects: Pipelines, the Training Operator (PyTorchJob, TFJob and others for distributed training), Katib (hyperparameter search), KServe (serving) and a model registry. Install only the parts you need, and expect real Kubernetes operations work.

Distributed training and tuning

  • Data parallel (DDP): replicate the model, shard the batch. Default for models that fit one GPU.
  • FSDP or DeepSpeed ZeRO: shard weights and optimiser state for large models.
  • Gang scheduling and queues: Kueue, Volcano or Slurm so jobs get all GPUs or none.
  • Checkpoint often to object storage; use spot GPUs with automatic resume.
  • Hyperparameter search: Optuna, Ray Tune, Katib or W&B sweeps; use early stopping and budget caps.
