Use Cases 4 and 5: SLM Fine-Tuning and Computer Vision

The fine-tuning case shows the LLMOps pipeline end to end, from data curation to adapter serving and the feedback flywheel. The vision case adds labelling operations and edge fleets.

Use case 4: Fine-tuning a small language model

ItemRequirement
GoalA tuned 8B model that replaces a frontier API for support classification, extraction and reply drafting
Data400 M tickets and chats (about 300 B tokens); 2 M curated candidates for tuning; PII-heavy
Traffic150 M calls a month, p95 under 2 s
CadenceRetrain monthly and on policy change; one adapter per business line (12)
ConstraintsData stays in region, audit, rollback within minutes
Decision firstFine-tune only after a prompted baseline plus retrieval has been measured and the gap is behaviour, cost or latency (see the GenAI decision ladder). This use case assumes that proof exists.

UC4 pipeline

Raw tickets (lake, Iceberg snapshot id) -> PII redaction + consent filter -> dedupe (MinHash) -> quality filter (CSAT, resolved, no escalation)
 -> label/augment: teacher LLM drafts, humans verify 5 percent -> split by time and customer -> DVC/lakeFS version "sft-2026-10"
 -> Train (orchestrator job on GPU pool): QLoRA or LoRA on 8B, 4 x 80 GB GPUs FSDP, bf16, checkpoints to object storage, tracked in MLflow/W&B
 -> Evaluate: golden set 1,500, task metrics, LLM judge calibrated on human labels, safety + regression suite, latency/throughput benchmark
 -> Gates: >= prompted baseline - 1 pt, no slice regression, safety pass, cost per call target
 -> Register adapter + model card + data version; sign artifact
 -> Deploy: vLLM with multi-LoRA (12 adapters on a shared base), GitOps rollout: shadow -> canary 5 percent -> full; frontier fallback for low confidence
 -> Monitor: traces, judge scores on sampled traffic, refusal and escalation rate, cost per resolved ticket, drift in query mix
 -> Feedback: agent edits and ratings -> next data version
  • Compute: 2 M examples x 800 tokens = 1.6 B tokens per epoch; at about 5,000 tokens per second per GPU on 4 GPUs that is roughly 22 hours per epoch, so a run is 1 to 2 days. Use spot with checkpoints; cache tokenised data.
  • Serving capacity: 150 M calls a month is about 60 per second on average, 200 at peak, at about 1,200 input and 150 output tokens; plan a vLLM pool measured against that, with autoscaling on queue depth.
  • Lineage: a deployed adapter links to the data snapshot, base model hash, code SHA and eval report; required for audit.
  • Base model upgrades force re-training and re-evaluation; keep the pipeline fully automated so this is a config change.
  • Risks: memorised PII, forgetting, template mismatch, judge bias. Mitigate with redaction, regression suites, identical chat templates and human calibration.

Use case 5: Computer vision quality inspection

ItemRequirement
Scale400 factories, 6,000 cameras, 40 images a second each, 1 PB of new images a month
GoalDetect defects in real time at the line; update models weekly as products change
LatencyUnder 50 ms at the edge, works offline
ConstraintsIntermittent connectivity, scarce defect labels, fleet of heterogeneous devices
Edge device: camera -> preprocessing -> optimised detector (TensorRT/ONNX, INT8) -> reject signal (local, offline-safe)
   -> uploads: all defects + uncertain + 0.5 percent random samples (active-learning selection) -> object storage
Cloud: ingest -> dedupe + metadata (line, product, lighting) -> labelling queue (CVAT/Label Studio, active learning picks hard cases)
   -> versioned dataset (DVC/lakeFS) -> train (GPU, mixed precision; pretrained backbone fine-tuned) -> eval per product + per site
   -> gates incl. recall on rare defects, false-reject cost, edge latency on target hardware
   -> convert + quantise + sign -> OTA rollout by ring: lab line -> 1 factory -> 10 percent -> all; auto-rollback on KPI drop
Monitoring: per-device latency, confidence distribution, reject rate drift, human audit sample accuracy, camera health
  • Data engine: the value is the loop: edge sampling, active learning, labelling, retraining. Budget labelling and storage as first-class costs; keep hot data 30 days and tier older data cold.
  • Storage: 1 PB a month needs lifecycle rules, thumbnails for browsing, and sampling policies so only informative images are kept long term.
  • Edge fleet ops: device registry, versioned model per device, staged OTA updates, remote health, secure boot and signed models.
  • Evaluation: metrics per defect class and site; test on new lighting and camera conditions; synthetic augmentation for rare defects.
  • Risks: distribution shift per factory, silent camera degradation, false rejects stopping the line. Mitigate with shadow mode first, per-site thresholds, and automatic fallback to the previous model.

Comparing the five cases

CaseScale driverKey MLOps challenge
1 Fraud25k QPS, 80 TBStreaming features, delayed labels, latency
2 Recommendations300 M users, 20 B events a monthMulti-stage serving, embedding refresh, A/B evaluation
3 Forecasting200 M seriesParallel training, backtesting, nightly batch cost
4 SLM tuning300 B tokens, 150 M calls a monthData curation, GPU training, adapter serving, lineage
5 Vision at edge1 PB images a month, 6,000 devicesData engine, edge rollout, labelling operations
  • Version data, features, models and prompts together.
  • Gate every release on slices, cost and latency, not one aggregate metric.
  • Close the loop: production feedback becomes the next training set.
  • Keep a safe fallback for every automated decision.
