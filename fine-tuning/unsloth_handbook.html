What is Unsloth?

// FOUNDATIONS · FROM A LIBRARY TO A FULL LOCAL AI PLATFORM

Unsloth started as an open-source Python library for making LLM fine-tuning radically faster and more memory-efficient — and it still is that. But by mid-2026 it has grown into a small platform: the same hand-written Triton/CUDA kernels now power a Python library (Unsloth Core), a fully local no-code browser UI (Unsloth Studio), and a zero-setup desktop app (Unsloth Desktop) — all sharing one training and inference engine underneath.

Unsloth rewrites the critical CUDA kernels — attention, cross-entropy loss, RoPE embeddings, and weight updates — in Triton and C++, patching them directly into Hugging Face Transformers. Training is numerically exact, not approximated, so accuracy is preserved while throughput and VRAM usage improve dramatically across every surface: code, Studio, or Desktop.

GGUF Explained

// FOUNDATIONS

GGUF (GPT-Generated Unified Format) is a binary file format designed by Georgi Gerganov (creator of llama.cpp) as the successor to GGML. It stores model weights plus all metadata needed to run inference in a single self-contained file — no Python, no Hugging Face Hub connection required at runtime.

Why GGUF matters

GGUF models run via llama.cpp, a pure C++ inference engine with CUDA / Metal / ROCm / Vulkan acceleration:

  • Single binary, no Python dependency
  • CPU + GPU hybrid inference for VRAM-limited setups
  • Quantized models (Q4_K_M, Q5_K_M, UD-Q4_K_XL, etc.) that are tiny but high quality
  • Runs in Ollama, LM Studio, llama-server, Unsloth Studio/Desktop, Jan, AnythingLLM

Quantization Formats & Dynamic 2.0

// TRAINING-TIME QUANTS VS INFERENCE-TIME GGUF

Unsloth supports multiple quantization strategies during training — distinct from the GGUF formats above, which apply at inference time.

4-bit NF4 (QLoRA)
NormalFloat4 — stores base model weights in 4-bit with a Normal-distribution mapping. LoRA adapters stay in float16/bfloat16. Best VRAM/quality ratio for training. Default in Studio's QLoRA method.
4-bit Int4
Integer 4-bit quantization. Slightly more VRAM-efficient than NF4 but marginally lower quality — useful for very tight VRAM budgets.
8-bit (LLM.int8)
Mixed-precision 8-bit. Good quality but uses more VRAM than NF4. Rarely needed with Unsloth — NF4 is usually better.
NVFP4
NVIDIA's 4-bit float format for Blackwell-class GPUs. Unsloth now publishes NVFP4 builds alongside GGUF/4-bit for select flagship models on the Hugging Face Hub.

Dynamic 2.0 GGUFs

Unsloth's Dynamic 2.0 quantization scheme selectively adjusts the quantization type of every possible layer, rather than applying one uniform bit-width. The combination differs per layer and per model — Gemma's layer profile is not the same as Llama's. Calibration uses a hand-curated dataset of 1.5M+ tokens per model to preserve conversational quality, and the scheme now works on both MoE and dense architectures (earlier "Dynamic" quantization only helped MoE models like DeepSeek-R1).

Model-Specific Quants
Each model uses a custom-tailored quantization scheme — the layers quantized in Gemma 4 differ significantly from Llama 4 or Qwen3.8.
Upstream Bug Fixes
Unsloth collaborates directly with the Qwen, Meta (Llama), Mistral, Google (Gemma), and Microsoft (Phi) teams — contributing accuracy fixes that land in the Dynamic quants first.
Benchmarked, Not Assumed
Dynamic quants are benchmarked on perplexity, KL-divergence, and Aider Polyglot. A Dynamic 3-bit DeepSeek V3.1 GGUF scored 75.6% on Aider Polyglot — beating many full-precision models.
ℹ️
Dynamic 2.0 GGUFs run in any standard GGUF-compatible engine — llama.cpp, Ollama, LM Studio, and Unsloth Studio/Desktop — no special runtime needed. Look for the unsloth/<model>-GGUF repos on Hugging Face and pick the UD- prefixed variant.

LoRA & QLoRA

// PARAMETER-EFFICIENT FINE-TUNING

LoRA (Low-Rank Adaptation) freezes the base model and trains small rank-decomposition matrices injected into attention and MLP projections. QLoRA combines LoRA with 4-bit quantization of the frozen base weights — this is what makes 7–70B fine-tuning possible on a single consumer GPU.

MethodTrainable ParamsVRAM (7B)QualityUse When
Full Fine-Tune100%~60–80 GBHighest ceilingYou have multi-GPU / A100+ cluster access
LoRA (16-bit)0.1–1%~16–18 GBVery close to full24GB+ single GPU, want max adapter quality
QLoRA (4-bit)0.1–1%~6–9 GBNear-identical to LoRADefault choice — 12–16GB consumer GPU
pythonlora_setup.py
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "unsloth/Qwen3.8-8B-Instruct-bnb-4bit",
    max_seq_length = 4096,
    load_in_4bit = True,   # QLoRA — set False for 16-bit LoRA
)

model = FastLanguageModel.get_peft_model(
    model,
    r = 32,                        # LoRA rank — higher = more capacity
    lora_alpha = 32,
    target_modules = ["q_proj", "k_proj", "v_proj", "o_proj",
                       "gate_proj", "up_proj", "down_proj"],
    lora_dropout = 0,               # 0 is fastest & optimized in Unsloth
    bias = "none",
    use_gradient_checkpointing = "unsloth",  # 30% less VRAM vs "True"
    use_rslora = False,          # rank-stabilized LoRA for r > 64
    random_state = 3407,
)
✅
Rank of thumb: r=16 for style/tone adaptation, r=32–64 for teaching new domain knowledge, r=128+ combined with use_rslora=True only for very large, diverse datasets. Higher rank ≠ automatically better — it increases VRAM and overfitting risk.

Dataset Preparation

// FINE-TUNING (CODE)

Unsloth accepts datasets from the Hugging Face Hub, local JSON/JSONL, CSV, or Parquet files. The chat_template utilities handle formatting for the model's expected instruction format automatically.

pythondataset_prep.py
from datasets import load_dataset
from unsloth.chat_templates import get_chat_template

tokenizer = get_chat_template(
    tokenizer,
    chat_template = "qwen3",   # or "llama-3.1", "gemma", "chatml"...
)

def formatting_prompts_func(examples):
    convos = examples["conversations"]
    texts = [tokenizer.apply_chat_template(c, tokenize=False,
             add_generation_prompt=False) for c in convos]
    return {"text": texts}

dataset = load_dataset("your-org/your-dataset", split="train")
dataset = dataset.map(formatting_prompts_func, batched=True)
Instruction Format
Single-turn task-response pairs. Best for narrow, well-defined tasks (classification, extraction, summarization).
Conversational (ShareGPT)
Multi-turn dialogues. Best for assistants and chatbots — captures context retention across turns.
Raw Text (Continued Pretraining)
Domain-adaptive pretraining on unlabeled text before instruction fine-tuning. Use Unsloth's UnslothTrainer for this.
✅
Don't have clean instruction-response pairs yet? Data Recipes in Unsloth Studio (§19) turns raw PDFs, docs, and text dumps into training-ready pairs automatically — useful before dropping into the code path above.

Training Loop

// PUTTING IT TOGETHER WITH SFTTRAINER
pythontrain.py
from trl import SFTTrainer, SFTConfig
from unsloth import FastLanguageModel, is_bfloat16_supported

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "unsloth/Qwen3.8-8B-Instruct-bnb-4bit",
    max_seq_length = 4096,
    load_in_4bit = True,
)
model = FastLanguageModel.get_peft_model(model, r=32, lora_alpha=32)

trainer = SFTTrainer(
    model = model,
    tokenizer = tokenizer,
    train_dataset = dataset,
    dataset_text_field = "text",
    args = SFTConfig(
        per_device_train_batch_size = 2,
        gradient_accumulation_steps = 8,
        num_train_epochs = 2,
        learning_rate = 2e-4,
        fp16 = not is_bfloat16_supported(),
        bf16 = is_bfloat16_supported(),
        output_dir = "outputs",
    ),
)

stats = trainer.train()
print(f"Peak VRAM: {torch.cuda.max_memory_allocated()/1e9:.2f} GB")
ℹ️
Prefer not to write this loop yourself? The exact same training run — model, dataset, hyperparameters — can be configured and launched from Unsloth Studio's Fine-tuning tab (§17) with live loss curves and GPU stats, no script required.

Curriculum Training

// STAGED DIFFICULTY FOR BETTER CONVERGENCE

Curriculum training orders examples from easy to hard (or general to specific) across multiple training stages, rather than shuffling everything together. This often improves convergence stability and final quality, especially for reasoning-heavy fine-tunes.

pythoncurriculum.py
# Stage 1: general instruction-following (broad, easy)
trainer = SFTTrainer(model=model, train_dataset=stage1_general, ...)
trainer.train()

# Stage 2: domain-specific examples (narrower, harder)
trainer = SFTTrainer(model=model, train_dataset=stage2_domain, ...)
trainer.args.learning_rate = 5e-5  # lower LR for the refinement stage
trainer.train()

# Stage 3: hard negatives / edge cases (narrowest, hardest)
trainer = SFTTrainer(model=model, train_dataset=stage3_edge_cases, ...)
trainer.args.learning_rate = 1e-5
trainer.train()
✅
Save a checkpoint after each stage (model.save_pretrained(f"stage{n}_checkpoint")) so you can roll back if a later stage degrades quality on your eval set.

Knowledge Distillation

// TRAIN A SMALL STUDENT FROM A LARGE TEACHER

Distillation trains a small "student" model to mimic a larger "teacher" model's outputs — either its final answers (response distillation) or its full output distribution (logit distillation). Unsloth's speed makes this practical to run locally rather than only via cloud APIs.

pythondistill.py
# 1. Generate teacher responses (once, offline)
teacher, teacher_tok = FastLanguageModel.from_pretrained(
    "unsloth/Qwen3.8-32B-Instruct-bnb-4bit", fast_inference=True
)
FastLanguageModel.for_inference(teacher)

teacher_outputs = [teacher.fast_generate(p) for p in prompts]

# 2. Fine-tune a small student on (prompt, teacher_response) pairs
student, student_tok = FastLanguageModel.from_pretrained(
    "unsloth/Qwen3.8-4B-Instruct-bnb-4bit"
)
student = FastLanguageModel.get_peft_model(student, r=16)

# dataset = {"prompt": prompts, "response": teacher_outputs}
trainer = SFTTrainer(model=student, train_dataset=distill_dataset, ...)
trainer.train()
ℹ️
Combine distillation with Model Arena in Studio (§18) to visually compare the student's answers against the teacher's on held-out prompts before deploying.

Reinforcement Learning — GRPO / GSPO / DPO

// NEW: RL WITH FAST_INFERENCE VLLM ROLLOUTS

Unsloth supports the full range of RL post-training methods TRL provides — DPO, ORPO, GRPO, and GSPO — and the standout feature here is fast_inference=True: loading the model with Unsloth's built-in vLLM integration so the same weights are used for both training and the high-throughput rollout generation RL needs, without doubling VRAM usage.

pythongrpo_setup.py
# pip install unsloth vllm
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "unsloth/Llama-3.2-3B-Instruct",
    max_seq_length = 4096,
    load_in_4bit = True,
    fast_inference = True,     # enables the vLLM backend for rollouts
    gpu_memory_utilization = 0.6,
)

model = FastLanguageModel.get_peft_model(
    model, r=32, lora_alpha=32,
    target_modules=["q_proj","k_proj","v_proj","o_proj"],
)

# Unsloth removes double memory usage when loading vLLM + training weights
# together — ~5GB saved for an 8B model, ~3GB for a 3B model.
GRPO
Group Relative Policy Optimization — the method behind DeepSeek-R1-style reasoning training. Rewards are computed over groups of sampled completions; no separate value/critic model needed.
GSPO
Sequence-level variant with improved stability for longer generations and multi-step reasoning chains.
DPO / ORPO
Preference-pair training — no reward model or rollout loop needed, just (chosen, rejected) response pairs. Cheaper than GRPO/GSPO for style and safety alignment.
⚠️
GRPO takes patience. Wait for at least 300 steps before expecting the reward signal to trend upward — this is inherent to how group-relative RL converges, not a bug. Budget 8–12+ hours for meaningful results; short demo runs (an hour or two) will look "subpar" by design. Use a base model of at least ~1.5B parameters so it can reliably generate structured thinking tokens.
🖼️
Vision RL: vLLM fast inference now also covers VLMs — set fast_inference=True on FastVisionModel and optionally UNSLOTH_VLLM_STANDBY=1 for a memory-efficient standby mode that limits speed loss during GRPO/GSPO on vision-language models. Note vLLM does not support LoRA on vision/encoder layers — set finetune_vision_layers=False when training a LoRA adapter with fast inference enabled.

No-Code Fine-Tuning Workflow

// THE FINE-TUNING TAB, STEP BY STEP

The Fine-tuning page in Studio is a single configure screen split into four areas: Model, Dataset, Parameters, and Training/Config. It fills in sensible defaults for every hyperparameter the moment you pick a model.

1
Pick a base model
Type into the Hugging Face search box or browse recommended models. For a single consumer GPU, Unsloth's pre-built 4-bit dynamic quants (e.g. unsloth/Llama-3.1-8B-Instruct-unsloth-bnb-4bit) load fastest and use the least VRAM.
2
Choose a training method
QLoRA (4-bit) is the default and the right choice for a single GPU. Switch to LoRA (16-bit) or Full fine-tuning only when you have the VRAM headroom and a specific reason to update more weights.
3
Load a dataset
Studio reads CSV, JSONL, JSON, and Parquet — from the Hugging Face Hub, a local file, S3, or the output of a Data Recipe (§19).
4
Tune parameters (optional)
Rank, learning rate, epochs, sequence length, and batch size are pre-filled based on the model and your detected VRAM. Override only what you need to.
5
Train and monitor live
Watch live loss curves, GPU memory/utilization, tokens/sec, and startup status without leaving the browser.
6
Test, then export
Open the trained checkpoint in Chat, compare it against the base model in Model Arena, then export from the Export tab.
⚠️
At the time of writing, the Fine-tuning tab accepts Parquet or a Data Recipe's output directly, but not a raw .jsonl upload with manual column-to-role mapping. If your data is already clean JSONL with a known schema, the Unsloth Core code path (§10–12) currently has less friction than the UI for that specific case.

Chat Capabilities

Data Recipes

// TURN RAW DOCUMENTS INTO TRAINING DATA

Data preparation is usually the real bottleneck in fine-tuning, not the training run itself. Data Recipes addresses this directly: point it at raw source material — PDFs, internal docs, transcripts, spreadsheets — and it generates structured instruction-response training pairs automatically, ready to feed into the Fine-tuning tab or export as Parquet/JSONL for the code path.

Ingest
Upload PDFs, DOCX, TXT, CSV, or paste raw text. Data never leaves your machine.
Generate
A local or connected model converts source material into instruction-response pairs, with configurable style and difficulty.
Curate
Review, edit, filter, and deduplicate generated pairs before they go anywhere near a training run.
✅
Example workflow: upload de-identified domain documents → generate instruction-response pairs with Data Recipes → fine-tune a mid-size model with QLoRA in the Fine-tuning tab → export to GGUF → run fully offline. This closes a loop that previously required a dedicated data engineering step before anyone could even start training.
⚠️
Generated pairs inherit any bias, hallucination, or inaccuracy present in the generating model. Always spot-check a sample of Data Recipe output — especially for regulated domains (medical, legal, financial) — before training on it at scale.

Custom & Hugging Face Models

// LOADING ANYTHING — NOT JUST THE OFFICIAL CATALOG

Unsloth is not limited to a curated model list. Both Unsloth Core and Unsloth Studio can load essentially any Transformers-compatible model from the Hugging Face Hub, plus fully custom local checkpoints and previously downloaded caches from other tools.

In Studio / Desktop

  • Search the Hub directly — type any Hugging Face model name or search term into the model combobox; Studio fetches its config and pre-fills sensible defaults automatically.
  • Set a custom model directory — point Studio at a folder of local weights outside the standard cache.
  • Auto-detected caches — models already downloaded via the Hugging Face Hub cache, or via other local tools like LM Studio, are detected and listed automatically.
  • Gated models — paste a Hugging Face access token in Settings for gated repos (Llama, Gemma, and similar license-gated families).
  • Fine-tuned models — locally trained and exported checkpoints appear under the Fine-tuned tab in the model dropdown, ready to chat with immediately after export.
  • GGUF is inference-only — GGUF-format models are excluded from the Fine-tuning tab's model list since GGUF is a quantized inference format, not a trainable one; load the original safetensors repo to fine-tune instead.

In Unsloth Core (Python)

FastLanguageModel.from_pretrained wraps the standard Transformers loading path — it calls AutoConfig.from_pretrained and AutoModelForCausalLM.from_pretrained under the hood, then patches attention, decoder-layer, and rotary-embedding classes for speed. This means any architecture Transformers already supports is a candidate for Unsloth's optimizations, including models with no official Unsloth-branded repo.

pythoncustom_model.py
from unsloth import FastLanguageModel

# Any Hub repo ID — not just the "unsloth/" namespace — works here,
# as long as the architecture is Transformers-compatible.
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "your-org/your-custom-finetuned-checkpoint",
    max_seq_length = 4096,
    dtype = "auto",          # bf16 on Ampere+, fp16 on older cards
    load_in_4bit = True,
    token = "hf_...",         # required for gated / private repos
)

# A local directory of safetensors works identically:
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "./my-local-checkpoint",
    max_seq_length = 4096,
    load_in_4bit = True,
)

Export Formats

// GGUF · MERGED SAFETENSORS · LORA ADAPTER

Once training finishes, choose an export format that matches your deployment target. Both Unsloth Core and Studio's Export tab support the same three paths.

FormatBest ForDeployment Target
GGUF (Dynamic 2.0)Fully local, CPU+GPU hybrid inferenceOllama, llama.cpp, LM Studio, Unsloth Studio/Desktop
Merged Safetensors (16-bit)Maximum quality servingvLLM, TGI, Hugging Face Inference Endpoints
Merged Safetensors (4-bit)Further DPO/RL training, or memory-light servingContinued training pipelines; use with caution otherwise
LoRA Adapter OnlySmallest artifact, swap adapters at runtimeAny base-model server that supports adapter loading
pythonexport.py
# GGUF export (Dynamic 2.0 quant, e.g. UD-Q4_K_XL)
model.save_pretrained_gguf("model-gguf", tokenizer,
    quantization_method = "UD-Q4_K_XL")

# Merged 16-bit safetensors — best quality for vLLM serving
model.save_pretrained_merged("model-merged", tokenizer,
    save_method = "merged_16bit")

# Merged 4-bit — only if you know what comes next (e.g. further DPO)
model.save_pretrained_merged("model-merged-4bit", tokenizer,
    save_method = "merged_4bit_forced")

# LoRA adapter only (smallest artifact)
model.save_pretrained("model-lora")
tokenizer.save_pretrained("model-lora")

# Push straight to the Hugging Face Hub from any of the above
model.push_to_hub_gguf("your-org/your-model-GGUF", tokenizer,
    quantization_method = "UD-Q4_K_XL", token = "hf_...")
⚠️
Only use merged_4bit_forced if you have a specific downstream need for it (e.g. DPO training on the merged weights, or Hugging Face's online 4-bit inference path). For general local serving, prefer GGUF; for GPU-server serving, prefer 16-bit merged safetensors.

Unsloth's Inference Engine & vLLM

// NEW: TWO INFERENCE BACKENDS, ONE API

Unsloth ships with two inference backends behind the same model.generate() interface, and picks between them automatically based on how the model was loaded.

⚙ Native Fast Inference
  • Default backend — no extra dependency required
  • Paged KV cache + inference-specific fused kernels
  • Automatic mode switching between train and inference
  • ~2× faster than stock Transformers generation
  • Best for: single-request chat, low-latency local serving
🚀 vLLM Backend (fast_inference=True)
  • High-throughput batched generation via PagedAttention
  • Memory-deduplicated with training weights — no double VRAM cost
  • Native LoRA adapter serving without merging first
  • Required for GRPO/GSPO RL rollouts at usable speed
  • Best for: RL training, concurrent multi-user serving

Native Fast Inference

pythonnative_inference.py
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained("outputs/checkpoint-final")
FastLanguageModel.for_inference(model)   # switches to the fast generation path

inputs = tokenizer(["Explain QLoRA in one sentence."], return_tensors="pt").to("cuda")
outputs = model.generate(**inputs, max_new_tokens=128, use_cache=True)
print(tokenizer.batch_decode(outputs))

Deploying with vLLM Directly

After fine-tuning, you can also hand a merged model off to a standalone vllm serve process for production-grade concurrent serving with an OpenAI-compatible API.

bashvllm_serve.sh
# Install a current vLLM build
pip install --upgrade pip
pip install uv
uv pip install -U vllm --torch-backend=auto

# Serve a merged Unsloth fine-tune, OpenAI-compatible API
vllm serve ./model-merged \
  --dtype auto \
  --host 0.0.0.0 \
  --port 8000 \
  --api-key token-abc123 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.9
✅
Connect that server back to Studio: in Studio's Settings → Connections, add the vLLM server's base URL and API key. It then appears in the model dropdown alongside local models — giving you a single chat UI over both local GGUFs and a remote/production vLLM deployment.
⚠️
A model fine-tuned with Unsloth and then served through a separately installed vLLM instance can occasionally produce off-target responses if the chat template or LoRA merge step doesn't match exactly what vLLM expects. Prefer the merged-safetensors export path over hand-wiring a raw checkpoint into vLLM, and verify output quality with a held-out prompt set before shipping.

Troubleshooting

// COMMON ERRORS & FIXES

CUDA Out of Memory (OOM)

fix
# Try these in order until OOM resolves:
1. Reduce max_seq_length:    4096 → 2048 → 1024
2. Reduce batch size:        per_device_train_batch_size=1
3. Increase grad accum:     gradient_accumulation_steps=16
4. Use 8-bit Adam:           optim="adamw_8bit"
5. Enable grad checkpointing: use_gradient_checkpointing="unsloth"
6. Reduce LoRA rank:         r=32 → r=16
7. If using fast_inference: lower gpu_memory_utilization
8. Disable packing temporarily and check GPU util with nvidia-smi

Triton / CUDA Kernel Errors on RTX 50 Series

fix
# Blackwell (sm_120) needs CUDA 12.8 wheels + a current driver
pip install torch torchvision torchaudio --index-url \
  https://download.pytorch.org/whl/cu128

# Ensure your NVIDIA driver is current
nvidia-smi  # Check driver version

Slow Training — Tokens/sec Too Low

diagnose
# Check GPU utilization during training
watch -n 1 nvidia-smi

# If GPU util < 80%, your DataLoader is bottlenecking:
# - Increase dataset_num_proc (e.g., 4 → 8)
# - Enable packing=True to densify batches
# - Move dataset to Linux FS (not /mnt/c/ in WSL2)
# - Pre-tokenize and cache dataset before training

NaN / Inf Loss

fix
# NaN loss usually means LR too high or bad data
1. Lower LR: 2e-4 → 5e-5
2. Add max_grad_norm=1.0 to clip gradients
3. Inspect dataset for empty or malformed examples
4. Try bf16=False, fp16=True (or vice versa)
5. Increase warmup_steps to 100+

Studio: KV Cache Setting Reverts After Reload

workaround
# Known beta issue — KV cache precision can reset Q8 → F16 on page reload.
1. Re-apply the Q8 KV cache setting after any Studio page refresh
2. Avoid reloading mid-conversation on long-context chats
3. Track fixed status in the Unsloth changelog before relying on it in a demo

Version Mismatch (Unsloth / PEFT / TRL / Transformers)

bash
# Pin compatible versions together for reproducible runs
pip install "unsloth==2026.8.3"
pip install "peft>=0.13" "trl>=0.19" "transformers>=4.46"

# Check what's installed
pip show unsloth peft trl transformers | grep -E "Name|Version"
