Architecting DevOps for 20 microservices

With around twenty services and multiple teams, consistency becomes the main challenge. This capstone gives an opinionated reference architecture, explains each decision and the alternatives, and ties together everything in the path.

Reference architectureGitOpsHelm and Argo CDObservabilitySecurityDecision log

1. Landscape and goals

Goals: independent deploys per service, a uniform paved road, strong security defaults, observability by default, and cost visibility. Assume 20 services owned by several teams, a managed Kubernetes cluster per environment (or per region), a shared platform team, and a service mesh or gateway only where needed.

PrerequisiteThis design assumes you are comfortable with Steps 05–11. If a term is unfamiliar, revisit that step first.

2. Source control and branching

  • Repo per service (polyrepo) for ownership and independent pipelines; shared code lives in versioned libraries and reusable workflows, not copy-paste. A monorepo is viable with strong tooling (Bazel, Nx) but raises build and access complexity.
  • Trunk-based development, short-lived branches, feature flags, and required checks on main (Step 02).
  • A separate GitOps config repo (or one per environment group) holds deployment state. It is mandatory: it gives an auditable, reviewable record of what runs where.

4. Packaging and GitOps tooling

  • Helm with one shared, versioned "service chart" that each service configures through values, giving consistent probes, resources, security context, autoscaling, and monitoring. Kustomize overlays handle per-environment differences. Raw manifests do not scale to 20 services; Kustomize alone makes sharing defaults awkward.
  • Argo CD with ApplicationSets generates an app per service per environment, supports multi-cluster, SSO, RBAC and sync waves. Flux is an equally valid choice if your team prefers a composable, CLI-first model; do not run both.
  • Use Argo Rollouts or Flagger for canary and blue/green, with metric analysis.

5. Kubernetes platform layout

  • Cluster per environment (at minimum prod separate from non-prod); namespace per team or service with quotas, LimitRanges, default-deny NetworkPolicies, and Pod Security restricted.
  • Gateway API for north-south traffic with automated TLS; add a service mesh only if you need uniform mTLS, traffic policy, or advanced telemetry.
  • Autoscaling: HPA or KEDA for pods, Karpenter or Cluster Autoscaler for nodes, PodDisruptionBudgets and topology spread for resilience.
  • Platform add-ons managed by the platform team through GitOps: ingress/gateway, cert-manager, External Secrets, policy engine, observability agents, cost tooling.
  • Clusters, networks and cloud accounts provisioned with Terraform (Step 09), versioned and drift-checked.

6. Observability and reliability

  • OpenTelemetry everywhere; Collector DaemonSet and gateway; traces, metrics, and logs correlated by trace ID. Choose a backend (Grafana LGTM stack, or a commercial platform) and standardize dashboards generated from service metadata.
  • Each service ships with SLOs, burn-rate alerts, and a runbook link created from a template when the service is scaffolded.
  • Run chaos and game days, define RTO and RPO per tier, and test restores regularly.

7. Secrets, environments and security

  • External Secrets Operator with Vault or a cloud secret manager; workload identity for cloud access; short-lived credentials.
  • Environments: dev (ephemeral preview environments per pull request if affordable), staging (production-like), production. Same image and chart everywhere; only values differ. Promote by pull request in the config repo.
  • Supply chain: SLSA provenance, cosign signatures, admission verification, SBOM storage, dependency update automation, and scheduled rescans of deployed images.
  • Policy as code with Kyverno or Gatekeeper in audit then enforce; required owner and cost labels; audit logging and runtime detection with Falco or Tetragon.
