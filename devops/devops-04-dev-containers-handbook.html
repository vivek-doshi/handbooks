Dev Containers: reproducible dev environments

A dev container runs your editor against a container that holds the exact toolchain your project needs. New developers get a working environment in minutes, and local, CI, and cloud workspaces stay aligned.

devcontainer.jsonFeaturesCodespacesOnboarding

1. Why use them

  • One definition of the toolchain checked into the repo (.devcontainer/).
  • Fast onboarding and identical environments for every contributor.
  • Works locally (VS Code, JetBrains), in GitHub Codespaces, and as a base for CI.

It builds directly on Step 03: the environment is a container image, optionally orchestrated with Compose for databases and queues.

2. Anatomy of devcontainer.json

PropertyPurpose
image / build / dockerComposeFileWhere the environment comes from
featuresComposable installable tools (Node, .NET, Docker-in-Docker, kubectl, Terraform)
customizationsEditor extensions and settings
postCreateCommand and other lifecycle hooksInstall dependencies after creation
forwardPorts, mounts, remoteUserNetworking, volumes, non-root user
See real snippets in the DevOps Playbook Complete devcontainer.json examples for Python, Node, full-stack with Compose and data science are available there. Open the DevOps Playbook code template browser to read and copy complete, working files.

3. Secure and practical defaults

  • Use a non-root remoteUser.
  • Never commit secrets; use Codespaces or editor secrets and environment variables.
  • Pin feature versions and base image tags; keep images updated through Dependabot or Renovate.
  • Cache package directories in named volumes to keep rebuilds fast.
PracticeAdd a .devcontainer to one repo so a fresh clone can run its tests with zero manual installs.
