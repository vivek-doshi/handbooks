Step 10 · Advanced · Declarative delivery you can trust: reconcile, verify, enforce

GitOps, supply chain security and policy as code

Once you have pipelines, clusters, and infrastructure as code, the next question is trust: who can change production, and how do we know what we run is what we built? This step covers GitOps delivery, secret handling, software supply chain security, and policy as code.

1. GitOps principles

OpenGitOps defines four principles: the system is declarative; desired state is versioned and immutable (Git); agents pull approved state automatically; and agents continuously reconcile drift. Benefits: a complete audit trail, easy rollback (revert a commit), no cluster credentials in CI, and self-healing.

2. Repository and promotion design

  • Separate application repos (code, CI) from a GitOps/config repo (manifests, environment overlays).
  • Use Helm or Kustomize for packaging: Helm for third-party and parameterized charts, Kustomize overlays for simple per-environment patches.
  • CI builds and signs the image, then opens a pull request (or uses image automation) updating the image tag or digest in the config repo; merge triggers reconciliation.
  • Promote by pull request across environment directories; production requires approval.
  • Use ApplicationSets (Argo) or Kustomizations per cluster to scale to many clusters and tenants.
See real snippets in the DevOps Playbook Argo CD Application and ApplicationSet patterns, promotion flow, Helm and Kustomize layouts, and Kyverno policies are provided as templates there. Open the DevOps Playbook code template browser to read and copy complete, working files.

3. Progressive delivery

Deploy safely by controlling exposure: rolling (default), blue/green, canary with automated analysis, and feature flags to decouple deploy from release. Argo Rollouts or Flagger shift traffic in steps and abort automatically when SLO metrics (error rate, latency) regress. Database changes use expand/contract migrations so old and new versions run together.

4. Secrets and identity

  • Never store plaintext secrets in Git. Use External Secrets Operator or the Secrets Store CSI Driver with Vault or a cloud secret manager; or encrypted-in-Git (SOPS, Sealed Secrets) if you accept key-management overhead.
  • Prefer workload identity (IRSA, Azure Workload Identity, GKE Workload Identity) over static credentials; prefer short-lived and dynamic secrets.
  • Rotate regularly, audit access, and scan repositories and images for leaked secrets.

Pin dependencies and base images by digest, use hermetic or reproducible builds where feasible, and aim for progressively higher SLSA build levels. Keep a vulnerability management process with severity and SLA targets, and use VEX statements to reduce noise.

6. Policy as code and runtime

  • Admission policy: Kyverno or OPA Gatekeeper, and native ValidatingAdmissionPolicy (CEL, GA in 1.30). Start in audit mode, then enforce: no privileged pods, required resource limits, required cost and owner labels, allowed registries, signed images.
  • Shift left: run the same policies in CI with Conftest or Kyverno CLI so developers see failures before merge.
  • Runtime: Falco or Tetragon for syscall-level detection, audit logging, and runbooks for response.
  • Compliance evidence: collect policy results, scan reports, and attestations automatically.
PracticeInstall Argo CD or Flux on a local cluster, deploy an app from a config repo, then add an admission policy that rejects unsigned images and prove it blocks a test pod.
