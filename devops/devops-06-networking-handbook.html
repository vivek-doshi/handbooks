Networking for Docker and Kubernetes

Most production incidents in containerized systems are network problems in disguise. This step builds the model from IP, DNS, and ports up through Docker networks, the Kubernetes network model, traffic entry, and zero-trust policy.

1. Fundamentals you will use daily

  • OSI/TCP-IP layers: most issues sit at L3/L4 (routing, ports) or L7 (HTTP, TLS, DNS).
  • CIDR planning: pod, service, and node ranges must not overlap with each other or with VPC/on-prem ranges you will peer with.
  • DNS first: when something "cannot connect", check name resolution and TTLs before anything else.

2. Docker networking

Use user-defined networks (not the default bridge) so Compose services resolve each other by name. -p host:container publishes a port; EXPOSE is documentation only.

3. The Kubernetes network model

Three rules: every pod gets its own IP; pods can reach all other pods without NAT; agents on a node can reach that node's pods. A CNI plugin implements this (Cilium, Calico, cloud-native VPC CNIs, Flannel). Cilium uses eBPF and can replace kube-proxy and provide L7-aware policy and observability. Pick the CNI before building the cluster because changing it later is disruptive.

  • Service types: ClusterIP (internal), NodePort, LoadBalancer (cloud LB), ExternalName. Headless Services give per-pod DNS for StatefulSets.
  • CoreDNS serves svc.namespace.svc.cluster.local; mind ndots and DNS caching (NodeLocal DNSCache) for latency.

4. Getting traffic in: Ingress and Gateway API

Gateway API (GatewayClass, Gateway, HTTPRoute, and GRPCRoute) is the successor to Ingress, with role-oriented resources, richer routing, and portable features across implementations (Envoy Gateway, Cilium, Istio, cloud gateways). Ingress still works but is frozen in feature scope, and the widely used community ingress-nginx controller has been announced for retirement, so choose Gateway API for new clusters and plan migrations. Terminate TLS with cert-manager and automate certificates.

5. Zero trust inside the cluster

  • Start with a default-deny NetworkPolicy per namespace, then allow only needed ingress and egress (including DNS).
  • NetworkPolicies need a CNI that enforces them; test them with connectivity checks in CI.
  • Add mTLS and identity-based authorization with a service mesh (Istio, including ambient mode without sidecars, or Linkerd) when you need uniform encryption, retries, traffic shifting, and telemetry across many services. Do not add a mesh for a handful of services.

6. Troubleshooting ladder

  1. Pod to pod by IP (CNI).
  2. Pod to Service ClusterIP and endpoints (kube-proxy or eBPF, selectors, readiness).
  3. DNS lookup.
  4. Ingress or Gateway to Service.
  5. Policy and mesh authorization.
  6. External load balancer and security groups.

Tools: kubectl port-forward, a netshoot debug pod, kubectl get endpointslices, hubble observe (Cilium), and packet capture on the node as a last resort.

PracticeApply a default-deny policy to a namespace, confirm the app breaks, then add the minimal allow rules (frontend to backend, backend to DNS and database) and verify each with a debug pod.
