Infrastructure as Code with Terraform

Infrastructure as Code makes environments reproducible, reviewable and auditable. This step goes beyond terraform apply: state design, module contracts, testing, delivery workflow and governance for teams.

State and lockingModulesTestingPolicyPipelinesDrift

1. The model

Terraform describes desired infrastructure in HCL. The workflow is init → plan → apply: the plan diffs configuration against state and reality, and a reviewed plan is applied. Providers translate resources into API calls. OpenTofu is the Linux Foundation fork created after Terraform moved to the BUSL license; the language is largely compatible, so check licensing and feature needs when choosing, and pin the tool version either way.

2. State is the critical asset

  • Use a remote backend with locking (S3 with native lockfile locking, Azure Blob, GCS, or HCP Terraform / similar). Enable versioning and encryption.
  • Split state by blast radius and change cadence: network, platform/cluster, and each application separately; never one state for everything.
  • Treat state as sensitive: it can contain secrets. Restrict read access, and use ephemeral values and write-only arguments (newer Terraform) or an external secret manager so secrets stay out of state.
  • Bootstrap the backend itself first, then migrate state into it.

3. Modules and composition

  • A module has a narrow purpose, typed variables with validation, documented outputs, and a version.
  • Prefer composition of small modules over one flexible "do everything" module; avoid deeply nested modules.
  • Publish internal modules to a registry or tag them in Git; pin consumers to versions and update deliberately.
  • Use for_each over count for stable addressing; use moved blocks for safe refactors and import blocks to adopt existing resources.
  • Pin provider versions and commit the lock file.

5. Delivery workflow and access

  1. Pull request runs fmt, validate, scans, and posts the plan.
  2. Review and approve the plan, then merge.
  3. Pipeline applies the saved plan using OIDC federation to the cloud (no static keys), with a protected production environment.
  4. Scheduled plan-only runs detect drift and alert.

Limit human write access to production; keep break-glass procedures. Tools such as Atlantis, Terraform Cloud, Spacelift, or plain CI work; what matters is consistent, auditable applies. Alternatives and complements: Pulumi, Crossplane (Kubernetes-native control planes, a building block for platforms in Step 11), and CDK for Terraform.

6. Multi-environment layout

Prefer one root configuration per environment-and-stack that reuses versioned modules with environment-specific variables (directories, not workspaces, for strongly isolated prod). Keep accounts/subscriptions separate per environment, and keep naming and tagging conventions in a shared module, including cost-allocation tags for Step 11.

PracticeCreate a small module with variable validation and a terraform test, publish it with a tag, consume it from two environments with a remote backend, and add a scheduled drift check.
