Getting Started

Quick Start

Five commands to go from clone to running local environment with a deployed workload.

ℹ
Prerequisites Git 2.40+, Docker Desktop 4.x, kubectl 1.29+, kind 0.24+, Helm 3.14+, Python 3.12+, Node 20+
bash
# 1. Clone the repository
git clone https://github.com/your-org/cicd-reference.git
cd cicd-reference

# 2. Verify all tools are installed
bash scripts/env-checker.sh

# 3. Install pre-commit hooks (run once)
make hooks

# 4. Start a local kind cluster with registry and ingress
make dev

# 5. Build and deploy the example app
make deploy-dev

What just happened?

  • make hooks installs pre-commit guardrails for secrets, Dockerfile linting, Terraform validation, YAML checks, and conventional commits.
  • make dev creates a kind cluster named devops-playbook, starts a local registry at localhost:5001, and installs ingress-nginx.
  • make deploy-dev builds the Docker image, pushes it to the local registry, and applies the dev Kustomize overlay.

Golden Path

Kubernetes Microservice

End-to-end path: local dev → CI build+scan → image push → GitOps update → ArgoCD sync → Kubernetes → burn-rate alerts.

ℹ
File: docs/golden-paths/kubernetes-microservice.md

Flow

pipeline
local dev → pre-commit → CI (build + test + scan) → image push
         → GitOps update → ArgoCD sync → Kubernetes → alerts

Steps

  1. Start local environment — bash local-dev/kind/setup.sh creates kind cluster, local registry, ingress-nginx, and applies dev overlay.
  2. Containerize — copy docker/<language>/Dockerfile template. Ensure non-root user, pinned base image digest, and HEALTHCHECK.
  3. Install pre-commit — make hooks. Guardrails: Hadolint, Gitleaks, Checkov, YAML/JSON validation, conventional commits.
  4. Pick a CI template — ci/github-actions/, ci/azure-pipelines/, or ci/gitlab-ci/. Copy the relevant template and connect to your repository.
  5. Write Kubernetes manifests — start from cd/kubernetes/_base/. Require CPU/memory limits, liveness/readiness probes, security context (runAsNonRoot: true).
  6. Create environment overlays — copy cd/kubernetes/_overlays/dev/ and staging/production versions. Use Kustomize for image tags and replica counts.
  7. Set up GitOps — create an ArgoCD Application or Flux Kustomization pointing at your overlay path.
  8. Define SLOs — copy observability/prometheus/slos/slo-schema.yaml. Write recording rules with naming convention slo:<service>:<metric>:<window>.
  9. Register in service catalog — create catalog/services/<service>.yaml, set lifecycle, owner, runbook URL, SLO file, cost center.
  10. Validate everything — make catalog-validate slo-validate policy-report.
Golden Path

SLO-Driven Development

Define availability or latency SLOs, write multi-window burn-rate alerts, connect error budget tracking, and run quarterly reviews.

⚠
Model constraint: Only the multi-window burn-rate model (Google SRE Workbook) is used. Four fixed alert tiers — never deviate from these thresholds.

Burn-Rate Alert Tiers

TierBurn RateWindowsfor DurationSeverity
1 — Critical14.4×1h + 5m2mPage immediately
2 — High6×6h + 30m15mPage during business hours
3 — Warning3×24h + 2h1hTicket
4 — Info1×72h + 6h3hWeekly review

Recording Rule Naming Convention

prometheus
# Pattern: slo:<service>:<metric>:<window>
record: slo:api_gateway:error_rate:1h
expr: |
  sum(rate(http_requests_total{job="api-gateway",status=~"5.."}[1h]))
  / sum(rate(http_requests_total{job="api-gateway"}[1h]))

Steps

  1. Copy observability/prometheus/slos/slo-schema.yaml to <service>-slo.yaml.
  2. Write recording rules — never inline multi-window ratios into alert expressions.
  3. Define burn-rate alerts referencing recording rules at all 4 tiers.
  4. Import observability/prometheus/dashboards/slo-dashboard.json in Grafana.
  5. Connect Alertmanager to PagerDuty or Slack (notifications/).
  6. Add slo.definition_file to your service catalog entry.
  7. Schedule quarterly error budget review using docs/runbooks/slo-quarterly-review.md.

Compliance Mapping

SLO recording rules and alert history satisfy SOC 2 controls CC7.2 (monitoring) and CC7.4 (incident response). Include this cross-reference in your compliance evidence.

Golden Path

Service Catalog Registration

Standardizes how teams register services, validate ownership metadata, and enforce admission guardrails in Kubernetes.

Two-Gate Model

Every service registration passes through two mandatory gates:

  1. CI Gate — catalog/scripts/validate-catalog.py --strict runs on every PR touching catalog/.
  2. Admission Gate — Kyverno require-catalog-registration ClusterPolicy blocks deployments in production namespaces that lack the catalog.io/registered: "true" annotation.

lifecycle Requirements

Fieldalphabetastable
metadata.ownerRequiredRequiredRequired
spec.runbook_urlOptionalOptionalRequired
spec.slo.definition_fileOptionalOptionalRequired
spec.cost_centerOptionalOptionalRequired

Steps

  1. Create catalog/teams/<team-name>.yaml from catalog/teams/schema/team.yaml.
  2. Create catalog/services/<service-name>.yaml from catalog/schema/service.yaml. Ensure metadata.name matches the Deployment app label.
  3. Validate locally: python catalog/scripts/validate-catalog.py --strict --skip-url-check
  4. Regenerate CODEOWNERS: python catalog/scripts/generate-codeowners.py --output .github/CODEOWNERS
  5. Open PR — CI gate validates automatically via .github/workflows/validate-catalog.yml.
  6. Annotate Deployment: catalog.io/registered: "true"
  7. Apply Kyverno policy: kubectl apply -f policy/kyverno/require-catalog-registration.yaml

Supply Chain Security

Keyless image signing with Cosign, SBOM generation, SLSA provenance, and Kyverno admission verification.

ℹ
Prerequisite: OIDC federation must be configured before keyless signing works. See docs/guides/github-actions-oidc.md.

Key Rules

  • Always pin cosign, slsa-github-generator, and anchore/sbom-action to specific versions or SHAs — never floating tags. Add # <-- UPDATE QUARTERLY to each pin.
  • Every cosign verify must include --certificate-identity-regexp and --certificate-oidc-issuer.
  • New supply chain policies extend secops/supply-chain/ — never replace existing policies.
yaml — .github/workflows/build.yml (excerpt)
- name: Sign image with Cosign
  uses: sigstore/cosign-installer@v3.4.0  # <-- UPDATE QUARTERLY
  with:
    cosign-release: 'v2.2.3'             # <-- UPDATE QUARTERLY

- name: Verify signed image
  run: |
    cosign verify \
      --certificate-identity-regexp="https://github.com/your-org/.*" \
      --certificate-oidc-issuer="https://token.actions.githubusercontent.com" \
      $IMAGE_REF

.github/workflows/ci.yml (example)
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    uses: ./.github/workflows/_shared/build-push.yml
    with:
      image-name: your-org/your-service
      dockerfile: docker/node/Dockerfile.api

  security:
    needs: build
    uses: ./.github/workflows/_shared/security-scan.yml

  deploy-staging:
    needs: security
    if: github.ref == 'refs/heads/main'
    uses: ./.github/workflows/_shared/deploy-k8s.yml
    with:
      overlay: cd/kubernetes/_overlays/staging

Kubernetes

Kubernetes Deployment Patterns

Base Manifests

Located in cd/kubernetes/_base/. Every base manifest includes:

  • CPU and memory requests and limits — required, not optional
  • readinessProbe and livenessProbe
  • securityContext.runAsNonRoot: true
  • securityContext.readOnlyRootFilesystem: true
  • terminationGracePeriodSeconds set explicitly

Kustomize Overlays

Located in cd/kubernetes/_overlays/. Overlay structure:

directory structure
cd/kubernetes/_overlays/
├── dev/          # replicas: 1, debug logging, no HPA
├── staging/      # replicas: 2, staging ingress, HPA enabled
└── production/   # replicas: 3+, PDB, strict network policies, HPA + KEDA

Helm Charts

Generic service chart at cd/helm/microservice/. Webapp chart at cd/helm/webapp/. Override defaults via values.yaml per environment.

GitOps

Two supported controllers:

  • ArgoCD — cd/gitops/argocd/. Application and AppProject resources. Use syncPolicy.automated with prune: true and selfHeal: true.
  • Flux — cd/gitops/flux/. Kustomization and GitRepository resources. Use retryInterval and healthChecks.

Fleet Management

Multi-cluster topology driven by cd/fleet-overlays/ and ArgoCD fleet ApplicationSets.

⚠
Fleet policies must use Audit mode only. Enforce mode on a workload cluster is a production outage. The cluster registry ConfigMap is human-maintained — never automate writes to it. Scale limit: 20 clusters per fleet ApplicationSet.

Secrets Management

Canonical location: secrets/. Uses External Secrets Operator to sync from AWS Secrets Manager, Azure Key Vault, or GCP Secret Manager into Kubernetes Secrets.

🔒
Never commit secret values to the repository — not even in examples. Use <SECRET-VALUE> placeholders. Secret naming convention: /service-name/environment/secret-name.

refreshInterval guidelines

  • 1h — default for most secrets
  • 15m — high-rotation secrets (API keys, tokens)
  • 24h — stable infrastructure credentials

FinOps — Cost Governance and Optimization

Architecture

Cost data flows: Cloud billing → Kubecost → Prometheus → Grafana dashboards. Infracost runs in CI to estimate IaC cost changes before merge. Optimization scripts query Kubecost API.

data flow
Cloud APIs ──► Kubecost ──► Prometheus ──► Grafana dashboards

Service Catalog

Service Catalog

Git-native service and team registry. No database, no API server — just YAML files validated by Python and enforced by Kyverno.

ℹ
The Backstage migration path is available at catalog/scripts/migrate-to-backstage.py. Only consider it when you reach 50+ services.

Service Schema

catalog/services/example.yaml
apiVersion: catalog.io/v1
kind: Service
metadata:
  name: api-gateway        # must match Deployment app label exactly
  owner: platform-team      # must match a file in catalog/teams/
  display_name: API Gateway
  lifecycle: stable         # alpha | beta | stable
spec:
  contact:
    slack: '#platform-alerts'
    email: platform@example.com
  oncall:
    schedule: https://your-oncall-tool/schedule
  slo:
    definition_file: observability/prometheus/slos/api-gateway-slo.yaml
  runbook_url: https://your-runbooks/api-gateway  # required for stable
  cost_center: platform-001                         # required for stable
  data_classification: internal
  compliance_frameworks: [soc2, iso27001]

Validation

bash
# Validate all entries (CI-equivalent)
python catalog/scripts/validate-catalog.py --strict --skip-url-check

# Validate a single service
python catalog/scripts/validate-catalog.py --service api-gateway --strict

# Make target
make catalog-validate

CODEOWNERS

bash
# Regenerate after any team membership change
python catalog/scripts/generate-codeowners.py --output .github/CODEOWNERS

# Make target
make catalog-codeowners

Backstage Migration

bash
# Convert all catalog entries to Backstage component YAML format
# Use only when you have 50+ services -- see catalog/README.md
python catalog/scripts/migrate-to-backstage.py \
  --catalog-dir catalog/services \
  --output-dir backstage/catalog

Ownership Discovery

bash
# Who owns the api-gateway service?
yq '.metadata.owner' catalog/services/api-gateway.yaml

# What does platform-team own?
grep -r "owner: platform-team" catalog/services/ | awk -F: '{print $1}'

# Find on-call schedule for a service
yq '.spec.oncall.schedule' catalog/services/api-gateway.yaml
