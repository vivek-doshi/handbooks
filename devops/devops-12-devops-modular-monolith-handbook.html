Step 12 · Architect · One deployable, many modules: a lean delivery and operations design

Architecting DevOps for a modular monolith

A modular monolith needs less platform than a fleet of microservices, but it still needs a disciplined delivery system. This step designs it end to end, applying every earlier step with the minimum moving parts that stay safe, observable, and easy to evolve.

Single artifactModule-aware CIZero-downtimeObservabilityEvolution

1. Context and design principles

Assume one deployable application containing several domain modules (see Architecture path step 07), one primary database with module-owned schemas, a handful of teams, and a need for frequent releases. Principles: one repo, one pipeline, one artifact, modular boundaries enforced in code and in CI, and operational complexity added only when a measured problem demands it.

DecisionChoiceWhy
RepositorySingle repo, CODEOWNERS per moduleAtomic changes, simple tooling
BranchingTrunk-based, short branches, feature flagsBest flow; flags decouple deploy from release
ArtifactOne signed container image tagged by commit SHABuild once, promote everywhere
RuntimeManaged container service or a small Kubernetes deploymentMatch operational burden to team size

2. Pipeline design

  1. Fast verify: build, unit tests, and architecture tests that fail on forbidden module dependencies. Use path-based test selection and build caching to keep runs short as the codebase grows.
  2. Integration: module and contract tests against Testcontainers or Compose-provisioned dependencies.
  3. Security: SCA, SAST, secret scan, image scan; generate SBOM and provenance (Step 10).
  4. Package: one multi-stage image, signed with cosign.
  5. Release: promote the identical image to staging, run smoke and end-to-end tests, then production with an approval and automatic verification.
See real snippets in the DevOps Playbook Reusable CI workflows, a multi-stage Dockerfile, and deployment manifests that fit this one-artifact model are available there. Open the DevOps Playbook code template browser to read and copy complete, working files.

3. Deployment strategy

  • Rolling or blue/green on the runtime of choice; add canary when traffic and metrics justify it. Use readiness checks that exercise critical dependencies lightly.
  • Feature flags for incomplete modules and risky behavior; clean flags up on a schedule.
  • Database migrations use expand/contract: additive change first, deploy code that works with both shapes, then remove the old one. Run migrations as a controlled step (job or init), never as an uncoordinated side effect of app start in multi-replica deployments.
  • Keep rollback as "redeploy the previous image"; keep schema changes backwards compatible so it is always possible.

4. Infrastructure, config and secrets

  • Provision with Terraform (Step 09): network, runtime, database with backups and point-in-time recovery, secret store, and registry; separate state per environment.
  • Environment parity: the same image and config shape in all environments; differences only in values.
  • Secrets from a managed store via workload identity; no secrets in images, repos, or pipeline variables where avoidable.
  • If using Kubernetes, adopt GitOps (Argo CD or Flux) with a small config repo; if using a managed container service, use pipeline deploys with environment approvals.

5. Observability tuned for modules

Instrument with OpenTelemetry. Tag every span, metric, and log with a module attribute so you can see per-module latency, error rate, and database time inside one process. Define SLOs for user journeys that cross modules, alert on burn rate, and add per-module dashboards for owning teams. Track DORA metrics for the single pipeline, and add module-level change failure attribution through CODEOWNERS.

6. Scaling and when to evolve

SignalFirst responseConsider extraction when
Hot module saturates CPUScale replicas, optimize, add caching or a read replicaIts scaling profile differs sharply and cost is material

Data couplingEnforce schema ownership, use contractsA module needs an isolated store or compliance boundary

Extract one module at a time behind its contract (strangler pattern), reusing the same pipeline templates; Step 13 shows the target operating model if you grow into many services.
