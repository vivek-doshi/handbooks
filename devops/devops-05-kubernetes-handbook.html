Step 05 · Intermediate · From pods to production workloads, scaling, security, and troubleshooting

Kubernetes core concepts and operations

Kubernetes is the control plane for running containers at scale: you declare desired state and controllers continually reconcile reality to match it. This step teaches the objects and operational habits you need before anything is automated on top.

1. Architecture and the reconcile loop

The control plane (API server, etcd, scheduler, controller manager) stores desired state and decides placement. Nodes run the kubelet, a container runtime (containerd or CRI-O), and kube-proxy or an eBPF dataplane. Every object is a declarative resource: you apply a manifest, and controllers drive the cluster toward it. Docker as a runtime was removed in v1.24; images built with Docker still run unchanged.

Managed services (EKS, AKS, GKE) operate the control plane; you own workloads, upgrades of node pools, and add-ons. Upgrade at least a few times a year because only the three most recent minor versions receive patches.

2. Choosing the right workload object

NeedObject
Stateless service with rolling updatesDeployment (manages ReplicaSets, which manage Pods)
Stable identity and per-replica storageStatefulSet
One pod per node (agents, log shippers)DaemonSet
Run to completion / on a scheduleJob / CronJob

Pods are disposable. Use native sidecar containers (init containers with restartPolicy: Always, GA in 1.33) for proxies and log shippers that must start before and outlive the main container. Organize with Namespaces and labels; enforce quotas with ResourceQuota and LimitRange.

3. Configuration, secrets and resources

  • ConfigMap for non-secret settings; Secret for sensitive values. Secrets are only base64-encoded by default: enable encryption at rest and prefer an external store (External Secrets Operator, Secrets Store CSI Driver) in production.
  • Always set requests (scheduling and the guaranteed share) and sensible limits. Avoid CPU limits that cause throttling unless you need them; always set memory limits.
  • QoS classes (Guaranteed, Burstable, BestEffort) decide eviction order under pressure.

4. Health, rollouts and rollbacks

  • Startup probe protects slow starters, readiness gates traffic, liveness restarts stuck containers. Do not use liveness to check dependencies.
  • Tune maxSurge/maxUnavailable, set minReadySeconds, and add a PodDisruptionBudget so drains and upgrades do not take every replica down.
  • Roll back with kubectl rollout undo, but prefer fixing forward through Git (Step 10).
  • Spread replicas with topologySpreadConstraints across zones and nodes.

Storage uses PersistentVolumeClaims bound through a StorageClass and a CSI driver. Choose the reclaim policy and volume binding mode deliberately, and test backups and snapshot restores.

6. Access control and baseline security

  • RBAC: grant least privilege with namespaced Roles; avoid cluster-admin and wildcards; one ServiceAccount per workload; disable token automount when unneeded.
  • Pod Security Admission enforces the baseline or restricted Pod Security Standards per namespace: non-root, no privilege escalation, dropped capabilities, seccomp RuntimeDefault.
  • Add NetworkPolicies (Step 06), image pull from trusted registries only, and policy-as-code admission (Step 10).

7. A debugging routine

  1. kubectl get pods -o wide and kubectl describe pod — read Events first.
  2. Pending: check requests vs capacity, taints, PVC binding. ImagePullBackOff: registry auth or tag. CrashLoopBackOff: kubectl logs --previous.
  3. Network or DNS: test from a debug pod; check Service endpoints (kubectl get endpointslices).
  4. Use kubectl debug with ephemeral containers on distroless images.
PracticeDeploy a two-replica app with probes, a PDB and resource requests. Break it three ways (bad image tag, failing readiness, memory limit too low) and diagnose each using only get, describe, and logs.
