Step 02 · Beginner · Branching, pull requests, and safe undo for shared repositories

Git for team collaboration

Every DevOps practice starts from a repository. This refresher covers the Git habits that keep a team's history clean and its main branch always releasable.

BranchingPull requestsSafe undoProtected main

1. The daily loop

git switch -c feature/short-name   # branch from an up-to-date main
git add -p                         # stage deliberately
git commit -m "feat: add login"    # small, meaningful commit
git push -u origin HEAD            # publish and open a pull request
git fetch --prune && git rebase origin/main   # stay current

Keep branches short-lived (hours to a couple of days). Long-lived branches are where integration pain and hidden risk accumulate.

2. Choosing a branching model

ModelFitsTrade-off
Trunk-based with short branchesContinuous delivery, most servicesNeeds good tests and feature flags
GitHub flowWeb apps, simple release cadenceOne production line only
Release branchesVersioned products, multiple supported releasesBack-porting overhead

Default to trunk-based: it gives the best delivery metrics and is what later pipeline and GitOps steps assume.

3. Pull requests and protection rules

  • Protect main: require a pull request, required status checks, and at least one review.
  • Use CODEOWNERS so changes reach the right reviewers.
  • Require signed commits or verified tags where provenance matters.
  • Prefer squash or rebase merges for a linear, bisectable history.
  • Use Conventional Commits so changelogs and semantic versions can be automated.

4. Undoing things safely

SituationUse
Discard unstaged editsgit restore file
Undo a published commitgit revert <sha> (adds a new commit)
Find a lost commitgit reflog
Rewrite your own unpublished branchgit rebase -i
Must force push your branchgit push --force-with-lease, never on shared branches
PracticeIn a scratch repo, make three commits, revert the middle one, then recover a deleted branch with git reflog.
