Step 08 · Intermediate · Fast, secure, reusable pipelines from commit to deploy

CI/CD pipelines with GitHub Actions

A pipeline turns every commit into a verified, releasable artifact. This step uses GitHub Actions as the concrete tool, but the principles (fast feedback, build once, least privilege, traceable releases) apply to GitLab CI, Azure Pipelines, or Jenkins.

1. Anatomy and triggers

A workflow (YAML in .github/workflows) contains jobs that run on runners; jobs contain steps that run commands or reusable actions. Common triggers: push, pull_request, workflow_dispatch, schedule, release, and workflow_call. Use path filters and concurrency groups with cancel-in-progress to avoid wasted runs.

Contexts and expressions (github, env, secrets, needs, matrix) drive conditions; keep logic in scripts you can run locally rather than in long expression chains.

2. A good universal pipeline

  1. Verify: lint, unit tests, type checks, on every pull request, in under ~10 minutes.
  2. Security: dependency scan (SCA), secret scan, SAST (CodeQL), IaC scan.
  3. Build once: create the container image or package, tag with the commit SHA, push to the registry.
  4. Attest: generate an SBOM and provenance, sign the artifact (Step 10).
  5. Deploy: promote the same artifact dev → staging → production with approvals; GitOps for clusters.
  6. Verify in production: smoke tests, SLO checks, automatic rollback.
See real snippets in the DevOps Playbook Complete CI and CD workflows for Node.js, .NET, Docker build and push, GitHub Pages, and release/deploy are available as Actions templates there. Open the DevOps Playbook code template browser to read and copy complete, working files.

3. Speed and reuse

  • Caching: use the built-in caching of setup-* actions and Docker layer caching (cache-from/cache-to with BuildKit).
  • Matrix strategies test across versions and operating systems in parallel; use fail-fast deliberately.
  • Reusable workflows (workflow_call) and composite actions give you one maintained pipeline for many repositories; org-level required workflows or rulesets can enforce them.
  • Runners: GitHub-hosted for convenience; larger runners for heavy builds; self-hosted or Actions Runner Controller on Kubernetes for private networks (ephemeral, isolated runners only).

4. Securing pipelines

  • Set permissions: to read-only at the top and widen per job. The default token should never have write access you do not need.
  • Use OIDC federation to AWS, Azure, or GCP instead of long-lived cloud keys.
  • Pin third-party actions to a full commit SHA, and let Dependabot update them. Prefer verified or first-party actions.
  • Use environments with required reviewers and environment-scoped secrets for production.
  • Never run untrusted pull request code with secrets (pull_request_target pitfalls). Treat script injection from ${{ github.event.* }} inputs as a real attack path.
  • Use artifact attestations and branch protection or rulesets so only reviewed code reaches release workflows.

5. Pipeline as a product

Track the DORA metrics from your pipeline: lead time (commit to production), deployment frequency, change fail rate, and time to recover. Keep a flaky-test budget, monitor queue and run time, and treat a failing main as an urgent defect.

PracticeBuild a workflow that lints, tests, builds an image tagged with the commit SHA, pushes it to GHCR with permissions minimized, and deploys to a staging environment requiring approval.
