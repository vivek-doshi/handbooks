Step 03 · Beginner · Images, containers, Dockerfiles, and what production-grade means

Containers with Docker

Containers package an application with its dependencies so it runs the same on a laptop, in CI, and in production. This refresher covers the model, the habits of good images, and where to see full Dockerfiles.

ImagesDockerfileMulti-stageComposePodman

1. The mental model

  • Image: an immutable, layered filesystem plus metadata, built from a Dockerfile.
  • Container: a running process isolated with namespaces and cgroups; it is not a VM.
  • Registry: where images are stored and pulled (Docker Hub, GHCR, ECR, ACR, Artifact Registry).
  • Volume: storage that outlives the container.
docker build -t app:1.0 .
docker run --rm -p 8080:8080 app:1.0
docker logs -f <container>
docker exec -it <container> sh

2. What a good Dockerfile does

  • Uses a small, pinned base image (digest-pinned for reproducibility; minimal or hardened images reduce CVEs).
  • Uses multi-stage builds: compile in a builder stage, copy only the artifact into a slim runtime stage.
  • Orders layers so dependency installs are cached before source copies.
  • Runs as a non-root user and drops writable paths where possible.
  • Ships a .dockerignore, a HEALTHCHECK or probe, and no secrets (use BuildKit secret mounts).

3. Compose for local multi-service work

Docker Compose describes an app's services, networks, and volumes in one compose.yaml. Use docker compose up --build locally and in integration tests; use depends_on with health conditions rather than sleeps. Compose is for development and small deployments; Kubernetes (Step 05) is the production path for most teams.

4. Habits, pitfalls and alternatives

Anti-patternBetter
latest tagsImmutable version or digest tags
Running as rootUSER non-root, read-only root filesystem
Secrets in ENV or layersRuntime secret injection or BuildKit secret mounts
One giant image with build toolsMulti-stage, minimal runtime image

Podman is a daemonless, rootless-by-default OCI-compatible alternative with a near-identical CLI; both build and run the same images.
