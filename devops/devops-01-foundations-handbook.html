Step 01 · Beginner · A quick refresher on what DevOps is and how the lifecycle fits together

DevOps foundations

DevOps is a way of working that shortens the path from idea to running software while keeping it reliable and secure. This step is a refresher: the vocabulary, the loop, and how the rest of this path builds on it.

CultureLifecycleDORA metricsPath map

1. What DevOps is (and is not)

DevOps joins development and operations responsibilities so one team can build, ship, and run a service. It is a mix of culture (shared ownership), practices (automation, small batches, fast feedback) and tooling. It is not a job title, a toolchain you buy, or a separate team that "does deployments".

  • Shared ownership: the team that writes code carries the pager for it.
  • Automation: anything repeated and error-prone is scripted and versioned.
  • Fast feedback: tests, scans, and telemetry tell you within minutes whether a change is safe.
  • Small batches: frequent, small releases are easier to review, deploy, and roll back.

2. The delivery loop

Think of one continuous loop: plan → code → build → test → release → deploy → operate → observe → learn, then back to plan. Each later step in this path deepens one part of the loop.

3. Measuring delivery performance

DORA's research ties delivery performance to five metrics: change lead time, deployment frequency, change fail rate, failed deployment recovery time, and deployment rework rate. The first two measure throughput; the others measure stability. Track them per service and use them to find bottlenecks, not to rank people.

Rule of thumbIf speed improves while stability drops, you are skipping safety work. If both improve, the practices are working.

4. Principles to carry through the path

  • Everything as code: infrastructure, pipelines, policy, dashboards.
  • Git is the source of truth; changes arrive through reviewed pull requests.
  • Build once, promote the same artifact through environments.
  • Shift security left, but also enforce it at runtime.
  • Observe everything you operate: metrics, logs, traces, and SLOs.
  • Prefer paved roads (a platform) over every team inventing its own tooling.
PracticePick one service you own. Write down its lead time from commit to production, how often it deploys, and the last time a change caused an incident. That is your baseline.
