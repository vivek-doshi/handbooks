Step 12 · Advanced · Design for failure, recover predictably, and prove it with drills

Resilience and disaster recovery

Outages and attacks are certain; surprise is optional. This step turns resilience into engineering: targets, patterns, automation and regular proof.

RTO and RPOPatternsImmutable backupsRecovery as codeComplianceChaos drills

1. Targets and tiers

Define RTO (how long you can be down) and RPO (how much data you can lose) per service from business impact, then group services into tiers.

TierExampleTypical RTO / RPOPattern
0Payments, identityMinutes / near zeroActive-active or hot standby
1Core productUnder 1 hour / minutesWarm standby
2Internal toolsHours / hoursPilot light
3Dev and batchDays / a dayBackup and restore
DependenciesA service is only as recoverable as its slowest dependency, including identity, DNS, secrets and CI/CD. Map and tier those too.

2. Failure domains

  • Instance and process, availability zone, region, whole provider, and your own control plane (accounts, identity, pipelines).
  • Include logical failures: bad deploys, data corruption, deletion and ransomware. Replication copies mistakes; backups with history recover from them.
  • Design static stability: keep data planes working when control planes are impaired.

3. Backups and data protection

  • Follow 3-2-1-1-0: three copies, two media types, one off-site, one immutable or air-gapped, zero restore errors after testing.
  • Use immutability (S3 Object Lock, Azure immutable blob storage, Cloud Storage retention and bucket lock) and a separate account or subscription with restricted access for the backup vault.
  • Cross-region and cross-account copies; encrypt with keys that are not controlled only by the production account.
  • Back up configuration and infrastructure state, identity data, secrets, and Kubernetes state (Velero or provider tools), not only databases.

4. Replication and consistency

NeedApproach
Zero data lossSynchronous replication within a region; multi-region strongly consistent stores such as Spanner or Cosmos DB strong consistency, at latency cost
Low RPOAsynchronous cross-region replicas (Aurora Global, Azure SQL geo-replication, Cloud SQL cross-region replicas)
Object dataCross-region replication with versioning
Traffic failoverHealth-checked DNS or global load balancing; avoid depending on a single control plane to fail over

5. Recovery as code

  • Rebuild the environment from infrastructure as code and GitOps; keep pipelines, state and images available in the recovery region.
  • Runbooks as executable automation with manual approval at critical steps; version them next to the code.
  • Maintain a clean-room recovery environment for ransomware scenarios, with verified-clean backups and independent credentials.
  • Use provider tools (AWS Resilience Hub and Elastic Disaster Recovery, Azure Site Recovery and Backup, Google Backup and DR) where they fit.

6. Incident communications and compliance

  • Define severities, an incident commander role, a communication plan (internal, customers, regulators), and an out-of-band channel that does not depend on the affected systems.
  • Regulations raise the bar: DORA (EU financial entities, in force since January 2025) requires ICT risk management, resilience testing and third-party oversight; NIS2 requires incident reporting and risk measures for essential entities.
  • Document exit and substitution plans for critical cloud providers.

7. Testing and chaos engineering

  • Test restores on a schedule, not only backups. Measure actual RTO and RPO against targets.
  • Run game days and fault injection (AWS Fault Injection Service, Azure Chaos Studio, Chaos Mesh or Litmus on Kubernetes) starting in non-production, then limited production.
  • Practice zone loss, region loss, dependency failure, credential compromise and data corruption.
  • Feed findings into post-incident reviews with tracked actions.

8. Recovering AI systems

  • Version prompts, model identifiers, evaluation sets and guardrail configs in Git.
  • Replicate vector indexes or keep the ingestion pipeline able to rebuild them; test rebuild time.
  • Plan model fallbacks: secondary model, secondary region, or degraded non-AI path, and handle provider quota loss.
  • Back up fine-tuned weights and training data lineage.
PracticePick a tier-1 service. Write its dependency map, set RTO and RPO, schedule a restore test, and record the measured result.
