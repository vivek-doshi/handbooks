Cloud architecture and scaling standards

Before designing a specific system, learn the patterns and standards that apply to all of them. This step is the toolbox that the architecture case studies draw from.

1. Principles: the well-architected pillars

PillarKey question
Operational excellenceCan we deploy, observe and improve safely?
SecurityIs access least-privilege and data protected?

All three providers publish these frameworks. Use them as review checklists and record trade-offs in architecture decision records.

3. Scaling standards

  • Design stateless compute; keep state in managed stores. Scale horizontally with autoscaling on a leading metric (queue depth, requests per target) rather than only CPU.
  • Protect dependencies: timeouts, retries with jitter, circuit breakers, bulkheads, backpressure and load shedding.
  • Cache deliberately (CDN, application, database) with clear invalidation rules.
  • Partition data by access pattern; avoid hot keys; plan read replicas and sharding before you need them.
  • Load test to find limits, and set quotas and capacity reservations ahead of launches.

4. Availability and multi-region

StrategyRTO / RPOCost
Backup and restoreHours / hoursLowest
Pilot lightTens of minutes / minutesLow
Warm standbyMinutes / seconds to minutesMedium
Active-activeNear zero / near zeroHighest; needs conflict handling

Use multiple availability zones by default. Go multi-region only for stated recovery or latency requirements, and remember that data replication and consistency are the hard part.

5. Architecture for AI workloads

  • Treat the model as a dependency behind a gateway: abstraction, routing, caching, rate limits, fallbacks and observability of tokens, latency and cost.
  • Separate the online path (inference, retrieval) from the offline path (ingestion, evaluation, fine-tuning).
  • Plan for GPU scarcity: quotas, reservations, spot with checkpointing, multi-region fallback.
  • Add evaluation and guardrails as first-class components, not afterthoughts.

6. Anti-patterns

Anti-patternInstead
Lift-and-shift foreverRe-platform to managed services where value is clear

Manual console changesEverything as code, drift detection
Unbounded autoscalingBudgets, max limits, quotas
Multi-cloud for its own sakeChoose deliberately; abstract only what you must
Chatty cross-region callsKeep data and compute close
Ignoring egressModel data transfer cost early
PracticePick one reference pattern and write its failure modes: for each component, what happens when it is slow, down or returns wrong data.
