Step 14 · Architect · Three complete systems that use AI components: real-time ML, an embedded copilot, and an agent platform

Cloud architecture by example: data and AI-enabled systems

Here AI is a component of a larger system, not the whole system. Each use case shows the surrounding platform, the AI parts, the controls around them, and how the choices map across the three providers.

Streaming and MLRAG copilotAgent platformAI governance

How these differ from classic systems

  • AI components are probabilistic: design evaluation, guardrails and fallbacks in from the start.
  • Data quality and permissions decide outcomes; retrieval and tools must enforce access.
  • Cost and latency are driven by tokens and model size; budget and measure per request.
  • Operate with new signals: groundedness, drift, tool success, and human override rate.

Use case 3: Real-time analytics with machine learning

A logistics company wants live visibility of vehicles and shipments, anomaly alerts, and ETA predictions. Millions of events arrive per minute from devices and applications.

Requirements

  • End-to-end latency under 5 seconds for alerts; dashboards refresh within 30 seconds
  • Historical analysis and model training on years of data
  • Prediction service with p95 latency under 200 ms
  • Data governance: lineage, access control and PII handling

Architecture flow

  1. Devices and services publish events to a streaming backbone.
  2. A stream processor validates, enriches and windows the events; bad records go to a dead-letter queue.
  3. Hot data lands in a low-latency store for dashboards; all data lands in a lakehouse in open table formats (Iceberg, Delta) for history.
  4. Features are computed once and served from an online store for inference and from the offline store for training.
  5. Training pipelines run on schedule or on drift; approved models are registered and deployed to autoscaled endpoints.
  6. Alerts and predictions flow back through the stream to operations tools; monitoring tracks data quality and model drift.

Where AI fits

  • Anomaly detection and ETA regression models trained on the lakehouse and served online.
  • Generative summaries of incidents and natural-language queries over analytics (text-to-SQL) with read-only, governed access.
  • Monitor drift, data quality and fairness; retrain through the same pipeline.

Security and governance

  • Column- and row-level access control; tokenise or mask PII at ingestion.
  • Catalogue with lineage; separate raw, curated and serving zones with different access.
  • Encrypt streams and storage; private networking between processing and stores.

Reliability and scaling

  • Partition streams for parallelism and size for peak plus headroom; use replay from retained logs to recover.
  • Exactly-once or idempotent writes; watermarking for late events.
  • Serve models from at least two zones; keep a rules-based fallback when the model is unavailable.

Cost levers

  • Tier data (hot, warm, cold); compact small files; prune partitions.
  • Autoscale or use serverless processing; spot for training.
  • Retain raw streams only as long as needed.

Trade-offs and decisions

  • Managed streaming costs more than self-run Kafka but saves operations.
  • Lakehouse with open formats reduces lock-in and lets multiple engines share data.
  • Real-time features raise complexity; compute only the ones that improve decisions.

Use case 4: AI copilot embedded in a business application

A financial services firm adds an assistant to its customer-service application. It answers questions from policies and customer records, drafts replies and can perform limited actions, such as creating a case.

Requirements

  • Answers grounded in approved documents with citations; permission-aware access to customer data
  • p95 response under 6 seconds with streaming; 500 concurrent conversations
  • No sensitive data leaves the approved boundary; full audit trail
  • Safe actions with human approval for anything that changes money or customer state

Architecture flow

  1. The application calls an AI gateway with the user's identity; the gateway applies rate limits, logging, redaction and routing.
  2. An orchestration service retrieves context: hybrid search over indexed documents (with ACLs) and read-only queries to customer systems.
  3. The model generates a response with citations; input and output pass through safety filters and groundedness checks.
  4. Tools (create case, fetch status) are exposed through a controlled tool gateway with scoped credentials; high-risk tools require approval.
  5. Conversations, retrieved sources and tool calls are traced; feedback and evaluation datasets improve the system.

Where AI fits

  • This use case is the AI component: evaluation sets, groundedness metrics and human feedback loops are part of the architecture, not optional extras.
  • Continuously test with adversarial prompts (red teaming) before each release.

Security and governance

  • Retrieval enforces the caller's permissions (security trimming); the model never sees data the user cannot see.
  • Defend against prompt injection, including indirect injection from documents; treat retrieved content as untrusted.
  • Private endpoints, customer-managed keys, regional deployment, no training on prompts; retention policy for logs.
  • Map to NIST AI RMF and applicable regulation; document model and data risks.

Reliability and scaling

  • Autoscale the gateway and orchestrator; provisioned throughput or reserved quota for predictable load.
  • Fallback model or cached answers when the primary model is throttled; graceful 'cannot answer' behaviour.
  • Timeouts and budgets per request to bound latency and cost.

Cost levers

  • Smallest model that passes evaluation; route simple intents to cheaper models; prompt caching for shared context.
  • Limit retrieved chunks and history; summarise long conversations.
  • Track cost per conversation and per resolved case.

Trade-offs and decisions

  • RAG versus fine-tuning: start with RAG; fine-tune for style or narrow tasks after measuring.
  • Managed retrieval is faster to ship; custom pipelines give control over chunking and ranking.
  • Autonomy versus control: begin with draft-only and approval-gated actions, widen only with evidence.

Use case 5: Agentic workflow platform for operations

An operations team wants agents that triage incidents, gather diagnostics from many systems, propose remediations and, after approval, execute runbooks. Multiple teams will build agents on a shared platform.

Requirements

  • Multiple agents with clear roles, shared tools and memory
  • Every tool call authenticated and authorised as the requesting user or a scoped service identity
  • Complete traceability and replay; cost and step limits per run
  • Human-in-the-loop approval for changes in production

Architecture flow

  1. A trigger (alert, ticket, chat) starts a workflow in an agent runtime with a unique run identity.
  2. A planner agent decomposes the task and delegates to specialist agents (diagnostics, knowledge, change) using an agent-to-agent protocol.
  3. Agents reach systems only through a tool gateway exposing MCP or API tools with per-tool scopes and rate limits.
  4. Short-term state lives in the run; long-term memory and knowledge use a governed vector and document store.
  5. Proposed changes are shown to an approver with evidence; approved actions execute through existing change pipelines.
  6. Telemetry captures prompts, tool calls, decisions and cost; evaluations run continuously against recorded scenarios.

Where AI fits

  • Evaluate end-to-end task success, not only model answers; keep scenario suites and regression tests.
  • Record decisions for audit and learning; require approvals for irreversible actions.

Security and governance

  • Least-privilege identity per agent and per tool; short-lived credentials; no shared super-user.
  • Policy checks outside the model (allow lists, limits, change windows); never rely on the prompt for enforcement.
  • Isolate code execution in sandboxes; scan tool descriptions and inputs for injection; version and review tools like code.

Reliability and scaling

  • Idempotent tools, timeouts, step and cost budgets, and loop detection.
  • Durable workflow engine so runs survive restarts and can be resumed or replayed.
  • Kill switch and per-agent circuit breaker; degrade to manual runbooks.

Cost levers

  • Cap tokens and tool calls per run; use small models for routine steps and larger models for planning.
  • Cache stable tool results; schedule non-urgent agents in batch.

Trade-offs and decisions

  • Single powerful agent versus several specialised agents: start simple, split when context or permissions demand.
  • Open protocols (MCP, A2A) reduce lock-in but need governance of external tools.
  • Autonomy level should match risk; measure success and escalation rate.
