FinOps and cost governance

Cloud cost is an engineering metric. FinOps is the operating model that gives teams the data, incentives and tools to manage it without slowing delivery.

FinOps phasesFOCUSCommitmentsKubernetesAI and GPUMaturity

1. The FinOps loop

FinOps works in three repeating phases: Inform (allocate and visualise), Optimize (reduce waste and improve rates), Operate (govern and align on goals). It is a cross-functional practice across engineering, finance and product, guided by the FinOps Foundation framework, which now also covers scopes beyond public cloud such as SaaS and AI.

2. Data foundation: FOCUS and tagging

  • FOCUS (FinOps Open Cost and Usage Specification) normalises billing data across providers; AWS, Azure and Google Cloud can export FOCUS-aligned data, making multi-cloud reporting practical.
  • Standard tags or labels: owner, team, product, environment, cost centre, data classification. Enforce them with policy at creation, not by chasing afterwards.
  • Export billing data to a warehouse, build allocation rules for shared costs, and aim for over 90 percent allocated spend.

Commit to the stable baseline (often 60 to 80 percent of steady usage), keep the variable part on-demand or spot, and review coverage and utilisation monthly.

4. Usage optimisation

  • Rightsize compute and databases using utilisation data; adopt newer generations and Arm instances.
  • Schedule non-production off outside working hours; use autoscaling and scale-to-zero services.
  • Storage: lifecycle tiering, delete orphaned volumes and snapshots, compress and deduplicate.
  • Data transfer: keep traffic in-region, use private endpoints and CDNs, and watch cross-AZ and egress charges.
  • Use provider tools (Cost Explorer and Compute Optimizer, Azure Advisor, Recommender) and automate action.

5. Kubernetes and container allocation

Allocate shared cluster cost by namespace, label and workload using OpenCost or provider add-ons. Set requests that match reality, bin-pack with Karpenter or node autoprovisioning, use spot node pools for tolerant workloads, and charge back idle capacity to the platform team so it is visible.

6. AI and GPU cost governance

  • Unit economics: track cost per request, per user, per document and per successful outcome, not just monthly total.
  • Model choice: the smallest model that passes your evaluation; route easy requests to cheap models; cache prompts and responses; batch offline work.
  • Token control: limit context size, summarise history, cap output, and set per-team quotas and budgets at an AI gateway.
  • GPUs: measure utilisation, share via multi-instance or batching, use spot with checkpointing for training, reserve for steady inference, and right-size accelerators.
  • Hidden costs: vector databases, embedding generation, logging of prompts, evaluation runs, and egress.

7. Showback, chargeback and governance

  • Start with showback (visibility per team), move to chargeback when allocation is trusted.
  • Budgets with alerts at 50, 80 and 100 percent plus anomaly detection routed to the owning team.
  • Include cost in architecture reviews and add pre-deploy estimates (for example Infracost) to pull requests.
  • Define guardrails: approved regions and instance families, quota limits, and expiry on sandboxes.
