Step 13 · Architect · Two end-to-end designs: global e-commerce and multi-tenant SaaS

Cloud architecture by example: classic systems

This book shows how to turn requirements into a cloud architecture, step by step. Each use case lists requirements, a flow, provider-specific service choices, security, reliability, cost and trade-offs, then adds the AI components that enhance the system.

E-commerceMulti-tenant SaaSCross-provider mappingTrade-offs

How to work through a case

  1. Write requirements as measurable targets (availability, latency, scale, compliance, cost).
  2. List constraints and assumptions.
  3. Sketch the request path and the data path separately.
  4. Choose services using the pillars and record decisions with trade-offs.
  5. Add security, reliability and cost explicitly.
  6. Decide where AI adds value and what guardrails it needs.

Use case 1: Global e-commerce platform

A retailer sells in 20 countries with seasonal peaks 10 times normal load. It wants fast pages, reliable checkout, and the ability to ship features daily.

Requirements

  • 99.95 percent availability for browse and checkout; peak of 20,000 requests per second
  • Sub-second page loads worldwide; payment data in PCI scope only where unavoidable
  • Daily deployments by several teams; cost must follow traffic

Architecture flow

  1. Users reach a CDN and WAF at the edge; static and cacheable content is served from cache.
  2. A global load balancer routes to regional stacks of stateless services (catalogue, cart, checkout, orders) on containers across three zones.
  3. Catalogue and sessions use a cache plus a document or key-value store; orders use a relational database with Multi-AZ failover.
  4. Order events go to an event bus or queue so inventory, email, fulfilment and analytics react asynchronously.
  5. Payments are delegated to a PCI-compliant provider; the platform stores tokens only.
  6. Telemetry flows to a central observability stack with SLOs on checkout success and latency.

Where AI fits

  • Personalised recommendations from a managed ML service or a feature store with a ranking model.
  • Semantic search with embeddings and a hybrid index for the catalogue.
  • Product description generation and a support assistant grounded in order and policy data, behind a guardrailed gateway.

Security and governance

  • Separate accounts or subscriptions for production and payments; private subnets and private endpoints for data stores.
  • Tokenised payments to keep card data out of scope; WAF bot and rate rules; secrets in a managed store.
  • Audit logs centralised and immutable; least-privilege workload identities.

Reliability and scaling

  • Three zones per region; multi-region active-active for stateless tiers, with the order database region-primary and cross-region replicas.
  • Autoscale on requests per target and queue depth; pre-scale and raise quotas before sales events; load test beforehand.
  • Idempotent order APIs, retries with jitter, circuit breakers, graceful degradation (for example cached catalogue when search fails).

Cost levers

  • CDN offload and image optimisation; Savings Plans for the baseline and spot for batch and analytics.
  • Right-size databases; use read replicas and caching before bigger instances.
  • Cross-AZ and egress charges tracked per service.

Trade-offs and decisions

  • Containers versus serverless: containers give predictable performance at peak; use functions for event glue.
  • Strong consistency only for stock reservation and payment; eventual consistency elsewhere.
  • Single-provider depth beats multi-cloud here unless regulation or risk demands otherwise.

Use case 2: Multi-tenant SaaS platform

A B2B SaaS product serves thousands of customers with different sizes, some with strict compliance needs. It needs strong tenant isolation, per-tenant metering and fast onboarding.

Requirements

  • Tenant isolation that withstands audit; noisy-neighbour protection
  • Self-service onboarding in minutes; enterprise SSO (SAML, OIDC)
  • Usage-based billing and per-tenant cost visibility
  • Regional data residency for selected customers

Architecture flow

  1. Identity layer authenticates users with tenant-aware tokens; every request carries a tenant context.
  2. An API gateway applies per-tenant rate limits and routes to services in a shared pool; large or regulated tenants can be placed in dedicated cells.
  3. Data uses a chosen isolation model: pooled with row-level security, schema per tenant, or database per tenant.
  4. A control plane service handles onboarding, provisioning (infrastructure as code per tenant when dedicated), configuration and entitlements.
  5. A metering pipeline records usage events to a stream, aggregates them and feeds billing and cost allocation.

Where AI fits

  • Tenant-scoped retrieval: vector indexes and prompts must never mix tenant data; filter by tenant in the index and enforce it in the data layer.
  • Per-tenant AI quotas, usage metering and model choice by plan tier.
  • Bring-your-own-key and data-processing terms for customers who restrict AI use.

Security and governance

  • Tenant ID enforced in the data layer, not only in application code; automated tests that try cross-tenant access.
  • Per-tenant encryption keys for sensitive customers; audit logs filterable by tenant.
  • Separate cells and accounts for regulated tenants; documented compliance mapping (SOC 2, ISO 27001, GDPR).

Reliability and scaling

  • Cell-based architecture: each cell is a full stack serving a subset of tenants, limiting blast radius and enabling gradual rollouts.
  • Per-tenant quotas, concurrency limits and queues to stop noisy neighbours.
  • Backups and restores that can target a single tenant.

Cost levers

  • Pool small tenants to maximise utilisation; dedicated resources priced into enterprise plans.
  • Tag or attribute cost per tenant using metering data to find unprofitable tenants.

Trade-offs and decisions

  • Pooled versus siloed: pooled is cheapest and simplest to operate; siloed is easiest to prove isolation. Many products use a hybrid with tiers.
  • Shared schema complicates migrations; plan expand and contract changes and tenant-by-tenant rollout.
  • Build the control plane early; retrofitting multi-tenancy is expensive.
