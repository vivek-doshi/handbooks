RAG Basics

Retrieval-augmented generation (RAG) fetches relevant knowledge at question time and puts it in the prompt. It is the default way to make a model answer from private, fresh or large data, and the foundation for the advanced strategies in the next step.

BeginnerIngest and queryMinimal RAG

Why RAG exists

ProblemHow RAG helps
Model does not know your private dataRetrieve it at run time
Knowledge changes dailyUpdate the index, not the model
Hallucinated answersAnswer from retrieved evidence and cite it
Per-user permissionsFilter retrieval by the caller's access rights
AuditabilityShow which sources produced the answer
RAG gives knowledge, not behaviourRAG changes what the model knows right now. It does not change tone, output format, reasoning style or domain skill. Fine-tuning changes behaviour. Step 12 turns this distinction into a decision framework.

The two pipelines

INGEST (offline, repeatable)
  sources -> parse -> clean -> chunk -> embed -> index (+ metadata, ACLs)

QUERY (online, per request)
  question -> (rewrite) -> embed -> retrieve top-k -> (rerank)
           -> build prompt with context -> LLM -> answer + citations
  • Parse: extract text and structure from PDF, HTML, Office, tickets, wikis. Parsing quality caps answer quality, especially for tables and scans.
  • Chunk: split into retrievable pieces, usually 200 to 800 tokens with 10 to 15 percent overlap, preferably along headings and paragraphs.
  • Metadata: store source, title, section, date, owner and access groups with each chunk.
  • Retrieve: top-k (often 20 to 50 candidates, narrowed later) by dense, sparse or hybrid search.
  • Generate: prompt with only the best chunks, instruct the model to use them and cite.

A minimal working example

import numpy as np
from sentence_transformers import SentenceTransformer
from openai import OpenAI

emb = SentenceTransformer("BAAI/bge-small-en-v1.5")
llm = OpenAI()

# --- ingest ---
docs = {"policy_1": "Refunds are available within 30 days of purchase with a receipt.",
        "policy_2": "Enterprise plans include 24/7 support with a 1 hour response SLA."}
ids, texts = list(docs), list(docs.values())
vecs = emb.encode(texts, normalize_embeddings=True)

# --- query ---
def answer(question, k=2):
    q = emb.encode([question], normalize_embeddings=True)
    top = np.argsort(-(vecs @ q.T).ravel())[:k]
    ctx = "\n".join(f"[{ids[i]}] {texts[i]}" for i in top)
    msg = [{"role": "system", "content":
            "Answer only from the context and cite ids like [policy_1]. "
            "If the answer is missing, say you do not know."},
           {"role": "user", "content": f"<context>\n{ctx}\n</context>\n\nQuestion: {question}"}]
    r = llm.chat.completions.create(model="MODEL_NAME", messages=msg, temperature=0)
    return r.choices[0].message.content

print(answer("How long do I have to return a purchase?"))

In production replace the NumPy array with a vector database, add metadata filters, and run ingestion as a pipeline with incremental updates and deletes. See the DevOps and data-engineering paths for scheduling and CI.

Chunking basics

StrategyHowWhen
Fixed size with overlapSplit every N tokensQuick baseline, uniform text
Recursive structure-awareSplit on headings, then paragraphs, then sentencesDocuments with structure (the sensible default)
SemanticSplit where embedding similarity dropsNarrative text; test before paying the cost
Parent-childSearch small chunks, return the larger parentPrecise match but wide context (next step)
  • Too small loses context; too large dilutes the embedding and wastes prompt budget.
  • Prepend the document title and section heading to each chunk before embedding.
  • Keep tables and code blocks intact, and evaluate parsing on your hardest documents first.

Evaluate retrieval before generation

Most RAG failures are retrieval failures. Build a small set of 50 to 200 real questions with the document or passage that answers each, then measure the retriever on its own.

MetricQuestion it answers
Recall@kIs a correct chunk in the top k?
MRR or nDCGIs it near the top?
FaithfulnessIs the answer supported by the retrieved context?
Answer relevanceDoes the answer address the question?
Context precisionHow much of the retrieved context was actually useful?

Fix retrieval first (parsing, chunking, hybrid search, reranking), then the prompt. Step 10 covers automated evaluation in depth.

When RAG is the wrong tool

  • The task needs consistent style, format or domain behaviour, which is a fine-tuning or prompting problem.
  • The whole corpus fits comfortably in the prompt and changes rarely: long context with prompt caching may be simpler.
  • The question needs aggregation over structured data (totals, joins): use text-to-SQL or tools, not chunk retrieval.
  • The answer needs multi-hop reasoning across many documents: consider graph or agentic retrieval (step 05).

Practice

Practice
  1. Build the example over 20 pages of your own documentation.
  2. Create 30 test questions and compute recall@3 and a manual faithfulness check.
  3. Change the chunk size from 200 to 800 tokens and compare.
