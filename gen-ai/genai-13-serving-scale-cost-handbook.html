Serving, Scale and Cost

Large to very large scale changes the problem. This step covers how inference actually consumes GPU memory and time, how to size and scale serving, how to operate billion-chunk indexes, and where the real cost savings are.

AdvancedInferenceCapacity and cost

How inference spends time and memory

  • Prefill processes the whole prompt in parallel and is compute-bound; it drives time to first token.
  • Decode generates one token at a time and is memory-bandwidth-bound; it drives tokens per second.
  • KV cache stores keys and values for every token of every active sequence. It is usually what limits concurrency.
KV cache bytes per token = 2 (K and V) * layers * kv_heads * head_dim * bytes_per_value
Example 70B-class model: 80 layers, 8 KV heads (grouped-query attention), head_dim 128, fp16
  = 2 * 80 * 8 * 128 * 2 = 327,680 bytes ~ 0.31 MB per token
  8,000-token sequence ~ 2.5 GB   |   32,000 tokens ~ 10 GB (per active request)

Weights: 70B at FP8 ~ 70 GB; at 4-bit ~ 40 GB
Two 80 GB GPUs (tensor parallel 2), FP8 weights: ~160 - 70 - overhead ~ 75 GB for KV
  -> roughly 30 concurrent 8k-token sequences. Measure with your real traffic mix.

Capacity planning

1. Measure: average and p95 input tokens, output tokens, requests/s at peak, latency SLO.
2. Throughput target (tokens/s) = peak_req_per_s * (avg_output_tokens + prefill_equivalent)
3. Benchmark ONE replica with your real prompt mix and engine settings:
   tokens/s at the SLO (time to first token < 1 s, inter-token < 50 ms, for example).
4. Replicas = ceil(peak_target / per_replica_throughput * headroom 1.3)
5. Add: redundancy across zones (N+1), warm pool for failover, canary capacity.
  • Autoscale on queue depth, KV-cache utilisation and time to first token, not CPU. GPU nodes take minutes to start, so keep a warm buffer and use schedulers such as KEDA or cloud-native autoscalers with pre-pulled images.
  • Reserve or commit for the steady base load; use on-demand or spot for bursts and batch jobs.
  • Separate pools: interactive (low latency), batch (throughput), and fine-tuning or evaluation jobs.
  • Plan quotas early: GPU and provider rate limits are the most common launch blockers.

Gateway, routing and resilience

  • Model gateway (LiteLLM, Portkey, cloud gateways): unified API, per-tenant budgets, rate limiting, retries, fallbacks across providers, and central logging.
  • Routing: by task type, input size, tenant tier or classifier confidence; cascade from a small model to a larger one.
  • Resilience: timeouts, exponential backoff with jitter, circuit breakers, hedged requests for tail latency, multi-region and multi-provider fallback, and graceful degradation.
  • Semantic cache: return stored answers for near-duplicate questions where the answer is not user-specific, with TTLs and invalidation; measure false-hit rate carefully.
  • Rate-limit fairness: per-tenant token budgets so one workload cannot starve the rest.

Practice

Practice
  1. Calculate KV cache per request for your model and the concurrency one GPU can hold.
  2. Benchmark vLLM on a sample of your traffic and record tokens per second at your latency target.
  3. Estimate monthly cost for API versus self-hosted at your volume.
