Step 11 · Intermediate · The building blocks

GenAI Architecture: Components

A production GenAI system is much more than a model call. This step walks through every component in the reference architecture, explains why it exists and when you need it, and shows how systems grow from a single prompt to a platform.

The reference architecture

Common architecture shapes

ShapeComponentsTypical useComplexity
Direct model callGateway, prompt, model, loggingSummarise, rewrite, classifyLow
RAG assistantPlus ingestion, vector store, retrieval, citationsKnowledge base Q&A, supportMedium
Hybrid RAG with rerank and guardrailsPlus hybrid search, reranker, ACLs, eval suiteEnterprise search at scaleMedium to high
Workflow automationOrchestrator with fixed steps, tools, human approvalDocument processing, ticket triageMedium
Agentic systemPlus tools or MCP, memory, verifiers, budgetsResearch, coding, ops automationHigh
GenAI platformShared gateway, registry, eval, guardrails, catalogue for many teamsOrganisation-wide enablementHigh, but amortised
Grow by evidenceStart with the smallest shape that meets the requirement and add a component only when a measured failure demands it. A reranker added because recall@5 was low is architecture; a graph database added because it sounded modern is cost.

Cross-cutting concerns

  • Security: identity propagation to retrieval and tools, secret management, egress control, prompt-injection defences, tenant isolation.
  • Data governance: classification, retention, residency, PII handling, and consent for using data in fine-tuning.
  • Reliability: timeouts, retries with jitter, circuit breakers, multi-provider fallback, graceful degradation (answer without retrieval, switch to a smaller model).
  • Cost: per-tenant budgets, token accounting, model routing, caching.
  • Operations: infrastructure as code, CI for prompts and evals, canary releases. See the DevOps and cloud paths.
