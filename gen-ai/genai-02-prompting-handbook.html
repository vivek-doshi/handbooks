Prompt Engineering

Prompting is the cheapest lever you have, and the first one to try before retrieval or fine-tuning. This step covers the techniques that still matter with modern models, and the habits that keep prompts maintainable.

BeginnerSystem promptsStructured output

Anatomy of a prompt

Chat models take a list of messages with roles. Instruction hierarchy matters: system or developer messages set rules; user messages carry the task; assistant messages are prior model turns; tool messages carry tool results.

PartPurposeExample
Role and goalWho the model is and what success looks likeYou are a support analyst. Summarise tickets for engineers.
ContextFacts the model needs (retrieved documents, user profile)Ticket text, policy excerpts
TaskThe specific actionClassify severity and list next steps
ConstraintsRules, tone, length, what to refuseMax 5 bullets; never promise refunds
Output formatExact shape of the answerJSON matching a schema
ExamplesFew-shot input and output pairsTwo labelled tickets

Principles that hold across models

  • Be specific. State the audience, the format, the length and what to do when information is missing.
  • Separate instructions from data. Wrap untrusted or long content in delimiters such as XML tags or triple quotes and tell the model it is data, not instructions.
  • Show, do not just tell. Two to five good examples beat a paragraph of rules for format and tone.
  • Give an exit. Say “answer only from the context; if it is not there, say you do not know”. This is the cheapest anti-hallucination rule.
  • Put long documents first and the question last, and repeat key constraints at the end for long prompts.
  • Iterate with tests, not vibes. Change one thing at a time and compare on a fixed set of examples.
SYSTEM = """You are a support analyst for Acme.
Answer ONLY from the <context> block. If the answer is not there, reply exactly:
"I don't have that information."
Cite sources as [doc_id]. Keep answers under 120 words."""

user = f"""<context>
{retrieved_text}

Zero-shot, few-shot and chain of thought

TechniqueWhat it isUse when
Zero-shotInstruction only, no examplesSimple tasks, strong models
Few-shotAdd labelled examples in the promptFixed output formats, niche labels, tone matching
Chain of thoughtAsk the model to reason step by step before answeringMulti-step logic with non-reasoning models
Self-consistencySample several answers and take the majorityHigh-stakes reasoning where cost allows
Decomposition and prompt chainingSplit a task into steps, one prompt per step, validating between themComplex workflows; easier to test and debug
Step-back and plan-then-actAsk for the general principle or a plan firstAmbiguous or planning-heavy tasks
Reasoning models change the adviceDedicated reasoning models already think internally. Give them the goal, constraints and acceptance criteria, and do not force “think step by step” or micro-manage the reasoning. Use the reasoning-effort setting to trade accuracy against cost.

Structured outputs

Free text is hard to integrate. Modern APIs can constrain output to a JSON schema (structured outputs, function-calling schemas, or grammar-constrained decoding in vLLM and llama.cpp), which makes parsing reliable.

from pydantic import BaseModel
from openai import OpenAI

class Ticket(BaseModel):
    severity: str          # "low" | "medium" | "high"
    summary: str
    next_steps: list[str]

client = OpenAI()
resp = client.chat.completions.parse(
    model="MODEL_NAME",
    messages=[{"role": "user", "content": "Triage: checkout page returns 500 for all EU users."}],
    response_format=Ticket,
)
ticket = resp.choices[0].message.parsed   # typed object, validated against the schema

Still validate semantically: a schema guarantees shape, not truth. Retry with the validation error on failure, and cap retries.

Prompt injection in one page

If the model reads untrusted text (web pages, emails, documents, tool output), an attacker can hide instructions in it. There is no perfect filter, so defend in layers:

  • Mark untrusted content as data and never place it in the system role.
  • Give the model the minimum tools and permissions; require human approval for irreversible actions.
  • Validate and constrain outputs, and never execute model output as code or SQL without a sandbox or allow-list.
  • Log and test with adversarial prompts (step 10 covers guardrails and red teaming).

Managing prompts like code

  • Store prompts in version control or a prompt registry, with a version id logged on every call.
  • Keep a golden set of 30 to 200 representative inputs with expected outputs or rubrics, and run it on every prompt or model change.
  • Template variables explicitly; avoid string concatenation scattered through the code.
  • Pin the model version in production, and re-run the golden set before upgrading.
  • Common mistakes: vague goals, contradictory rules, huge copy-pasted contexts, no failure path, and tuning on three examples.

Practice

Practice
  1. Write a classifier prompt for support tickets, first zero-shot, then with three examples, and compare accuracy on 20 samples.
  2. Add a Pydantic schema and make the output parse every time.
  3. Try a prompt injection hidden in a document and then harden the prompt and tool permissions.
