Tools, Agents and MCP

Language models become systems when they can call tools. This step covers tool calling, the common workflow and agent patterns, MCP as the standard connector, and the engineering discipline (loops, budgets, verifiers) that keeps agents reliable.

IntermediateFunction callingMCP and loops

Tool and function calling

You describe tools with a name, description and JSON schema. The model replies with a structured request to call one; your code executes it and returns the result; the model continues. The model never runs anything itself.

import json
from openai import OpenAI
client = OpenAI()

tools = [{"type": "function", "function": {
    "name": "get_order_status",
    "description": "Look up the status of a customer order by id.",
    "parameters": {"type": "object",
                   "properties": {"order_id": {"type": "string"}},
                   "required": ["order_id"], "additionalProperties": False}}}]

def get_order_status(order_id): return {"order_id": order_id, "status": "shipped"}

messages = [{"role": "user", "content": "Where is order A-1042?"}]
for _ in range(5):                                       # hard step budget
    r = client.chat.completions.create(model="MODEL_NAME", messages=messages, tools=tools)
    msg = r.choices[0].message
    if not msg.tool_calls:
        print(msg.content); break
    messages.append(msg)
    for call in msg.tool_calls:
        args = json.loads(call.function.arguments)
        result = get_order_status(**args)                # validate args, check permissions here
        messages.append({"role": "tool", "tool_call_id": call.id, "content": json.dumps(result)})
  • Write tool descriptions like documentation for a new colleague: when to use it, inputs, side effects.
  • Keep tools few, focused and non-overlapping. Fifty similar tools confuse the model.
  • Return concise, structured results with clear error messages the model can act on.
  • Enforce authorisation in the tool, using the end user's identity. Never rely on the prompt to restrict access.

Workflows versus agents

A workflow follows code-defined paths; an agent lets the model decide the next step in a loop. Start with the simplest design that works, because autonomy costs latency, money and predictability.

PatternHow it worksUse when
Single call with toolsOne prompt, optional tool callsMost assistants and Q&A
Prompt chainingFixed sequence, output of one step feeds the next, with checks betweenTasks that decompose cleanly (draft, critique, finalise)
RoutingClassify the input, send to a specialised prompt, model or toolMixed request types; cost control by sending easy requests to small models
ParallelisationRun independent sub-tasks or votes simultaneously, then mergeSpeed or confidence (multi-document analysis, guardrail checks)
Orchestrator and workersA planner delegates dynamic sub-tasks to worker agentsUnpredictable decomposition (research, code changes across files)
Evaluator and optimiserOne model generates, another critiques, iterateClear quality criteria (translation, code with tests)
Autonomous agent loopModel plans, acts, observes until done or budget hitOpen-ended problems with a verifiable outcome

The agent loop, engineered

while not done and steps < MAX_STEPS and cost < MAX_COST:
    context = build_context(goal, memory, recent_observations)   # step 06
    action  = model(context)                                     # tool call or final answer
    result  = execute(action)           # sandboxed, least privilege, logged
    verify(result)                      # tests, schema, policy check, second model
    update(memory, result)
    done = stop_condition(result)
BlockPurposePractical rule
TriggerWhat starts the run: user, schedule, event, webhookMake runs idempotent so retries are safe
ContextWhat the model sees each stepCompact state, not full transcripts
ToolsActions the agent may takeRead-only by default; approval for writes
VerifierObjective checks on progressPrefer programmatic checks (tests, linters, schema) over self-assessment
Stop conditions and budgetsMax steps, tokens, cost, wall time, repeated-error detectionAlways set all of them
Memory and skillsPersisted notes and reusable proceduresWrite progress to files or a store so runs can resume
Loop engineeringReliable agents come from the loop around the model, not from a cleverer prompt. Deterministic verifiers, small action spaces, checkpoints and clear exits turn an unpredictable generator into a controllable process.

Model Context Protocol (MCP)

MCP is an open protocol that standardises how AI applications connect to tools and data. Instead of writing a custom integration per app and per service (an N times M problem), a service exposes one MCP server and any MCP-capable client can use it.

PieceRole
HostThe AI application (an IDE, a chat app, your agent) that manages connections and user consent
ClientA connector inside the host that talks to exactly one server
ServerExposes capabilities: tools (actions), resources (readable data), prompts (templates)
Transportsstdio for local processes; Streamable HTTP for remote servers (with OAuth-based authorisation)
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("orders")

@mcp.tool()
def get_order(order_id: str) -> dict:
    """Return status and line items for an order."""
    return {"order_id": order_id, "status": "shipped"}

@mcp.resource("policy://returns")
def returns_policy() -> str:
    return "Returns accepted within 30 days."

if __name__ == "__main__":
    mcp.run()          # stdio by default; use a streamable HTTP transport for remote servers
  • Enterprise pattern: publish internal MCP servers behind an API gateway with authentication, per-tool authorisation, rate limits and audit logs, and keep a registry of approved servers.
  • Security: treat tool descriptions and results as untrusted input (tool poisoning and indirect injection are real); pin and review servers; avoid broad credentials; require user confirmation for sensitive actions.
  • MCP versus plain function calling: function calling is how a model asks for a tool in one application; MCP is how tools are packaged and discovered across applications.
  • Agent-to-agent: complementary protocols such as A2A address agents discovering and delegating to other agents across vendors.

Multi-agent systems

DesignDescriptionCaution
Supervisor and workersOne agent routes to specialistsSupervisor becomes a bottleneck; keep roles narrow
Hand-offsControl moves between agents (triage to billing to support)Pass state explicitly; avoid ping-pong loops
Parallel researchersMany sub-agents explore in parallel and report backLarge token cost; cap fan-out
Debate or criticAgents challenge each other's outputDiminishing returns; verify with tools, not opinion

Multi-agent systems cost multiples of single-agent token usage and are harder to debug. Use them when sub-tasks are truly parallel or need isolated context, not as a default.

Frameworks save boilerplate but hide behaviour. Understand the raw loop above first, and keep the ability to inspect every prompt and tool call.

Failure modes and defences

FailureDefence
Infinite or wandering loopsStep, token and time budgets; repeated-action detection
Wrong tool or bad argumentsClear schemas, argument validation, fewer tools, few-shot examples
Compounding errors over many stepsVerifiers after steps, checkpoints, shorter chains
Excessive permissionsLeast privilege, scoped tokens, human approval for irreversible actions
Indirect prompt injection via tool outputTreat results as data, isolate untrusted content, output checks
Cost surprisesPer-run budgets, model routing, caching, alerts
Hard-to-reproduce bugsFull traces, deterministic seeds where possible, replay tools (step 10)
