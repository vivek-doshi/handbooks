LLM Foundations

Everything in generative AI sits on one idea: a model that predicts the next token. This step builds the vocabulary you need for every later step, so the architecture choices later feel obvious rather than magical.

BeginnerTokens and contextFirst API call

What an LLM is

A large language model (LLM) is a neural network, almost always a decoder-only transformer, trained to predict the next token given the tokens before it. Generating text is just repeating that step: predict a token, append it, predict again. Everything else (chat, code, reasoning, tool use) is behaviour layered on that loop.

Training stageWhat happensResult
PretrainingNext-token prediction over trillions of tokens of web, books, code and licensed dataA base model that continues text but does not follow instructions
Supervised fine-tuning (SFT)Train on curated instruction and answer pairsAn instruction-following model
Preference and RL tuningRLHF, DPO and reinforcement learning with verifiable rewardsHelpful, safer, and (for reasoning models) better at multi-step problems
Reasoning trainingRL teaches the model to produce long hidden chains of thought before answeringReasoning models that trade latency and cost for accuracy
Why this matters for architectureKnowledge is frozen at pretraining time, behaviour is shaped by fine-tuning, and everything else you add (retrieval, tools, guardrails) happens around the model at run time. Most of this handbook is about choosing which of those levers to pull.

Tokens, cost and the context window

Models do not read words; they read tokens, sub-word pieces produced by a tokenizer such as byte-pair encoding. In English one token is roughly 4 characters or 0.75 words; code, numbers and non-English text use more tokens per word. You pay per token (input and output are priced separately, output costs more) and latency grows with output tokens.

import tiktoken
enc = tiktoken.get_encoding("o200k_base")
text = "Retrieval-augmented generation reduces hallucinations."
ids = enc.encode(text)
print(len(ids), ids[:5])       # token count drives cost and latency
print(enc.decode(ids))

The context window is the maximum number of tokens (prompt plus output) the model can attend to in one request. Frontier models now advertise hundreds of thousands to millions of tokens, but three rules still hold:

  • Quality degrades before the limit: models retrieve facts from the start and end of a long prompt better than from the middle (the “lost in the middle” effect).
  • Cost and time-to-first-token grow with prompt length, so stuffing everything in is rarely free.
  • The window is per request. The model has no memory between calls unless your application resends the history.

Controlling the output

After each step the model produces a probability distribution over the vocabulary. Sampling settings decide how the next token is chosen.

SettingEffectTypical use
temperature0 is near-deterministic; higher flattens the distribution and adds variety0 to 0.3 for extraction and code, 0.7 to 1 for brainstorming
top_pSample only from the smallest set of tokens whose probability sums to pLeave at default; tune temperature or top_p, not both
max_tokensHard cap on output lengthAlways set, to bound cost and runaway output
stopStrings that end generationCut off at a delimiter
Reasoning effortHow long a reasoning model thinks (low, medium, high)Raise for hard problems, lower for latency and cost

Even at temperature 0, outputs are not guaranteed identical across runs or provider versions. Design for tolerance: validate outputs, pin model versions, and keep regression tests (step 10).

Your first API call

Most providers, and self-hosted servers such as vLLM, Ollama and llama.cpp, expose an OpenAI-compatible chat endpoint, so the same client code works across them. Only the base URL, key and model name change.

from openai import OpenAI

client = OpenAI()  # reads OPENAI_API_KEY; set base_url= for vLLM, Ollama, etc.

resp = client.chat.completions.create(
    model="MODEL_NAME",                 # check your provider's current list
    messages=[
        {"role": "system", "content": "You are a concise technical assistant."},
        {"role": "user", "content": "Explain a context window in two sentences."},
    ],
    temperature=0.2,
    max_tokens=200,
)
print(resp.choices[0].message.content)
print(resp.usage)                       # prompt_tokens, completion_tokens

# Streaming: show tokens as they arrive (better perceived latency)
for chunk in client.chat.completions.create(
        model="MODEL_NAME", stream=True,
        messages=[{"role": "user", "content": "Name three uses of embeddings."}]):
    print(chunk.choices[0].delta.content or "", end="")
Habits to start nowLog token usage on every call, store the model name and prompt version with each response, never hard-code secrets, and set timeouts and retries. These are cheap now and painful to add later.

Practice

Practice
  1. Count tokens for the same paragraph in English, Hindi and Python code and compare.
  2. Call a model at temperature 0 and 1 five times each and note the variation.
  3. Ask a question about an event after the model's cutoff and observe the failure mode. You will fix it in step 04.
