Use Cases 3 and 4: Document Intelligence and Code Intelligence

A batch pipeline where distillation and tiered models drive the economics, and a developer platform where latency, freshness and agentic search over a huge repository set the design.

Advanced600M pages a month5B lines of code

Use case 3: Document intelligence pipeline

ItemRequirement
Volume50 million documents a month (contracts, invoices, claims, forms), averaging 12 pages: about 600 million pages a month; a 2 PB back-archive to process once
OutputStructured JSON per document (parties, dates, amounts, clauses), searchable index, human review for low confidence
AccuracyAt least 98 percent field-level accuracy on key fields; audit trail for every value
LatencyHours, not seconds; throughput and cost per page matter most
ConstraintsSensitive data, region-bound, many layouts and languages, scanned and handwritten input
Reading the scale600 million pages a month is about 230 pages a second sustained. At this volume, a frontier vision model on every page is rarely affordable, so the design is a funnel of cheaper models with expensive ones reserved for the hard cases.

UC3 decisions

QuestionDecisionReason
RAG or fine-tuning?Fine-tune and distil. RAG appears only in the search index and optional clause-lookup featuresExtraction is a behavioural task with a fixed schema at huge volume
Model funnelClassifier (tiny) -> layout and OCR -> small tuned extractor -> frontier model for low confidence -> human reviewMost documents are routine
How to get training data?Label 20k documents with a frontier model plus human verification; distil into a small multimodal or text modelCheap labels, strong supervision
Output controlJSON schema constrained decoding plus business-rule validation (totals add up, dates valid)Shape and consistency guaranteed
Execution modeAsynchronous queues and provider batch APIs where availableThroughput and discounts

UC3 architecture

Object storage (landing) -> event -> queue (SQS / Pub/Sub / Kafka) -> orchestrator (Temporal / Step Functions)
  1. Classify doc type + language + quality          (small model, ~5 ms)
  2. Layout + OCR / parse                             (document AI or open layout models; GPU or serverless)
  3. Extract fields                                   (tuned small model, JSON-schema constrained)
  4. Validate                                         (rules, cross-field checks, confidence from logprobs + agreement)
  5. Escalate low confidence (about 10-15 percent)    (frontier model with the page image)
  6. Human review queue (about 2-5 percent)           (UI shows source highlights; corrections saved)
  7. Persist: structured store + search index (chunks with provenance) + audit log
 Feedback: corrections -> labelled data -> weekly retrain -> eval gate -> canary
  • Idempotency and retries: each document has a content hash; every step is safe to re-run; poison documents go to a dead-letter queue with the reason.
  • Provenance: keep page and bounding-box references for each extracted value so reviewers and auditors can verify it.
  • Confidence: combine model log probabilities, agreement between two cheap passes, and rule validations. Calibrate thresholds so that auto-accepted fields meet the accuracy target.
  • Back-archive: run a separate low-priority lane on spot or batch capacity; throttle so it never starves live traffic.
Illustrative per-page cost funnel (replace with measured numbers)
  all pages:      OCR/layout ............ $0.0006
  all docs:       tuned extractor ........ $0.0004 per page-equivalent
  12% escalated:  frontier vision ........ $0.012 per page -> $0.0014 amortised
  4% human:       reviewer time .......... $0.15 per document -> $0.0005 per page amortised
  total ~ $0.003 per page -> ~ $1.8M / month at 600M pages
  frontier-only alternative at ~$0.012 per page -> ~$7.2M / month

UC3 evaluation and risks

  • Field-level precision and recall per document type and language; a frozen test set refreshed quarterly; track accuracy by layout vendor.
  • Monitor drift: new templates, new languages and scan quality shifts show up as a falling confidence distribution.
  • Risks: silent layout drift, rare-class documents, over-trust in OCR text, and PII in prompts. Mitigate with drift alerts, per-class thresholds, vision fallbacks, and redaction before any external call.

Use case 4: Code intelligence platform

ItemRequirement
Users20,000 developers
Code100,000 repositories, about 5 billion lines, several languages, monorepos, thousands of commits an hour
FeaturesInline completion, chat over the codebase, agentic changes with tests, automated pull-request review, security fixes
LatencyCompletion under 300 ms; chat first token under 2 s; agents run minutes
ConstraintsSource code must not leave the company boundary unless approved; secrets and licences must be respected

UC4 decisions

CapabilityApproachReason
Inline completionSelf-hosted code model (7B to 15B) fine-tuned for fill-in-the-middle on internal code, speculative decoding, prefix cachingTight latency and huge call volume: roughly 2,000 completions per developer per day is 40 million a day
Chat and Q&A on codeFrontier model plus hybrid code retrieval: trigram or lexical search, symbol graph, embeddingsQuality on reasoning; code needs exact identifiers
Agentic editsAgent with tools (search, read, edit, run tests) in sandboxes; verifiers are tests, linters and type checkersVerifiable outcomes make agents reliable
Retrieval for a huge codebaseAgentic search (grep, symbol lookup, go-to-definition) over a precise index rather than relying on embeddings aloneCode is structured; exact search beats semantic similarity for many queries
FreshnessIncremental indexing per commit with branch overlaysDevelopers expect results from the code they just wrote
Fine-tuningCompletion model and a small PR-review model on internal conventions; not for facts about the codeStyle and conventions are behaviour; the code itself is retrieved

UC4 architecture

IDE / CLI / PR bot -> gateway (SSO, repo permissions) -> router
   Completion path (hot): editor context (prefix + suffix + recent files) -> FIM model (self-hosted, speculative decoding)
   Chat / agent path:    orchestrator -> tools:
        code search (trigram/lexical, e.g. Zoekt style) | symbol index (SCIP/LSIF) | embeddings (functions, docs)
        file read | edit | sandboxed build + test | CI results | issue tracker (MCP servers)
        -> frontier model(s) with budgets, verifiers (tests, lint, type check, security scan)
Indexing: git events -> parse with tree-sitter -> chunk by function/class -> symbols + call graph -> embeddings
   -> per-repo shards, ACLs from repository permissions, branch overlays for open PRs
Safety: secret scanners, licence filters, sandbox with no network by default, human approval to merge
  • Index size: 5 billion lines is on the order of 50 to 100 million functions and classes; at 768 dimensions with quantisation that is tens to hundreds of GB, which is easily sharded. The lexical and symbol indexes matter more than the vector index.
  • Completion capacity: 40 million requests a day is roughly 460 a second on average and 1,500 at peak, with short prompts (a few thousand tokens) and short outputs. Plan a replicated GPU pool of a few dozen cards, regional placement near developers, aggressive prefix caching, and cancellation when the developer keeps typing.
  • Agent cost control: per-task token and time budgets, a limited tool set, test-based verification, and escalation to humans when tests fail repeatedly.
  • Evaluation: completion acceptance rate and persistence of accepted code; for agents, task success on a benchmark built from your own resolved issues (the SWE-bench idea on internal repositories); review precision for PR comments.
  • Risks: insecure or licence-tainted suggestions, secret leakage, prompt injection from comments and issues, over-reliance. Mitigate with scanners, sandboxes, repository-scoped permissions and mandatory review.
