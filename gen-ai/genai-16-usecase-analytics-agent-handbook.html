Use Case 5: Analytics Agent and the Architecture Playbook

The final case is the most agentic: a text-to-SQL analytics assistant over a multi-petabyte lakehouse, where the retrieval target is metadata rather than documents. The step ends with a comparison of all five cases and a reusable architecture playbook.

Advanced10 PB lakehousePlaybook

Use case 5: Natural-language analytics agent

ItemRequirement
Data10 PB lakehouse (Iceberg or Delta), 200,000 tables, about 5 million columns, multiple warehouses and BI tools
Users30,000 business users and analysts asking questions in plain language
OutputCorrect SQL, a result table, a chart and a plain-language explanation with the metric definitions used
ControlsRow and column-level security, masked PII, query cost limits, no writes
AccuracyMetric answers must match certified dashboards; wrong numbers are worse than no number
Where the scale isThe data is huge, but the retrieval corpus is not: table and column descriptions, metric definitions and example queries total a few million small items, which fits one modest vector index. The scale problem is query cost, governance and correctness, not vector search.

UC5 decisions

QuestionDecisionReason
Embed the data?No. Embed metadata only: table and column descriptions, metric definitions, example question-and-SQL pairsRows cannot be retrieved by similarity and would be a security risk
Semantic layerYes: governed metrics, dimensions, join paths and synonyms (dbt semantic layer, LookML, Cube or the platform's native one)Lets the model choose metrics instead of inventing SQL, the largest accuracy gain
Model approachFrontier or strong reasoning model, schema-linked prompts, retrieved similar queries; fine-tune only a small SQL dialect model if volume demandsCorrectness is more important than cost per call; volume is modest
Agent or pipeline?Bounded agent loop: plan, retrieve schema, write SQL, validate, run, inspect, answer; max 6 stepsSelf-repair on errors is valuable; the budget keeps it safe
VerificationStatic validation, EXPLAIN cost estimate, row-limit sampling, comparison with certified metrics, and a result sanity checkProgrammatic verifiers beat self-assessment
SecurityExecute as the end user with row and column policies, read-only role, allow-listed schemasThe model must never gain more access than the user

UC5 architecture

User question -> gateway (SSO) -> intent: metric lookup | ad-hoc analysis | explain | out of scope
  1. Retrieve context: hybrid search over catalog (tables, columns, metrics, glossary, golden queries)
                       + semantic layer lookup (certified metrics first)
  2. Plan + generate query (semantic-layer query if the metric exists, otherwise SQL with retrieved join paths)
  3. Validate: parse, allow-list tables, force partition filters and LIMIT, EXPLAIN -> estimated bytes scanned
        reject if above budget or ask the user to narrow
  4. Execute as the user on an isolated warehouse (workload management, timeout, scan cap)
  5. Inspect result: empty? implausible? compare with certified value; retry up to N times with the error
  6. Answer: table + chart + natural-language summary + SQL + metric definitions + data freshness
 Cache: normalised question + user policy hash -> result (TTL by data freshness)
 Feedback: thumbs, SQL edits by analysts -> new golden queries -> eval set
  • Catalog quality drives accuracy. Invest in column descriptions and metric definitions (LLMs can draft them for owners to approve) before tuning models.
  • Cost guardrails: estimated scan size limit, per-user and per-team budgets, dedicated small warehouses for the agent, and result caching.
  • Ambiguity handling: when several metrics match (“revenue”), ask a clarifying question or show the options rather than guessing.
  • Evaluation: 500 to 1,000 question and answer pairs with verified results; execution accuracy (the result matches, not the SQL text), schema-linking accuracy, refusal quality, cost per answer, and unsafe-query block rate.

Reusable patterns from the five cases

  • Funnel: cheap models first, expensive models for the hard remainder (cases 2, 3 and 4).
  • Verifiers beat opinions: tests, schemas, rules and certified metrics make AI output trustworthy (cases 3, 4 and 5).
  • Identity everywhere: propagate the user's identity to retrieval, tools and databases (cases 1, 4 and 5).
  • Retrieve the right thing: documents, tickets, symbols or metadata, depending on the question (all cases).
  • Close the loop: production corrections become golden sets and training data (all cases).
  • Separate knowledge from behaviour: RAG for facts, fine-tuning for style and skill (cases 1 and 2).
  • Budget everything: tokens, steps, scan bytes, dollars and time.

Production-readiness checklist

RequirementsScale, latency, quality targets and constraints written down; decision ADRs exist
DataSources, ownership, ACLs, retention and licence confirmed; ingestion is incremental and idempotent
RetrievalRecall measured; hybrid and rerank evaluated; ACL filtering tested for leaks
ModelsBaseline, routing and fallback defined; versions pinned; fine-tune only with eval proof
SafetyGuardrails, injection tests, least-privilege tools, human approval for risky actions
