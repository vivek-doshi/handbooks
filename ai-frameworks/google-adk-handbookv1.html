Getting Started — Install & Setup

Google Agent Development Kit (ADK) is an open-source, code-first framework for building, evaluating, and deploying agentic AI applications. ADK supports Python, TypeScript, Go, and Java; this handbook focuses on Python.

ℹ️
Official docs: adk.dev/get-started/python/ — always check here for the latest API changes. ADK 2.0 introduces graph-based workflows and agent teams.

Installation

# Install ADK (requires Python 3.10+)
pip install google-adk

# Optional: install with all extras for full feature set
pip install google-adk[eval]         # evaluation tools
pip install google-adk[litellm]      # LiteLLM multi-provider support

# Create a new agent project scaffold
adk create my_agent

Project Structure

The adk create command scaffolds a minimal but complete agent project:

my_agent/
  agent.py          # root_agent definition — required entry point
  .env              # API keys and environment variables
  __init__.py       # exposes root_agent for the ADK runner

The only required element is a root_agent variable in agent.py. Everything else is optional.

First Agent

Update agent.py with a working agent that uses a tool:

from google.adk.agents import Agent

# Tool: plain Python function — ADK infers schema from type hints + docstring
def get_weather(city: str) -> dict:
    """Returns current weather conditions for a city.

    Args:
        city: The name of the city to get weather for.

    Returns:
        A dict with status, city, and temperature fields.
    """
    # Replace with a real weather API call in production
    return {"status": "success", "city": city, "temp_c": 22}

root_agent = Agent(
    name="weather_agent",
    model="gemini-2.0-flash",
    description="Provides current weather for any city.",
    instruction="You are a weather assistant. Use get_weather to answer questions.",
    tools=[get_weather],
)

Build Your Agent

The primary agent type in ADK is LlmAgent (aliased as Agent). It uses a large language model as its core engine to reason, plan, use tools, and generate responses.

LlmAgent Parameters

name
Required. Unique identifier for the agent. Used in multi-agent delegation and logs.
model
Required. Model string: "gemini-2.0-flash", "gemini-2.5-pro", or any LiteLLM-supported model.
instruction
System prompt defining the agent's persona, scope, and behavioral guardrails. Supports templating with {variable} placeholders bound via instruction_provider.
description
Human-readable summary used by parent orchestrators to decide when to delegate to this agent.
tools
List of callables or BaseTool instances. Functions are auto-wrapped; docstrings drive schema generation.
sub_agents
List of child agents this agent can delegate to. Enables hierarchical multi-agent systems.
generate_content_config
Low-level GenerateContentConfig for temperature, top-p, max tokens, safety settings, etc.
output_schema
Pydantic model or JSON schema for structured output. Forces the LLM to return valid JSON matching the schema.
planner
Enables multi-step planning before tool execution. Use built_in_planner() for Gemini's native planning.
code_executor
Attach a code execution environment (e.g., LocalCodeExecutor) allowing the agent to run Python dynamically.

Writing Effective Instructions

- End every response with: 'Is there anything else I can help with?'

    tools=[search_kb, get_account_info],

Sessions & Memory

ADK separates sessions (short-term per-conversation state) from memory (long-term cross-session recall).

Session State
Scoped to a single conversation run. Access via tool_context.state or callback_context.state inside tools and callbacks. Automatically checkpointed.
Memory Service
Persists facts across sessions. Use InMemoryMemoryService for dev or VertexAiRagMemoryService for production RAG-backed recall.
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.adk.memory import InMemoryMemoryService

runner = Runner(
    agent=root_agent,
    app_name="my_app",
    session_service=InMemorySessionService(),
    memory_service=InMemoryMemoryService(),   # optional
)

# Create a session and run
session = await runner.session_service.create_session(
    app_name="my_app", user_id="user-123"
)
async for event in runner.run_async(
    user_id="user-123",
    session_id=session.id,
    new_message=Content(parts=[Part(text="What is the weather in Tokyo?")]),
):
    if event.is_final_response():
        print(event.content.parts[0].text)

Defining an Agent Team

from google.adk.agents import Agent

# Specialist agents
billing_agent = Agent(
    name="billing_agent",
    model="gemini-2.0-flash",
    description="Handles billing questions, invoices, and subscription changes.",
    instruction="You are a billing specialist. Only answer billing-related questions.",
    tools=[get_invoice, update_subscription, apply_credit],
)

technical_agent = Agent(
    name="technical_agent",
    model="gemini-2.5-pro",  # richer model for complex debugging
    description="Handles technical support, bugs, and integration issues.",
    instruction="You are a technical support engineer. Diagnose and resolve technical issues.",
    tools=[search_kb, run_diagnostics, create_ticket],
)

# Orchestrator — delegates via sub_agents, no direct tools needed
root_agent = Agent(
    name="support_orchestrator",
    model="gemini-2.0-flash",
    description="Routes customer support requests to the right specialist.",
    instruction="""
You are a customer support orchestrator.
Analyse the user's intent and delegate to the appropriate specialist agent.
- Billing questions → billing_agent
- Technical issues  → technical_agent
Never answer domain questions yourself — always delegate.
    """,
    sub_agents=[billing_agent, technical_agent],
)

Context Sharing Between Agents

All agents in a team share the same session state. Sub-agents can read and write state keys to pass results back to the orchestrator.

from google.adk.tools import ToolContext

def fetch_user_profile(user_id: str, tool_context: ToolContext) -> dict:
    """Fetch and cache user profile in session state."""
    profile = call_user_api(user_id)
    # Write to shared session state
    tool_context.state["user_profile"] = profile
    return profile

# In another agent's tool, read state written by a sibling agent:
def personalize_response(tool_context: ToolContext) -> str:
    profile = tool_context.state.get("user_profile", {})
    return f"Hello {profile.get('name', 'there')}!"
💡
Design principle: Give each sub-agent a narrow, well-described description. The orchestrator uses this description — not the agent's name — to decide delegation. Be precise about what each agent does and does not handle.

Inter-Agent Communication Patterns

Hierarchical Delegation
Orchestrator LlmAgent delegates to specialists via sub_agents. The LLM decides which sub-agent to call based on description. Default and most flexible pattern.
A2A Protocol
Agent-to-Agent protocol for cross-service agents. Sub-agents can run in different processes or regions and are discovered via URL endpoints. Uses ADK's A2AClient.
Sequential Pipeline
Use SequentialAgent when each sub-agent must complete before the next starts. Output of each step is available in shared session state.
Parallel Fanout
Use ParallelAgent to run multiple sub-agents concurrently. Results are merged into session state. Ideal for independent data-gathering tasks.

Multi-Tool Agents

A multi-tool agent is an LlmAgent equipped with several tools. The LLM autonomously decides which tools to call, in what order, and how to chain their outputs to fulfil the user's request.

Tool Types Overview

TypeHow to CreateBest For

AgentTool Wrap another Agent as a tool Reusing an existing agent inside another agent
Built-in Tools google_search(), code_execution() Web grounding, running code
MCP Tools MCPToolset.from_server(...) Third-party MCP server integrations
OpenAPI Tools OpenAPIToolset.from_spec(...) Any REST API with an OpenAPI spec

Multi-Tool Agent Example

from google.adk.agents import Agent
from google.adk.tools import google_search, code_execution

def query_database(sql: str) -> dict:
    """Run a read-only SQL query against the analytics database.

    Args:
        sql: A valid SELECT statement.

    Returns:
        A dict with 'rows' (list of row dicts) and 'row_count'.
    """
    results = db.execute(sql).fetchall()
    return {"rows": [dict(r) for r in results], "row_count": len(results)}

def send_email(to: str, subject: str, body: str) -> dict:
    """Send an email via the internal mailer service.

    Args:
        to: Recipient email address.
        subject: Email subject line.
        body: Plain-text email body.

    Returns:
        dict with 'sent' boolean and 'message_id'.
    """
    result = mailer.send(to=to, subject=subject, body=body)
    return {"sent": True, "message_id": result.id}

analyst_agent = Agent(
    name="analyst_agent",
    model="gemini-2.5-pro",
    instruction="""
You are a data analyst. You can query the database, search the web for context,
execute Python for data transformation, and email summaries.
Always validate your SQL is read-only before executing.
    """,
    tools=[
        query_database,

    ],
)

Tool Result Handling

ADK serialises tool return values to JSON and injects them back into the LLM context as tool response parts. Best practices:

  • Return structured dicts, not raw strings — the LLM reasons better over structured data.
  • Always include a status key ("success" or "error") so the LLM can handle failures gracefully.
  • Return only what the LLM needs — large payloads inflate token usage and can confuse reasoning.
  • Use consistent key names across tools to reduce LLM confusion (e.g., always "items" not sometimes "results").
# Good: structured, status-keyed response
def get_order(order_id: str) -> dict:
    """Fetch order details by ID."""
    try:
        order = orders_db.get(order_id)
        if not order:
            return {"status": "error", "message": f"Order {order_id} not found"}
        return {
            "status": "success",
            "order_id": order.id,
            "total": order.total,
            "items": order.items,
            "state": order.state,
        }
    except Exception as e:
        return {"status": "error", "message": str(e)}
💡
Tool count tip: LLMs perform best with 5–10 well-defined tools. Beyond ~15 tools, consider splitting the agent into specialised sub-agents with a routing orchestrator.

Workflow Agents

Workflow agents provide deterministic, LLM-free orchestration. They control the execution order of other agents without using a model for flow decisions — making them predictable, fast, and cheap to run.

SequentialAgent
Runs sub-agents one after another. Each agent receives the session state written by the previous agent. Use for pipelines where order matters.
ParallelAgent
Runs all sub-agents concurrently. Use for independent data-gathering steps where you want to minimise latency.
LoopAgent
Repeats a sub-agent until a termination condition is met (via escalate or a max iteration count). Use for retry loops and validation passes.

SequentialAgent — Pipeline Pattern

from google.adk.agents import SequentialAgent, Agent

# Each step reads from / writes to shared session state
fetch_agent = Agent(
    name="fetch_agent", model="gemini-2.0-flash",
    instruction="Fetch the raw data and store it in state['raw_data'].",
    tools=[fetch_data],
)
clean_agent = Agent(
    name="clean_agent", model="gemini-2.0-flash",
    instruction="Read state['raw_data'], clean it, store in state['clean_data'].",
    tools=[clean_data],
)
report_agent = Agent(
    name="report_agent", model="gemini-2.5-pro",
    instruction="Read state['clean_data'] and write a summary report.",
)

pipeline = SequentialAgent(
    name="data_pipeline",
    sub_agents=[fetch_agent, clean_agent, report_agent],
)

ParallelAgent — Concurrent Fanout

from google.adk.agents import ParallelAgent, Agent

# All three run concurrently — write to distinct state keys
weather_agent = Agent(name="weather_agent", ..., tools=[get_weather])
news_agent    = Agent(name="news_agent",    ..., tools=[get_news])
stocks_agent  = Agent(name="stocks_agent",  ..., tools=[get_stocks])

morning_brief = ParallelAgent(
    name="morning_brief",
    sub_agents=[weather_agent, news_agent, stocks_agent],
)
# After completion, session state has weather/news/stocks — feed to a summary LlmAgent

LoopAgent — Retry / Validation Loop

from google.adk.agents import LoopAgent, Agent

def validate_output(tool_context) -> dict:
    """Check if draft meets quality criteria. Escalate to exit loop."""
    draft = tool_context.state.get("draft", "")
    score = quality_check(draft)
    if score >= 0.9:
        tool_context.actions.escalate = True   # signals loop to stop
    return {"score": score, "passed": score >= 0.9}

writer  = Agent(name="writer",   ..., instruction="Generate/improve the draft in state['draft'].")
checker = Agent(name="checker",  ..., tools=[validate_output])

refinement_loop = LoopAgent(
    name="refinement_loop",
    sub_agents=[writer, checker],
    max_iterations=5,   # hard cap — prevents infinite loops
)
⚠️
Always set max_iterations on LoopAgent. Without it, a bug in the termination condition leads to infinite loops and runaway costs.

Agent Routing

Agent routing controls which agent handles a given request. ADK supports several routing strategies — from fully LLM-driven to deterministic code-based routing.

LLM-Based Routing (Default)

The orchestrator's LLM reads the user input and selects a sub-agent based on each agent's description. No routing code required.

router = Agent(
    name="router",
    model="gemini-2.0-flash",
    instruction="Route the user's request to the most appropriate specialist.",
    sub_agents=[billing_agent, tech_agent, onboarding_agent],
    # ADK uses agent.description to build the routing prompt automatically
)

Custom Router Function

For deterministic or cost-optimised routing, provide a before_agent_callback that returns the target agent name:

from google.adk.agents.callback_context import CallbackContext
from google.adk.agents import Agent
import re

def intent_router(callback_context: CallbackContext):
    """Keyword-based intent classification before LLM routing."""
    user_msg = callback_context.user_content.parts[0].text.lower()

    if re.search(r"invoice|billing|payment|refund", user_msg):
        callback_context.state["intended_agent"] = "billing_agent"
    elif re.search(r"error|crash|bug|integrate", user_msg):
        callback_context.state["intended_agent"] = "tech_agent"
    # Returning None lets the LLM orchestrator handle ambiguous cases

router = Agent(
    name="router",
    model="gemini-2.0-flash",
    before_agent_callback=intent_router,
    instruction="If state['intended_agent'] is set, delegate to that agent.",
    sub_agents=[billing_agent, tech_agent],
)

Model Routing

Route to different models based on task complexity — use a fast cheap model for simple tasks and a powerful model for complex reasoning:

from google.adk.models import ModelRouter

def pick_model(request) -> str:
    # Simple heuristic: long / complex → pro; short / simple → flash
    token_estimate = len(request.messages[-1].content.split())
    if token_estimate > 200 or "analyze" in request.messages[-1].content:
        return "gemini-2.5-pro"
    return "gemini-2.0-flash"

agent = Agent(
    name="smart_router_agent",
    model=ModelRouter(router_fn=pick_model),
    ...
)

Routing Patterns Summary

LLM Routing
Pro: Flexible, handles ambiguous inputs, zero code. Con: Costs tokens per request, non-deterministic.
LlmAgent + sub_agents
Keyword / Rule Routing
Pro: Fast, free, deterministic. Con: Brittle, misses paraphrasing, requires maintenance.
before_agent_callback
Classifier Routing
Pro: Accurate, cheap (small model). Con: Requires training data and a separate ML model deployment.
custom classifier
Fallback Chain
Try primary agent; on error or low-confidence response, re-route to a fallback agent. Implement via after_agent_callback.
after_agent_callback

Structured Output

Force the LLM to return JSON matching a Pydantic schema — disables free-text responses and tool calls:

from pydantic import BaseModel
from google.adk.agents import Agent

class ExtractedOrder(BaseModel):
    order_id: str
    customer_name: str
    total: float
    line_items: list[str]

extractor = Agent(
    name="order_extractor",
    model="gemini-2.0-flash",
    instruction="Extract order details from the provided email text.",
    output_schema=ExtractedOrder,  # response is always valid JSON
)
# Agent response will be a JSON string matching ExtractedOrder schema

Custom Agents

Custom agents are created by subclassing BaseAgent. Use them when you need unique operational logic, specific control flows, or integrations not covered by LlmAgent or the workflow agents.

BaseAgent Contract

from google.adk.agents import BaseAgent
from google.adk.agents.invocation_context import InvocationContext
from google.adk.events import Event
from typing import AsyncGenerator

class MyCustomAgent(BaseAgent):
    """A custom agent with bespoke control flow."""

    # Declare sub-agents and config as class fields (Pydantic model_fields)
    validator: BaseAgent
    executor: BaseAgent
    max_retries: int = 3

    async def _run_async_impl(
        self, ctx: InvocationContext
    ) -> AsyncGenerator[Event, None]:
        """Core execution logic — must yield Event objects."""

        for attempt in range(self.max_retries):
            # Run validation step
            async for event in self.validator.run_async(ctx):
                yield event

            if ctx.session.state.get("validation_passed"):
                # Run execution step
                async for event in self.executor.run_async(ctx):
                    yield event
                return

            ctx.session.state["retry_count"] = attempt + 1

        # Exhausted retries — escalate
        ctx.session.state["failed"] = True

Custom Agent Use Cases

Rules Engine Agent
Deterministic business rule evaluation. Run rules before delegating to LLM; short-circuit to a direct response when rules match. Zero LLM cost for covered cases.
Human-in-the-Loop Agent
Pause execution mid-run and wait for human approval. Implement via ctx.actions.escalate + session resumption with Runner.resume_async().
Guard Agent
Input/output safety guard. Wrap any sub-agent: inspect the incoming message, optionally reject it, run the sub-agent, then inspect/redact the response before returning.
Caching Agent
Semantic cache layer. Hash the user query, check a vector store for near-duplicate prior responses, return cached answer if similarity > threshold. Falls through to LLM on cache miss.

Guard Agent Example

from google.adk.agents import BaseAgent
from google.genai.types import Content, Part

class InputGuardAgent(BaseAgent):
    """Validates inputs before passing to sub_agent."""
    inner_agent: BaseAgent
    forbidden_patterns: list[str] = []

    async def _run_async_impl(self, ctx):
        user_text = ctx.user_content.parts[0].text if ctx.user_content else ""

        for pattern in self.forbidden_patterns:
            if pattern.lower() in user_text.lower():
                yield self._make_final_response(
                    "I'm not able to help with that request."
                )
                return

        # Safe — pass through to inner agent
        async for event in self.inner_agent.run_async(ctx):
            yield event

Custom Tools

Custom tools are Python callables that agents can invoke. ADK auto-generates the tool schema from type annotations and the Google-style docstring. No additional registration boilerplate is needed.

Function Tool (Recommended)

def search_documents(
    query: str,
    collection: str = "general",
    max_results: int = 5,
) -> dict:
    """Search an internal document collection.

    Use this tool to find relevant documents, policies, or knowledge-base
    articles matching a natural-language query.

    Args:
        query: Natural-language search query.
        collection: Document collection to search. One of: 'general',
            'technical', 'legal'. Defaults to 'general'.
        max_results: Maximum number of results to return (1–20).

    Returns:
        dict with:
            status: 'success' or 'error'.
            results: list of dicts, each with 'title', 'url', 'snippet'.
            total_found: int — total matching documents.
    """
    hits = vector_store.search(query, collection=collection, top_k=max_results)
    return {
        "status": "success",
        "results": [{"title": h.title, "url": h.url, "snippet": h.snippet} for h in hits],
        "total_found": hits.total,

Long-Running Tool (Async)

import asyncio

async def run_batch_job(job_id: str, params: dict) -> dict:
    """Submit and await a long-running batch processing job.

    Args:
        job_id: Unique identifier for the batch job.
        params: Job parameters as a dict.

    Returns:
        dict with 'status', 'job_id', and 'result' on completion.
    """
    job = await batch_service.submit(job_id, params)
    for _ in range(30):               # poll up to 30s
        await asyncio.sleep(1)
        status = await batch_service.get_status(job.id)
        if status.done:
            return {"status": "success", "job_id": job.id, "result": status.result}
    return {"status": "timeout", "job_id": job.id}

Tool Best Practices

✅
Write docstrings like user stories. ADK passes your docstring verbatim to the LLM as the tool description. Vague docstrings lead to incorrect tool selection.

Use specific argument types. Prefer Literal["option_a", "option_b"] over bare str for enum-like args — it becomes an enum in the tool schema, drastically reducing LLM errors.

Never raise exceptions from tools. Return an {"status": "error", "message": "..."} dict instead. Unhandled exceptions break the agent run.

Skills for Agents

Agent Skills are reusable, self-contained capability packages that work within AI context-window limits. They differ from raw tools by encapsulating a higher-level behaviour with its own context, prompt fragments, and internal logic.

ℹ️
ADK Skills docs: adk.dev/skills/ — covers both pre-built skills from the Agent Skills registry and building custom skills.

Using a Pre-built Skill

from google.adk.skills import load_skill
from google.adk.agents import Agent

# Load a pre-built skill from the Agent Skills registry
web_research_skill = load_skill("google/web-research")
summariser_skill   = load_skill("google/summarise-document")

agent = Agent(
    name="research_agent",
    model="gemini-2.0-flash",
    tools=[web_research_skill, summariser_skill],
)

Building a Custom Skill

A skill is a Python class that implements the BaseSkill interface, packaging related tools + context instructions together:

from google.adk.skills import BaseSkill
from dataclasses import dataclass

@dataclass
class CRMSkill(BaseSkill):
    """CRM operations skill — search contacts, create deals, update pipeline.

    Optimised to minimise context-window usage by pre-fetching commonly
    needed metadata in a single batch call rather than individual lookups.
    """
    crm_url: str
    api_key: str

    @property
    def name(self) -> str:
        return "crm_skill"

    @property
    def description(self) -> str:
        return (
            "Search CRM contacts, create or update deals, "
            "and manage sales pipeline stages."
        )

    def get_tools(self) -> list:
        return [
            self._search_contacts,
            self._create_deal,
            self._update_stage,
        ]

    def _search_contacts(self, name: str = "", email: str = "") -> dict:
        """Search CRM for contacts by name or email."""
        results = crm_api.search(name=name, email=email, url=self.crm_url)
        return {"status": "success", "contacts": results}

    def _create_deal(self, contact_id: str, title: str, value: float) -> dict:
        """Create a new deal in the CRM pipeline."""
        deal = crm_api.create_deal(contact_id=contact_id, title=title, value=value)
        return {"status": "success", "deal_id": deal.id}

    def _update_stage(self, deal_id: str, stage: str) -> dict:
        """Update the pipeline stage of an existing deal."""
        crm_api.update(deal_id=deal_id, stage=stage)
        return {"status": "success"}

# Use the skill in an agent
crm_skill = CRMSkill(crm_url="https://crm.example.com", api_key="...")
agent = Agent(
    name="sales_agent",
    model="gemini-2.0-flash",
    tools=crm_skill.get_tools(),
)

Context-Efficiency Tips

  • Batch lookups: Skills should fetch all needed context in a single tool call rather than making multiple sequential calls.
  • Return summaries: Return compact summaries of large data sets; include a fetch_details(id) tool for when the LLM needs more.
  • Use state caching: Cache expensive lookups in session state so sibling tools in the same skill don't repeat the same API call.
  • Skill composition: Compose coarse-grained skills from fine-grained tools rather than exposing every low-level function directly to the LLM.

Callbacks

Callbacks hook into the agent execution lifecycle without modifying core logic. They are the primary extension point for logging, guardrails, caching, and side effects.

CallbackWhenCan Modify
before_agent_callbackBefore any agent run startsBlock execution, modify state
after_agent_callbackAfter agent run completesModify/replace final response
before_model_callbackBefore each LLM API callModify prompt, block call, inject cached response
after_model_callbackAfter each LLM API callInspect/modify raw LLM response
before_tool_callbackBefore each tool executionBlock call, modify args, return mock result
after_tool_callbackAfter each tool executionModify tool response, log results
 
from google.adk.agents.callback_context import CallbackContext
from google.adk.models import LlmRequest, LlmResponse
import time

# Example: LLM call logger + latency tracker
def before_model_log(ctx: CallbackContext, request: LlmRequest):
    ctx.state["_llm_start"] = time.time()
    print(f"[LLM] Calling {request.model} | tokens≈{len(str(request.contents))//4}")

def after_model_log(ctx: CallbackContext, response: LlmResponse):
    elapsed = time.time() - ctx.state.pop("_llm_start", time.time())
    print(f"[LLM] Done in {elapsed:.2f}s")

agent = Agent(
    name="monitored_agent",
    model="gemini-2.0-flash",
    before_model_callback=before_model_log,
    after_model_callback=after_model_log,
    ...
)

Deployment

Cloud Run (Recommended for Most Teams)

# Build and push container
gcloud builds submit --tag gcr.io/PROJECT_ID/my-agent

# Deploy to Cloud Run
gcloud run deploy my-agent \
  --image gcr.io/PROJECT_ID/my-agent \
  --region us-central1 \
  --platform managed \
  --allow-unauthenticated \
  --set-env-vars GOOGLE_CLOUD_PROJECT=PROJECT_ID

ADK Agent Runtime (Production Grade)

ADK's managed Agent Runtime provides session persistence, horizontal scaling, and built-in observability:

# Deploy using ADK CLI
adk deploy cloud_run \
  --project PROJECT_ID \
  --region us-central1 \
  --agent_module my_agent \
  --service_name my-agent-service

# Or use the agents-cli for the full managed runtime
agents deploy --source . --name my-agent --region us-central1

Deployment Checklist

  • Set max_llm_calls in RunConfig to prevent runaway agents.
  • Use a production-grade session service (Cloud Spanner, Firestore, or Postgres).
  • Enable LangSmith or Google Cloud Trace for observability from day one.
  • Store all secrets in Secret Manager — never in environment variables in container images.
  • Set up rate limiting and budget alerts in Google Cloud Billing.
  • Write evaluation tests with adk eval before promoting to production.
