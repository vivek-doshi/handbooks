Step 06 · Intermediate · Component-level design

Low-level design: make responsibilities explicit

Low-level design (LLD) transforms system-level architectural choices into clean, maintainable, thread-safe, and testable code structures. The objective is clarity at the component seams—not drawing class diagrams for every trivial line of code.

1. The SOLID Principles in Practice

SOLID principles guide object-oriented design to minimize fragility, tight coupling, and rigidity as business rules evolve.

S - Single Responsibility Principle (SRP)

"A class should have one, and only one, reason to change." Avoid "God Objects" that mix business calculations, database persistence, and presentation formatting.

// VIOLATION: User handles domain logic, persistence, and email formatting
class UserAccount {
  public void calculateDiscount() { /* ... */ }
  public void saveToDatabase() { /* SQL queries ... */ }
  public void sendWelcomeEmail() { /* SMTP client ... */ }
}

// CORRECTION: Decompose into focused single-responsibility classes
class UserDiscountCalculator { public BigDecimal calculate(User u) { /* ... */ } }
class UserRepository { public void save(User u) { /* ... */ } }
class NotificationService { public void sendWelcome(User u) { /* ... */ } }

O - Open/Closed Principle (OCP)

"Software entities should be open for extension, but closed for modification." Introduce new behaviors by adding new classes that implement an existing interface, rather than modifying existing switch statements.

// VIOLATION: Adding a new payment type requires modifying this class
class PaymentProcessor {
  public void process(String type, BigDecimal amount) {
    if (type.equals("CREDIT")) { /* ... */ }
    else if (type.equals("PAYPAL")) { /* ... */ }
    // Adding Crypto requires editing this method!
  }
}

// CORRECTION: Strategy pattern with polymorphic extension
interface PaymentStrategy { void pay(BigDecimal amount); }
class CreditCardPayment implements PaymentStrategy { public void pay(BigDecimal a) { /* ... */ } }
class PayPalPayment implements PaymentStrategy { public void pay(BigDecimal a) { /* ... */ } }
class CryptoPayment implements PaymentStrategy { public void pay(BigDecimal a) { /* ... */ } }

L - Liskov Substitution Principle (LSP)

"Subtypes must be substitutable for their base types without altering program correctness." A subclass must honor all behavioral contracts, preconditions, and postconditions of its parent.

I - Interface Segregation Principle (ISP)

"Clients should not be forced to depend on interfaces they do not use." Break bloated interfaces into small, cohesive, role-specific interfaces (e.g., separate Readable, Writable, and Closeable instead of a monolithic StreamManager).

D - Dependency Inversion Principle (DIP)

"High-level modules should not depend on low-level modules; both should depend on abstractions." Domain business rules must not import concrete database drivers or vendor SDKs.

2. GRASP Principles (General Responsibility Assignment)

While SOLID focuses on class inheritance and interfaces, GRASP provides behavioral guidelines for assigning responsibilities to objects:

GRASP PatternCore PrincipleReal-World Example
Information Expert Assign responsibility to the class that holds the required data. Order calculates total price because it holds the collection of OrderLines.
Creator Class B creates Class A if B contains, aggregates, or records A. ShoppingCart creates CartItem instances.
Controller First non-UI object receiving and coordinating a system operation. CheckoutController coordinates between cart, pricing, and payment without holding domain logic.
Low Coupling Minimize dependencies between classes to increase maintainability. Use events or interfaces instead of concrete references between modules.
High Cohesion Keep class responsibilities closely related and focused. A TaxCalculator only computes tax; it does not format receipts or debit bank accounts.

3. Core Design Patterns

CategoryPatternIntent & Practical System Use CaseWatch Out For
Creational Factory Method Encapsulate complex object instantiation logic (e.g., creating database connection pools based on config). Over-abstraction when a standard new constructor is sufficient.
Creational Builder Construct complex objects step-by-step with immutable state (e.g., HTTP Request or SQL Query builder). Excessive boilerplate for simple data structures with 2–3 fields.
Structural Adapter Translate incompatible third-party interfaces into an internal domain port (e.g., Stripe API adapter). Leaking vendor-specific types through the adapter interface.
Structural Decorator Attach cross-cutting behavior dynamically (e.g., adding caching, logging, or metrics around a Repository). Ordering-dependent decorators causing unpredictable bugs.
Behavioral Strategy Define a family of interchangeable algorithms (e.g., dynamic pricing strategies: Surge, Holiday, Bulk). Proliferation of tiny strategy classes for static algorithms.
Behavioral Observer / Pub-Sub One-to-many dependency notification (e.g., notifying analytics, inventory, and email upon OrderPlaced). Memory leaks from uncollected listener references; unhandled subscriber exceptions.
Behavioral State Machine Model an entity whose behavior changes based on explicit state (e.g., Order: Placed → Paid → Shipped → Delivered). Omitting error, cancellation, and timeout state transitions.

4. Concurrency Design Patterns and Thread Safety

Multi-threaded and asynchronous applications encounter race conditions, deadlocks, and thread pool starvation without deliberate concurrency design:

  • Producer-Consumer Pattern: Decouple task generation from execution using a thread-safe bounded blocking queue (e.g., ArrayBlockingQueue in Java). Prevents slow consumers from blocking fast web servers.
  • Reader-Writer Lock (Shared-Exclusive): Permits multiple concurrent reader threads while granting exclusive access to single writer threads. Ideal for read-heavy caches where writes occur infrequently.
  • Thread Pool Management: Size thread pools according to workload characteristics:
    • CPU-Bound Tasks (Crypto, Compression, Image Processing): Number of threads ≈ Number of CPU Cores (e.g., \(N_{\text{cpu}} + 1\)). Sizing larger causes severe thread context-switching overhead.
    • I/O-Bound Tasks (Database Queries, HTTP calls): Number of threads ≈ \(N_{\text{cpu}} \times \left(1 + \frac{\text{Wait Time}}{\text{Compute Time}}\right)\). Threads sleep while awaiting I/O, allowing higher thread counts.
  • Deadlock Prevention: Always acquire multiple locks in a strict, globally ordered sequence (e.g., always lock Account with smaller ID first: lock(min(idA, idB)); lock(max(idA, idB))).

5. Error Handling and Resilience Patterns

  • Exponential Backoff with Jitter: When retrying failed network calls, double the delay interval after each attempt and add random jitter (e.g., \(T = 2^{\text{attempt}} \times 100\text{ms} + \text{random}(0, 50\text{ms})\)) to prevent retry storms from overwhelming recovering servers.
  • Circuit Breaker State Machine:
    • Closed: Normal operations; requests pass through. Failures are counted.
    • Open: Failure threshold exceeded (e.g., 50% errors over 10s); all calls fail immediately with fallback without hitting the downstream dependency.
    • Half-Open: After a trial sleep window (e.g., 30s), allow a limited probe request through. If it succeeds, reset to Closed; if it fails, return to Open.
  • Bulkhead Pattern: Isolate resource pools (thread pools, connection pools) per downstream service so that an outage in a non-critical analytics service cannot consume all web worker threads and take down core checkout.

6. Database Schema Design and Normalization

Data modeling in LLD dictates performance, integrity, and future extensibility:

  • Normalization Levels:
    • 1NF: Atomic values; no repeating groups or arrays in columns.
    • 2NF: In 1NF and all non-key attributes are fully functionally dependent on the primary key (no partial key dependencies).
    • 3NF: In 2NF and no transitive dependencies (non-key attributes depend strictly on the primary key, nothing else).
  • Strategic Denormalization: In read-heavy production systems, carefully denormalize data (e.g., storing user_name alongside order_id) to eliminate costly multi-table SQL joins, using asynchronous event updates to keep copies consistent.
  • Index Optimization:
    • Composite Indexes: Order columns by highest cardinality and equality filters first, range filters last (Rule: Equality, Sort, Range).
    • Covering Indexes: Include all query columns in the index itself (via INCLUDE clause) to satisfy queries entirely from the B-tree without touching the primary heap table.

7. Worked Low-Level Designs

Case 1: Smart Parking Lot Management

  • Entities: ParkingLot, Floor, Spot (Compact, Large, EV, Handicapped), Vehicle, Ticket, Payment.
  • Allocation Strategy: Separate inventory from allocation logic using a SpotAssignmentStrategy (e.g., Nearest to Entrance, EV Priority).
  • Concurrency Invariant: Prevent race conditions where two vehicles claim the last spot using optimistic concurrency locking: 
    UPDATE parking_spots 
SET is_occupied = true, version = version + 1 
WHERE id = :spotId AND is_occupied = false AND version = :version;

Case 2: Elevator Controller System

  • Entities: ElevatorCar, Floor, InternalButton, ExternalCallButton, Door, Dispatcher.
  • Scheduler Algorithm: Implement the LOOK (SCAN / Elevator) Algorithm: The elevator continues traveling in its current direction (UP), serving all pending internal requests and external UP calls until no higher requests exist, then reverses direction (DOWN).
  • State Machine: Idle, MovingUp, MovingDown, DoorsOpening, DoorsOpen, EmergencyStop. Safety interlocks enforce that doors cannot open while velocity > 0.

8. Practical Exercises

  1. Refactoring to SOLID: Review a monolithic 800-line class in your codebase that performs database queries, JSON parsing, and validation. Refactor it into 3 distinct classes applying Single Responsibility and Dependency Inversion.
  2. Thread-Safe Rate Limiter: Implement an in-memory Token Bucket rate limiter in your language of choice. Ensure it handles concurrent requests from 100 parallel threads safely without memory corruption or race conditions.
  3. Vending Machine LLD: Design an object-oriented Vending Machine handling item selection, money insertion (coins, notes, credit card), dispensing, and change calculation. Model states using the State Design Pattern.
