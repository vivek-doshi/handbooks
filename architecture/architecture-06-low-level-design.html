Step 06 · Intermediate · Component-level design

Low-level design: make responsibilities explicit

Low-level design (LLD) turns a system-level choice into implementable modules, contracts, state transitions, and tests. The objective is clarity at the seams—not a class diagram for every line of code.

SOLIDInterfaces and APIsUMLDesign patterns

1. HLD vs. LLD and when to write one

HLD establishes system responsibilities and cross-system behavior. LLD specifies the internal contracts needed to implement a bounded feature: module responsibilities, data model, validation rules, state transitions, error behavior, and test seams.

Write LLD when multiple engineers must coordinate, a domain invariant is subtle, an interface has compatibility consequences, or concurrency/failure behavior is easy to misunderstand. For routine local changes, code plus tests may be the better documentation.

2. Responsibilities, SOLID, and class design

  • Single responsibility: keep a module focused on one reason to change.
  • Open/closed: extend through a stable seam when variation is real; do not build speculative plugin frameworks.
  • Liskov substitution: implementations must honor the behavioral contract callers rely on.
  • Interface segregation: expose small interfaces aligned to client needs.
  • Dependency inversion: keep policy independent from infrastructure details where the boundary pays for itself.

Prefer composition for assembling behavior. Avoid public mutable state, global service locators, deep inheritance, and classes that own unrelated persistence, transport, and business rules. Name concepts in the business domain rather than naming classes after a framework.

3. APIs, interface contracts, and data models

For each interface, define inputs, outputs, validation, authorization, errors, idempotency, pagination, concurrency, and compatibility. Use explicit error categories and stable client-facing semantics; do not leak implementation stack traces.

For persistence models, identify the aggregate or transaction boundary, invariants, uniqueness constraints, lifecycle, indexes, and migration strategy. Treat wire schemas and database schemas as contracts with readers and writers that may be on different versions during rollout.

  validates: item availability, quantity limits, customer access

  retries: same key returns the original outcome

4. UML and other diagrams in LLD

  • Class diagram: selected types, relationships, and ownership.
  • Sequence diagram: calls, events, and error paths in one use case.
  • State diagram: allowed states and transitions for an entity or workflow.
  • Activity diagram: branching business logic where prose is ambiguous.
  • ER diagram: persisted entities, keys, and relationships.

Use the least formal notation that makes a decision reviewable. Keep diagrams small and update them alongside the relevant contract or code.

6. Worked examples: parking, library, and elevator systems

Parking lot

Model a ticket, vehicle, spot, and payment. Define allocation policy separately from spot inventory. Make ticket close/idempotency and concurrent allocation invariants explicit. Persist the allocation transactionally or use a conditional update to prevent two vehicles claiming one spot.

Library management

Separate catalog search from circulation. A book title is not the same as a physical copy. Model loans with due date, renewal policy, holds, and overdue state. Define who may issue, renew, return, or reserve an item.

Elevator controller

Represent elevators, requests, current direction, and door state. Define safe transitions first; route optimization is secondary. A scheduler assigns requests while the controller enforces safety constraints and reports faults.

7. Create an LLD step by step

  1. Read the HLD and choose one bounded use case.
  2. Write invariants and edge cases before choosing classes.
  3. Identify domain concepts, ownership, and state transitions.
  4. Define API and persistence contracts, including failure and retry semantics.
  5. Draw only diagrams that resolve a real ambiguity.
  6. Map tests to invariants, boundary conditions, and contract compatibility.
  7. Review for security, concurrency, observability, and migration risks.
  8. Update the design when implementation teaches you something new.

Common pitfalls and review checklist

  • Can a new teammate implement the behavior without guessing invariants?
  • Do public interfaces hide internal representation and enforce authorization?
  • Are concurrency, retries, duplicate requests, and partial failures covered?
  • Are tests arranged around observable behavior, not private method layout?
  • Is a pattern or abstraction solving a demonstrated problem?
Practice and interview tipDesign a library checkout flow. First list invariants and edge cases, then define the API and data changes, and only then sketch types. In an interview, state assumptions, compare alternatives, and explain failure handling before optimizing for scale.
