Step 11 · Advanced · Edge and API policy

API gateway patterns

An API gateway is a controlled edge for routing, identity enforcement, traffic policy, and observability. Keep it focused on cross-cutting edge concerns; domain rules belong with the domain owner, and a gateway does not make an unsafe backend safe.

1. Gateway anatomy and product choices

A gateway commonly provides TLS termination, route selection, authentication integration, request limits, protocol translation, traffic shaping, and telemetry. A reverse proxy, API management platform, service mesh ingress, and BFF overlap but solve different operational problems.

Kong Gateway and Google Apigee are examples of products, not architecture patterns. Compare deployment model, control plane, policy lifecycle, plugin/extensions, latency, high availability, developer portal, analytics, data residency, and total operating cost. Keep configuration portable where practical and test the exit path.

2. Rate limiting, throttling, and quotas

Rate limiting bounds request rate, throttling controls behavior under pressure, and quotas enforce a usage allowance over a longer period. Choose the key deliberately: identity, tenant, API key, route, or a combination. A single IP limit is often unfair behind NAT and easy to evade with distributed clients.

  • Token bucket: permits bursts within a refill budget.
  • Leaky bucket / queue: smooths arrivals but may add latency or reject overflow.
  • Fixed window: simple counters, with boundary burst effects.
  • Sliding window: smoother accounting, at greater state/compute cost.

Define behavior when the limiter store is unavailable, how limits synchronize across regions, what clients receive on rejection, and how paid plans are audited. Do not rely on an edge policy as the only resource-protection control.

3. Circuit breakers and failure containment

A circuit breaker can stop repeated calls to a failing dependency, using closed/open/half-open states. Pair it with bounded timeouts, limited retries with jitter, concurrency limits, and fallbacks that preserve correctness. A breaker is not a replacement for capacity management or a service-level objective.

Avoid retries at every layer; stacked retries multiply load. Choose one retry owner, preserve an end-to-end deadline, and do not retry non-idempotent operations unless the request has an idempotency contract.

4. Authentication, mTLS, and zero trust

Use standards-based OIDC/OAuth flows appropriate to the client and current security guidance. Validate issuer, audience, expiry, signature, and scopes/claims; forward identity only through authenticated channels. Apply authorization at the service that owns the resource.

Mutual TLS can establish workload identity between services. Rotate credentials, validate identities, and authorize specific workloads and actions. Zero trust means continuously evaluating identity, device/workload, context, and resource policy—not simply putting a gateway at the network perimeter.

5. Threat protection and policy as code

Validate content type, request size, method, path normalization, schema, and known attack patterns. Protect against credential stuffing, injection, SSRF, broken object-level authorization, and resource exhaustion. Use a WAF as defense in depth, not a substitute for application fixes.

Keep gateway policies version-controlled, peer-reviewed, tested, and promoted through environments. Include policy owners, expiry for exceptions, safe rollback, and auditable changes. Test that misconfiguration fails safely and does not accidentally expose internal routes.

6. AI gateway patterns and LLM-specific risks

An AI gateway may route model-provider requests, centralize credential controls, record usage, apply budgets, select fallbacks, and standardize telemetry. It does not make model output reliable or remove the application's responsibility for safe tool execution.

  • Protect provider keys and tenant data; isolate credentials and enforce least privilege.
  • Apply per-tenant, per-model, and token-aware budgets while accounting for provider-specific tokenization and billing.
  • Defend against prompt injection, data exfiltration, unsafe tool calls, and cross-tenant context leakage.
  • Do not assume prompt inspection can reliably classify intent; combine controls, constrained tools, and human review where risk warrants.
  • Record model/provider version, latency, token usage, outcome, and safety signals without logging sensitive prompt content by default.
  • Evaluate quality and safety before routing traffic to a fallback model; equivalent names do not guarantee equivalent behavior.

Use risk management throughout design, evaluation, deployment, and monitoring. NIST's AI RMF 1.0 remains a voluntary framework and is being updated; check the official NIST page for revision status before referencing a version as current.

7. Observability, selection, and quick reference

Track request rate, rejection reasons, upstream latency/status, saturation, retries, breaker state, and per-tenant usage. Propagate trace context while protecting sensitive headers. Alert on SLO symptoms and policy failures, not only process health.
