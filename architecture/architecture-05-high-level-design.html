Step 05 · Intermediate · System-level design

High-level design: turn requirements into a system

A high-level design (HLD) defines the system boundary, major subsystems, data movement, external integrations, operational behavior, and threat mitigations. It creates an actionable, reviewable contract across engineering, security, and product teams.

1. What an HLD Is—and When to Write One

An HLD is required whenever an architectural initiative crosses multiple team boundaries, introduces a new trust boundary, impacts critical SLOs, or involves choices that are expensive to reverse.

DimensionHigh-Level Design (HLD)Low-Level Design (LLD)
Focus & Scope Subsystem boundaries, service topology, storage choices, external integrations, network protocols. Class models, database schema indexes, algorithm details, method signatures, local transaction boundaries.
Primary Audience Tech Leads, Security Architects, SREs, Product Managers, Staff Engineers. Individual software engineers implementing and reviewing the pull request.
Key Questions Answered "Where does data live? How do systems communicate? What happens when a dependency dies?" "How are objects instantiated? What is the concurrency model? How do we handle edge-case validation?"

2. Capacity Estimation and Back-of-the-Envelope Math

Architecture decisions must be grounded in quantitative estimation. System sizing moves sequentially from Users → Requests → Throughput (QPS) → Storage → Memory / Cache → Bandwidth.

Rules of Thumb and Constants

Constants for Quick Mental Calculations:
  - Seconds in a day: 86,400 ≈ 100,000 (10^5) seconds for fast approximations.
  - 1 Million requests / day ≈ 12 requests / second average.
  - 10 Million requests / day ≈ 115 requests / second average.
  - Peak QPS multiplier: Typically 2x to 5x average QPS (plan for 3x minimum).
  - Storage multipliers: 1 Byte -> 1 KB (10^3) -> 1 MB (10^6) -> 1 GB (10^9) -> 1 TB (10^12) -> 1 PB (10^15).

Worked Example 1: URL Shortener (e.g., TinyURL)

  • Traffic: 100 million new URLs created per month (~3.3M/day ≈ 40 writes/sec average; peak = 120 writes/sec). Read-to-write ratio is 100:1, so read traffic is 4,000 reads/sec (peak = 12,000 reads/sec).
  • Storage: Each URL record stores: short_hash (7 bytes) + original_url (500 bytes) + created_at (8 bytes) + user_id (16 bytes) ≈ 600 bytes. With DB overhead and indexing, estimate 1 KB per record.
    Monthly storage = 100M × 1 KB = 100 GB/month. 5-year storage = 100 GB × 60 = 6 TB (fits easily on modern SSD storage with replication).
  • Cache Sizing (Pareto 80/20 Rule): 20% of URLs generate 80% of read traffic. Cache the top 20% daily read requests: 330M reads/day × 20% × 1 KB = 66 GB RAM (achievable on a single modest Redis instance or small cluster).
  • Network Bandwidth: Write egress: 120 writes/sec × 1 KB = 120 KB/sec. Read egress: 12,000 reads/sec × 1 KB = 12 MB/sec (easily handled by standard 1 Gbps networking).

Worked Example 2: E-Commerce Product Catalog

  • Items: 5 million active products; average JSON payload = 4 KB. Total raw catalog dataset = 20 GB.
  • Traffic: 25,000 catalog page views/second at peak. Direct database queries would saturate relational connection pools.
  • Caching Strategy: Cache complete catalog in a distributed Redis cluster with LRU eviction. Total cluster memory required with 2x safety factor = 20 GB × 2 = 40 GB. 99% cache hit ratio leaves only 250 QPS hitting the primary PostgreSQL database.

3. Service Level Objectives (SLOs), SLIs, and Error Budgets

Agile systems require clear definitions of operational reliability:

  • Service Level Indicator (SLI): A quantifiable metric measured over time (e.g., "HTTP status codes < 500 divided by total requests").
  • Service Level Objective (SLO): The target reliability goal agreed upon by engineering and product (e.g., "99.9% of requests succeed over any rolling 30-day window").
  • Service Level Agreement (SLA): A contractual commitment to customers with financial or legal consequences if breached (typically looser than internal SLOs, e.g., 99.5%).
  • Error Budget: The allowable unreliability (\(100\% - \text{SLO}\)). For a 99.9% SLO, the error budget is 0.1% (allowing ~43 minutes of downtime or failed requests per month). When error budget is exhausted, feature releases are paused to focus entirely on reliability engineering.

5. Threat Modeling Integration: STRIDE

Incorporate security into the HLD from Day 1 using the Microsoft STRIDE methodology:

Threat CategorySecurity PropertyReal-World System VulnerabilityArchitectural Mitigation
S - Spoofing Authenticity Attacker impersonates a legitimate customer or microservice. OAuth 2.0 / OIDC with short-lived JWTs; internal mutual TLS (mTLS) with SPIFFE/SPIRE workload identities.
T - Tampering Integrity Attacker alters payload prices or database records in transit. Strict TLS 1.3 everywhere; cryptographic HMAC signatures; database column encryption with HSM keys.
R - Repudiation Non-repudiation User denies making a high-value money transfer. Immutable, append-only audit log with digital signatures stored in WORM (Write Once Read Many) storage.
I - Info Disclosure Confidentiality Customer PII or credit card numbers leaked in application error logs. Log sanitization and masking pipelines; AES-256 field-level encryption; zero secrets in code repositories.
D - Denial of Service Availability Botnet floods checkout endpoint, exhausting database thread pools. Distributed Cloudflare/AWS Shield DDoS protection; token bucket rate limiting; connection pool circuit breakers.
E - Elevation of Privilege Authorization Regular customer modifies URL parameter to access admin portal. Role-Based (RBAC) and Attribute-Based Access Control (ABAC) enforced at every domain service boundary.

6. Multi-Region Design and Disaster Recovery

Disaster recovery strategies balance Recovery Point Objective (RPO: maximum acceptable data loss in time) and Recovery Time Objective (RTO: maximum acceptable downtime):

DR StrategyRPO TargetRTO TargetInfrastructure CostComplexity
Backup & Restore Hours to 24 Hours 12 to 24 Hours Lowest ($) Simple nightly snapshots to cross-region S3; slow manual rebuild.
Pilot Light Minutes 1 to 2 Hours Low ($$) Database continuously replicates cross-region; compute instances scaled to zero until disaster.
Warm Standby Seconds to Minutes Minutes Moderate ($$$) Full environment running in secondary region at 20% capacity; scaled up on DNS failover.
Active-Active Multi-Region Near Zero (< 1s) Sub-second (Automatic) Very High ($$$$$) Traffic routed dynamically to nearest region; multi-primary databases with CRDT conflict resolution.

7. Traffic Management and Load Balancing

  • L4 vs. L7 Load Balancing: Layer 4 balances raw TCP/UDP packets based on IP and port without inspecting payloads (extreme throughput, low CPU). Layer 7 inspects HTTP/HTTPS headers, paths, and cookies, enabling content-based routing, gRPC multiplexing, and SSL termination.
  • Load Balancing Algorithms:
    • Round Robin / Weighted Round Robin: Distributes requests evenly or proportional to instance capacity.
    • Least Connections: Routes to the instance currently handling the fewest active requests (best for long-running RPCs).
    • Consistent Hashing: Routes identical user sessions or tenant IDs to the same caching node to maximize cache hit rates.
  • Global Traffic Routing: Route traffic across continents using GeoDNS (resolves to closest regional IP) or BGP Anycast (single IP announced globally; internet routers find the shortest network hop).

8. Worked Example: Complete 9-Section E-Commerce HLD

  1. Summary & Scope: Enterprise checkout platform handling 2,000 orders/sec peak with global payment settlement and automated warehouse fulfillment.
  2. Requirements & Non-Goals: Must support 99.99% checkout availability; zero duplicate charges under network partitions. Non-goals: Warehouse physical robot routing algorithms.
  3. System Context: Customers interact via Web/Mobile; external dependencies include Stripe Payment Gateway and DHL Shipping API.
  4. Component Design: Modular Monolith core running Order & Inventory modules; PostgreSQL with Transactional Outbox; Apache Kafka event broker; asynchronous payment workers.
  5. Runtime & Deployment: AWS EKS across 3 Availability Zones; multi-AZ Aurora PostgreSQL with synchronous replication.
  6. Security & Threat Controls: TLS 1.3 everywhere; PCI-DSS Level 1 compliance; credit card tokens handled exclusively by Stripe Elements iframe (zero cardholder data touches internal servers).
  7. Operational Readiness & SLOs: Checkout API p99 latency < 350 ms; automated PagerDuty paging when error budget burn rate exceeds 14.4x over 1 hour.
  8. Tradeoffs Considered: Synchronous payment calls rejected due to third-party timeout cascading; pure microservices rejected due to team size of 8 developers.
  9. Delivery & Rollout: Dark launching with feature flags; canary rollout starting at 1% of production traffic for 48 hours.

9. Architecture Review Checklist

  • Are all business goals translated into quantitative, measurable SLOs and latency budgets?
  • Have capacity requirements for QPS, RAM, disk storage, and network bandwidth been calculated?
  • Is every cross-system network interaction bounded by strict timeouts and circuit breakers?
  • Is data classified (Public, Internal, Confidential, Restricted/PII) with clear retention rules?
  • Are all trust boundaries identified with STRIDE threat mitigations documented?
  • Is there an explicit disaster recovery plan with documented RTO and RPO targets?
  • Are distributed transaction boundaries replaced with reliable transactional outboxes or sagas?
  • Are OpenTelemetry distributed tracing and correlation IDs propagated across every layer?
  • Has a canary rollout and instant rollback strategy been documented?
  • Can the system design survive the total loss of an entire cloud availability zone?

10. Practical Exercises

  1. Capacity Sizing: Design a photo-sharing platform (like Instagram) with 50 million Daily Active Users (DAU). Each user views 20 photos/day and uploads 1 photo/day (average image size = 2 MB). Calculate the daily ingestion storage, total 3-year storage, write QPS, read QPS, and required CDN bandwidth.
  2. Disaster Recovery Strategy: For a critical financial trading platform, evaluate whether a Pilot Light or Active-Active Multi-Region strategy is appropriate given an RPO requirement of < 100 milliseconds. Justify the infrastructure cost implications.
  3. Threat Modeling: Conduct a STRIDE threat model on a public IoT vehicle telemetry ingestion API. Identify 3 critical vulnerabilities and their architectural mitigations.
