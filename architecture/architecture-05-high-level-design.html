Step 05 · Intermediate · System-level design

High-level design: turn requirements into a system

A high-level design (HLD) communicates the system boundary, major components, data movement, external dependencies, and operational behavior. It is a shared model for decisions—not a promise that every implementation detail is already known.

1. What an HLD is—and when to write one

Write or update an HLD when a change crosses teams or systems, introduces a new trust boundary, changes a critical data flow, has significant availability/cost consequences, or is expensive to reverse. Keep it proportional: a small change may need only an ADR and a sequence diagram.

2. Gather requirements and define measurable qualities

Capture goals, actors, use cases, dependencies, data classification, legal constraints, availability targets, recovery expectations, and explicit non-goals. Convert terms like "fast" or "highly available" into scenarios with a workload and measure.

Quality scenarioDuring a 10-minute payment-provider outage, order placement remains available, pending payments are visible, no order is marked paid without confirmation, and recovery is observable within the agreed recovery objective.

Estimate capacity from peak traffic, payload size, retention, read/write mix, fan-out, and growth assumptions. Show the assumptions and ranges. Avoid false precision; load test the design before treating estimates as facts.

3. What to include: a concise HLD template

  1. Summary: goal, scope, owners, status, reviewers, and decision links.
  2. Requirements: use cases, quality scenarios, constraints, and non-goals.
  3. Context: users, external systems, data owners, and trust boundaries.
  4. Design: components, responsibilities, interfaces, persistence, and key flows.
  5. Runtime: deployment, scaling, regions, dependencies, and environment assumptions.
  6. Risk controls: identity, authorization, privacy, threat mitigations, and audit.
  7. Operations: SLOs, telemetry, alerts, failure modes, backup, restore, and support ownership.
  8. Tradeoffs: alternatives, cost model, decisions, open questions, and revisit signals.
  9. Delivery: migration, rollout, rollback, compatibility, and acceptance tests.

4. Diagram types and when to use them

  • System context: scope, users, and external dependencies.
  • Container / deployment view: major applications, datastores, runtime, network, and trust zones.
  • Component view: responsibilities inside one container, when that detail helps.
  • Sequence diagram: time-ordered calls, retries, and error paths.
  • Data-flow diagram: data origins, transformations, storage, classification, and deletion.
  • State diagram: important lifecycle and transition invariants.

Use a consistent legend, name each boundary, show direction and protocol where it matters, and annotate critical assumptions. A diagram that cannot be read without its author is not a useful design artifact.

5. Step by step: create and validate an HLD

  1. Write the problem statement, decision owner, stakeholders, and scope.
  2. Map the current system and the business/data owners involved.
  3. List functional requirements and rank quality scenarios.
  4. Sketch two or more viable options and make constraints visible.
  5. Choose component responsibilities and interface/data ownership.
  6. Walk through normal, peak, degraded, security, and recovery paths.
  7. Estimate cost and capacity; identify unknowns for prototype or test.
  8. Record decisions, migration steps, observability, and accountable owners.
  9. Review with implementation, security, data, platform, and operations peers.
  10. Update the design from implementation and production evidence.

6. Worked example: an e-commerce order flow

Keep the order API responsible for order state. Persist an order and an outbox record in the same database transaction. A publisher delivers the event; payment and fulfillment workflows consume it independently. Each consumer is idempotent and reports progress. A status API exposes pending, paid, rejected, and fulfillment states.

Document what happens if payment times out after the provider accepted it, if an event is delivered twice, if the broker is unavailable, or if the customer retries checkout. Define the authoritative status, reconciliation process, and compensation for a failed workflow.

7. Pitfalls and review checklist

  • Does every component have a responsibility and owner?
  • Are synchronous dependencies and timeout budgets bounded?
  • Are data ownership, consistency, retention, and deletion explicit?
  • Are authentication, authorization, secrets, and trust boundaries shown?
  • Can an operator detect, diagnose, recover, and safely replay work?
  • Are deployment, compatibility, rollback, and migration paths feasible?
  • Are costs, assumptions, and known unknowns visible?

Common HLD failures include technology inventories without behavior, diagrams with unbounded arrows, no failure path, mixing current and target states, and a document that is never revised after implementation.

PracticeProduce one context diagram, one order-flow sequence, and a one-page HLD for a service that accepts orders during a payment outage. Ask a teammate to identify the source of truth and recovery process without your explanation.

Tools and further reading

  • C4 model — context, container, component, and code views.
  • Mermaid — diagrams maintained as text alongside documentation.
  • OpenTelemetry semantic conventions — consistent telemetry attributes.
  • NIST SP 800-207 — zero-trust architecture principles.
