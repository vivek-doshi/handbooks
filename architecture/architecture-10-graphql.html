Step 10 · Advanced · Client-shaped APIs

GraphQL for enterprise systems

GraphQL gives clients a typed schema and lets each operation request a shaped result. It can reduce over-fetching across varied clients, but shifts important responsibilities to schema governance, query cost control, authorization, and resolver performance.

Schema designQueries and mutationsFederationSecurity and performance

1. GraphQL core concepts and current specification

A schema defines object, scalar, enum, interface, union, input, and root operation types. A query reads data, a mutation requests a state change, and a subscription delivers updates through a transport selected by the implementation.

As of October 2026, the official GraphQL specification site lists September 2025 as its latest release and a September 2026 working draft. Pin implementation behavior to a published specification and your server/client versions; do not assume working-draft features are production-stable.

Choose GraphQL whenmany clients need different compositions, a product needs a typed graph over owned data, and the organization can operate schema governance and query protections.

It may be a poor fit for a simple CRUD API with one stable client, large file transfer, public cacheable content with conventional HTTP semantics, or a team unable to monitor resolver/query behavior. REST, gRPC, or server-rendered pages may be simpler.

2. Schema design, queries, and mutations

type Query {
  order(id: ID!): Order
}

type Mutation {
  submitOrder(input: SubmitOrderInput!): SubmitOrderResult!
}

type Order {
  id: ID!
  status: OrderStatus!
  lines(first: Int!, after: String): OrderLineConnection!
}

Design from client-visible domain concepts, not database tables. Use stable IDs, explicit nullability, input objects, enums for closed sets, and connection pagination for large collections. Keep mutations task-oriented and define validation/business errors in a predictable result shape.

ARB pushback, answered

  • "It creates one giant API." Use domain ownership, schema review, and modular resolver code; federation is optional and adds its own coordination.
  • "Clients can request too much." Enforce depth/complexity budgets, pagination, timeouts, and persisted operations where suitable.
  • "It is hard to cache." Use field-aware caching and client operation strategies where they fit; do not assume URL-based HTTP caching works unchanged.
  • "It replaces every API." It need not. Keep REST, events, or gRPC where their contracts better fit the interaction.

3. Subscriptions, BFF, and federation

Subscriptions are long-lived streams; plan for connection authentication, reconnection, backpressure, fan-out, and delivery semantics. Do not promise durable event replay unless the implementation explicitly provides it.

A BFF can expose a GraphQL graph tailored to a product experience and compose data from owned services. Keep business invariants in their source domain and prevent resolver logic from becoming an unbounded integration layer.

Federation composes subgraphs under a supergraph/router. Define entity ownership, shared field rules, composition checks, rollout order, and failure isolation. Federation increases the importance of schema review, query plans, router telemetry, and clear team boundaries; it is not required for every GraphQL deployment.

4. Security and authorization

  • Authenticate requests and authorize at the data/field boundary; hide neither access decisions nor tenant scoping inside client assumptions.
  • Prevent object-level authorization flaws for every resolver returning user-owned data.
  • Bound query depth, complexity, aliases, batch sizes, pagination, and execution time.
  • Limit introspection or schema visibility according to the threat model; schema secrecy is not authorization.
  • Protect mutations against CSRF when cookie-based authentication is used; configure CORS and origin checks carefully.
  • Redact tokens, personal data, and query variables from logs; retain enough identifiers to investigate.

Use OWASP API Security guidance alongside GraphQL-specific controls. A gateway/WAF can enforce edge rules but cannot replace resolver authorization and cost limits.

5. Performance, tooling, and production operations

Nested field resolution can create an N+1 pattern. Use request-scoped batching/data loaders, bounded caches, and query planning. Measure resolver-level latency, downstream calls, error rate, result size, complexity, and saturation. Add deadlines to downstream operations and avoid waiting on long chains of synchronous services.

  • Validate and compose schemas in CI; treat breaking changes as managed migrations.
  • Use operation registries or persisted queries where they improve control and cacheability.
  • Run contract, authorization, query-cost, and compatibility tests.
  • Track field usage before deprecation; announce, migrate, and remove with a published policy.
  • Propagate traces through resolvers and downstream services using supported OpenTelemetry instrumentation.
PracticeDesign an order query for a mobile client with paginated lines. Add tenant authorization, a complexity budget, N+1 prevention, and a backward-compatible field deprecation plan.
