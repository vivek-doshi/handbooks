Step 02 · Beginner · Enterprise context

Enterprise architecture, made practical

Enterprise architecture connects business outcomes to the applications, data, technology, security, and integrations that deliver them. The goal is useful alignment and managed change—not an ivory-tower bureaucracy or a bottleneck that slows product delivery.

Six Domains Capability & Value Stream Mapping Build vs. Buy & TCO Technical Debt Governance ARB Charter & ADRs

1. The Six Architecture Domains

Enterprise architecture structures the holistic enterprise into distinct yet interdependent viewpoints. This six-domain model ensures decisions do not optimize a single technical silo at the expense of enterprise stability or customer value:

DomainCore Question It AnswersPrimary ArtifactsTypical Key Decisions
Business What strategic capabilities, revenue models, and value streams matter? Business capability maps, value stream diagrams, operating model models Core vs. context capability prioritization; customer journey alignment
Application Which systems support those capabilities and where are their operational seams? Application landscape catalog, C4 context & container models, lifecycle status System rationalization; monolith vs. microservice boundaries; legacy retirement
Data & Info What information is authoritative, regulated, retained, and exchanged? Master Data Management (MDM) maps, data classification, lineage graphs, schemas Single source of truth designation; data privacy (GDPR/HIPAA); retention schedules
Technology What runtime platforms, cloud networks, compute, and hardware are required? Deployment topologies, platform standards, cloud landing zones, infrastructure catalogs Multi-cloud vs. single provider; container orchestration; edge deployment topologies
Security How are identities, threat surfaces, regulatory controls, and trust boundaries enforced? Threat models (STRIDE), Zero Trust policies, IAM matrix, compliance mappings (SOC2/ISO) Workload identity federation; perimeter vs. identity controls; encryption standards
Integration How do autonomous systems reliably communicate events, commands, and queries? API catalogs (OpenAPI/GraphQL), event schemas (AsyncAPI), integration patterns Synchronous vs. asynchronous communication; event broker selection; API gateway strategy

Worked Example: Business Capability Mapping

A capability map describes what an enterprise does to deliver value, independent of how or who implements it. Capabilities are organized in a hierarchy (Level 1 to Level 3):

Value Stream Mapping

While capabilities define static organizational assets, value streams depict end-to-end customer journeys. In an Order-to-Cash value stream, the flow traces: Browse Catalog → Authorize Payment → Allocate Inventory → Dispatch Shipment → Issue Invoice → Settle Funds. Architects map applications, data handoffs, and cycle-time latencies across each stage to identify bottlenecks and single points of failure.

2. Selecting Technology: Build, Buy, or Integrate

Never choose tools based on buzzwords or vendor hype. Categorize the initiative according to Wardley Mapping principles: Genesis, Custom-Built, Product/Rental, or Commodity.

  • Build: Invest engineering resources only where the capability represents a proprietary, market-differentiating competitive advantage (e.g., proprietary pricing engine, custom recommendation algorithms).
  • Buy (SaaS / Off-the-Shelf): Adopt proven industry solutions for commodity, standard business functions (e.g., identity providers like Okta, payroll, CRM, tax calculation engines).
  • Integrate: Connect legacy backends and specialized partner ecosystems through standardized integration layers and facade adapters.

Vendor Assessment Checklist (Due Diligence)

  1. Security: Does the vendor provide verified SOC 2 Type II, ISO 27001, and FedRAMP audits?
  2. Data Portability: Can all data be exported in open, non-proprietary formats (Parquet, JSON, CSV) without vendor intervention?
  3. SLA Commitments: Is there a contractual 99.95%+ uptime guarantee with financial penalty credits?
  4. Disaster Recovery: What are the validated Recovery Time Objective (RTO) and Recovery Point Objective (RPO)?
  5. API Quotas: Are there hidden API rate limits or egress bandwidth charges that will constrain growth?

3. Technology Radar and Standards Lifecycle

A Technology Radar prevents chaotic tech proliferation ("resume-driven development") while encouraging systematic innovation. Technologies, frameworks, and tools are categorized across four rings:

RingStrategic IntentAdoption GuidanceExample Candidates
Adopt The recommended default for enterprise production systems. High confidence, mature tooling, shared company skills. Use without special review; standard support patterns provided by platform team. PostgreSQL, OpenTelemetry, TypeScript, Docker, Kubernetes.
Trial Proven capability ready for real production workloads under controlled, low-to-medium risk conditions. Requires ARB notification; clear success criteria and fallback plan required. gRPC for internal services, Rust for low-latency workers, Kafka Raft metadata.
Assess Promising technology to explore in spikes, hackathons, or non-critical prototypes. No production data; focus on understanding operational overhead and capabilities. WebAssembly on the edge (WasmEdge), Vector databases, eBPF telemetry.
Hold Technologies that should not be used in new projects; active migration plan for existing deployments. Explicit waiver required for any new usage; budget allocated for retirement. SOAP/XML services, self-hosted ZooKeeper clusters, legacy Angular 1.x.
How to Run a Quarterly Technology Radar Session

1. Gather nominations from engineering teams 3 weeks prior via a standardized 1-page form (Problem solved, alternatives, team experience).
2. Consolidate entries into Techniques, Platforms, Tools, and Languages/Frameworks.
3. Host a 2-hour ARB & Principal Engineer summit to debate changes in ring placement.
4. Publish radar with explicit rationale for every promotion, demotion, or new entry.

4. Architecture Reviews, ARB Charter, and Governance

Effective governance is an enabling guardrail, not an inspection checkpoint that delays delivery. Automate routine compliance via linters, pipeline scans, and contract verifiers; reserve human Architecture Review Boards (ARB) for irreversible decisions.

Architecture Review Board (ARB) Charter Template

  • Mission: Ensure technology investments align with enterprise strategy, minimize catastrophic operational risk, and foster long-term reusability.
  • Membership: Enterprise Architect (Chair), Chief Architect, Lead Security Architect, Data Governance Lead, Platform Engineering Director, rotating Principal Engineers.
  • Cadence: Bi-weekly 90-minute review sessions; asynchronous RFC reviews on GitHub/GitLab.
  • Decision Scope (Two-Way vs. One-Way Doors):
    • Type 1 (One-Way Door / Irreversible): New programming language, core database selection, major cloud vendor contract, cross-cutting auth change → Mandatory ARB Approval.
    • Type 2 (Two-Way Door / Reversible): Library upgrade, internal component refactoring, internal endpoint design → Delegated to local team lead.

Governance Anti-Patterns and Remedies

Anti-PatternSymptomRoot CausePractical Remedy
Ivory Tower Architects Architects produce 100-page specs that developers ignore or subvert. Architects detached from daily code, delivery pressure, and production debugging. Architects must pair with teams and maintain production on-call rotations.
Post-Mortem Review Gate Teams submit architectural designs for review 2 days before production launch. Governance viewed as an external hurdle rather than an early collaborative design session. Incorporate RFC drafts at sprint planning; require design sign-off before coding starts.
Unfunded Mandates ARB mandates migration to a new framework without engineering budget. Architecture disconnected from business prioritization and product backlog. Ring-fence 20% of every sprint capacity specifically for architectural enablement.

5. Technical Debt Governance

Technical debt is a natural byproduct of software development. Like financial debt, deliberate debt can be a healthy tool to capture time-sensitive business opportunities—provided the interest is actively tracked and repaid.

Martin Fowler's Technical Debt Quadrant

CategoryDeliberateInadvertent
Prudent "We must ship this MVP to beat competitors; we will deliberately defer database sharding and fix it in Q3." (Strategic, tracked) "Now that we've scaled to 10M users, we finally understand how the domain should really have been modeled." (Learning-driven)
Reckless "We don't have time to write automated tests or design a schema; just push to production." (Negligence, high interest) "What is layered architecture? What is dependency injection?" (Skill deficiency, unmanaged rot)

Technical Debt Register

Maintain an enterprise technical debt register alongside the product backlog. Each debt ticket must document: Debt ID, Owning System, Description, Annual Risk/Cost (Interest), Remediation Effort, Target Quarter, Responsible Lead. Teams allocate 15–20% of engineering bandwidth per sprint to service high-interest debt.

6. Stakeholder Management and Communication

Architects spend more time communicating tradeoffs than drawing diagrams. Map stakeholders using the standard Power-Interest Grid to calibrate communication depth:

QuadrantStakeholdersEngagement StrategyCommunication Medium
High Power, High Interest CTO, CISO, VP Engineering, Product VP Manage Closely; co-design key decisions; align on budget and strategic risk. Bi-weekly 1-on-1s, Executive Summaries, ADR impact briefs.
High Power, Low Interest CFO, General Counsel, Chief Compliance Officer Keep Satisfied; confirm regulatory adherence and financial TCO parameters. Quarterly risk/spend reports, formal audit deliverables.
Low Power, High Interest Senior Developers, DevOps/SREs, QA Leads Keep Informed & Consulted; deep-dive into developer ergonomics and APIs. RFC reviews, architecture town halls, interactive demos, code reviews.
Low Power, Low Interest External business users, wider enterprise staff Monitor; minimal communication unless systems disrupt daily workflows. Change logs, system release announcements.

7. Architecture Documentation: ADRs and C4 Models

Documentation must live in version control alongside the source code it describes. When architecture changes, the corresponding documentation PR merges in the same review.

Standard Architecture Decision Record (ADR)

# ADR-042: Adopt Event Sourcing for Order Fulfillment State

## Status
Accepted (Supersedes ADR-012)

## Date
2026-11-21

## Context
Our retail fulfillment engine suffers from race conditions during concurrent returns, 
warehouse pack cancellations, and customer address updates. Traditional CRUD updates 
overwrite states without an immutable audit trail, creating customer service disputes.

## Decision
We will model the Order aggregate using Event Sourcing. All state mutations will be 
recorded as an immutable sequence of domain events (OrderPlaced, ItemPacked, ReturnRequested) 
in an append-only event store backed by PostgreSQL with an outbox relay to Apache Kafka.

## Considered Alternatives
1. Pessimistic row locking on standard relational tables (Rejected: severe database contention at scale).
2. Distributed two-phase commit (2PC) with warehouse microservices (Rejected: high operational fragility).

## Consequences
- Positive: Complete auditability, time-travel debugging, zero state loss.
- Negative: Increased conceptual complexity for junior engineers; queries require read projections (CQRS).
- Compliance: PII in events must be protected via cryptographic key shredding upon GDPR deletion requests.

8. Practical Exercises

  1. Build vs. Buy Evaluation: Your company needs an enterprise authentication and Single Sign-On (SSO) solution supporting SAML, OIDC, and multi-factor authentication for 50,000 corporate users. Construct a weighted decision matrix comparing developing an internal OAuth service vs. adopting Auth0/Okta vs. running Keycloak on Kubernetes. Include 3-year TCO.
  2. Capability Decomposition: Choose a banking system (e.g., retail deposits or mortgage origination). Decompose the top-level capability into 3 Level-2 capabilities and 6 Level-3 capabilities. Identify which one represents competitive core differentiation.
  3. Technical Debt Remediation Plan: An order microservice is running an end-of-life database version with no automated regression test suite. Draft a 1-page business case to the Product Manager explaining why 2 full sprints must be dedicated to tech debt remediation, translating technical risks into customer impact and revenue risk.
