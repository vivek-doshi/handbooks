Software architecture: boundaries, qualities, and tradeoffs

Architecture is the set of structures and decisions that shape a system's behavior and evolution. Good architecture is not a diagram or a fashionable pattern: it is a set of deliberate choices that helps teams meet user needs under real constraints.

Quality attributesArchitectural stylesFailure and changeDecision checklist

1. Start with context and quality attributes

Before selecting a style, define system boundaries, actors, external dependencies, data ownership, and constraints. Convert vague goals into observable scenarios:

When [stimulus] occurs,
under [operating condition],
the system should [measurable response].
Measure: [latency, availability, correctness, cost, recovery].

Examples include a p95 checkout response below a target under a specified load, a recoverable regional outage, a safe schema migration with old and new clients, or a deletion request completed across derived data. Prioritize a few critical qualities; optimizing everything often creates needless complexity.

Architecture is consequential, not immutable

Keep decisions that are expensive to reverse visible, but do not freeze every implementation choice. Use lightweight Architecture Decision Records, small experiments, and fitness functions (automated checks for boundaries, dependencies, performance, or compliance) to validate that the design remains true.

BFF, CQRS, and event sourcing

A Backend for Frontend (BFF) tailors an API to a client experience; avoid turning it into a second business domain. CQRS separates command and query models when their needs differ materially. Event sourcing stores state changes as an event history; it adds replay, projection, privacy, and schema responsibilities. Neither CQRS nor event sourcing is a default requirement for every event-driven system.

3. Anti-patterns and the microservice complexity tax

  • Big-ball-of-mud: no enforced ownership or stable boundaries.
  • Distributed monolith: multiple services that must deploy together and share data tightly.
  • Premature abstraction: framework or platform built before repeatable needs are known.
  • Shared database by default: teams change one schema without clear ownership or compatibility.
  • Golden hammer: apply one style to every problem.
  • Architecture astronautics: optimize for hypothetical scale rather than measured constraints.

Microservices move complexity from in-process code to the network and organization: service discovery, authentication, deployment, compatibility, partial failure, tracing, on-call, and data consistency. A service boundary is worth its operational price when it buys clear ownership or an independently valuable capability.

4. Current practice: optimize for outcomes, not fashions

Modern architecture practice emphasizes operability and continuous learning: product-oriented platform capabilities, secure defaults, observable systems, automated delivery, and progressive change. A platform should be treated as a product for internal users, measured by adoption and reduced friction—not by how many tools it contains.

DORA's current software-delivery model uses five measures: change lead time, deployment frequency, failed deployment recovery time, change fail rate, and deployment rework rate. Use them to guide improvement for an application or service; do not turn one metric into an individual performance target. OpenTelemetry's semantic conventions help make telemetry more consistent across services and tools.

AI-enabled components add explicit concerns: model/provider substitution, data exposure, evaluation quality, cost per task, latency, unsafe outputs, and human escalation. Treat them as system dependencies with testable service objectives and risk controls, not as magical internal libraries.

5. A practical architecture process

  1. State users, outcomes, scope, constraints, and non-goals.
  2. Map important use cases, data flows, external systems, and trust boundaries.
  3. Write measurable quality scenarios and identify the highest risks.
  4. Compare at least two viable options, including the simplest one.
  5. Document only consequential decisions, alternatives, and consequences.
  6. Validate with a prototype, load test, threat model, or migration rehearsal.
  7. Instrument production, review evidence, and revise decisions when context changes.
PracticeFor a small online bookstore, compare a single deployable application, a modular monolith, and service decomposition. Use team count, independent release needs, availability targets, data ownership, and operating maturity—not anticipated user counts alone.

Architecture design checklist

  • Are system scope, responsibilities, owners, and external dependencies clear?
  • Are the critical quality attributes measurable and prioritized?
  • Are data classification, retention, privacy, and recovery addressed?
  • Are failure modes, overload, retries, timeouts, and degraded behavior explicit?
  • Can teams deploy, observe, secure, and operate the proposed design?
  • Are compatibility and migration steps planned for interfaces and data?
  • Can the design be simplified without breaking a real requirement?
