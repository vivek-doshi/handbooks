Step 08 · Intermediate · Asynchronous design

Event-driven architecture

Events allow producers to broadcast facts without real-time coordination with downstream consumers. This unlocks elastic scaling and temporal decoupling, while introducing eventual consistency, duplicate delivery, schema evolution, and distributed observability challenges.

Event Storming Kafka · Pulsar · RabbitMQ · Cloud Brokers Transactional Outbox & CDC Sagas & Event Sourcing DLQ Runbooks & Tracing

1. Event-Driven Concepts and Event Anatomy

A domain event is an immutable statement that an important state transition has already occurred in the past (e.g., OrderPlaced, PaymentAuthorized). It cannot be canceled; it can only be compensated by a subsequent event.

  • Command: A directed request to a specific recipient demanding an action (e.g., AuthorizePayment). May be rejected.
  • Event: A broadcast statement of completed fact. Cannot be rejected; recipients react autonomously.
  • Query: A read-only request for current state without side effects.

2. Event Storming: Rapid Domain Discovery

Event Storming is a collaborative workshop method that models complex business domains through the timeline of events they produce:

  • Orange Sticky Notes (Domain Events): Written strictly in past tense (OrderSubmitted, PaymentFailed, InventoryAllocated). Arranged left-to-right chronologically.
  • Blue Sticky Notes (Commands): Actions triggered by users or external systems that produce an event (SubmitOrder).
  • Yellow Sticky Notes (Aggregates): Domain entities and business invariant boundary enforcers (Order, Account).
  • Pink Sticky Notes (Policies / Reactive Rules): "Whenever [Event X] happens, do [Command Y]" (e.g., Whenever OrderPlaced, ReserveStock).

3. Selecting a Message Broker

Broker TechnologyStorage & Delivery ModelBest Fit WorkloadsKey Tradeoffs to Consider
Apache Kafka Durable, partitioned, append-only disk log. Consumers track offsets independently. High-throughput event streaming, event sourcing, replayable audit streams, real-time analytics. Partition rebalance pauses; partition sizing cannot be decreased; client complexity.
Apache Pulsar Separates compute (Brokers) from storage (Apache BookKeeper). Multi-tenancy native. Multi-tenant enterprises, millions of individual topics, geo-replication. High operational footprint (ZooKeeper + BookKeeper + Pulsar Brokers).
RabbitMQ Traditional smart-broker / dumb-consumer AMQP message queues with complex routing exchanges. Task queues, complex content/topic routing, RPC-over-messaging, immediate job dispatch. Messages deleted after ack; zero native historical replay; throughput limits under massive queues.
AWS EventBridge / SNS+SQS Fully managed cloud serverless event routing with schema registry and SaaS integrations. Serverless architectures, cross-AWS account event routing, low operational maintenance. Latency spikes (50–100ms+); vendor lock-in; per-million request cost at scale.
NATS / JetStream Ultra-lightweight, high-performance messaging with optional durable streaming. Microservices, edge computing, IoT, Kubernetes internal service communication. Smaller ecosystem of managed enterprise connectors compared to Kafka.

4. Kafka Architecture Deep Dive

  • Partition Strategy & Ordering: Kafka provides strict ordering only within a single partition. If order events must be processed sequentially for a customer, set the partition key to customerId (or orderId).
    Hot-Partition Warning: If a partition key is skewed (e.g., partition by merchant_id and Amazon is one merchant), a single broker partition will saturate while others sit idle. Add a synthetic salt (e.g., merchant_id + "_" + (hash % 10)) to balance high-volume keys.
  • Consumer Groups & Rebalancing: When a consumer node joins or crashes, Kafka triggers a rebalance. Use modern Cooperative Sticky Assignors (incremental rebalancing) to prevent "stop-the-world" consumer pauses across all partitions.
  • Exactly-Once Semantics (EOS): Kafka achieves idempotent production via producer sequence numbers and transactions across multiple topics. However, end-to-end "exactly-once" across external databases requires idempotent consumer processing at the application layer.

5. The Transactional Outbox Pattern and Change Data Capture (CDC)

A classic distributed systems bug occurs when an application updates a database and then attempts to publish an event to Kafka. If the broker is unreachable, the event is lost; if the broker succeeds but the database commits fail, a phantom event is broadcast.

The Transactional Outbox Solution

  1. Inside a single ACID database transaction, insert the business entity into orders and the serialized event into an outbox_events table.
  2. Commit the database transaction. State and event are guaranteed to be persisted together.
  3. An asynchronous background relay process (e.g., Debezium CDC or polling worker) reads the outbox table and publishes events to the broker.
  4. Once published, the relay marks the outbox record as published or removes it.

Change Data Capture (Debezium): Rather than polling the outbox table with SELECT ... FOR UPDATE, Debezium directly reads the database transaction log (PostgreSQL WAL or MySQL binlog). This produces near-zero database CPU overhead and captures mutations in sub-second time.

6. Event Sourcing and Aggregate Projections

Traditional CRUD overwrites row state. Event Sourcing stores the sequence of events as the single source of truth:

ShoppingCart Aggregate Event Stream:
  1. CartCreated(cartId: 101, userId: 44)
  2. ItemAdded(cartId: 101, sku: "A1", qty: 2)
  3. ItemAdded(cartId: 101, sku: "B2", qty: 1)
  4. ItemRemoved(cartId: 101, sku: "A1", qty: 1)
  5. CouponApplied(cartId: 101, code: "SAVE10")

Rebuilding State:
  Current Cart = Fold/Reduce(Events, InitialEmptyCart)
  - Result: 1x "A1", 1x "B2", 10% Discount applied.

Snapshots: Replaying 10,000 events to calculate current state is slow. Periodically write a snapshot (e.g., every 100 events) and replay only subsequent events.
Crypto-Shredding for GDPR: When a user requests deletion under GDPR, you cannot delete events from an immutable append-only ledger. Mitigate this by encrypting user PII in each event with a unique per-user encryption key; upon deletion request, destroy the user's encryption key. The event history remains intact, but the PII becomes unrecoverable cryptographically.

7. Observability, Dead-Letter Queues, and Operational Runbooks

  • Consumer Lag: The number of unread records between the producer's latest offset and the consumer's current committed offset. A growing lag indicates consumer failure, slow database queries, or traffic spikes.
  • Dead-Letter Queue (DLQ) Operational Runbook:
    1. Quarantine: If a message fails after 3 exponential backoff retries (e.g., malformed JSON or poisoned schema), route it to orders.dlq. Never drop messages silently.
    2. Alerting: Trigger PagerDuty when DLQ depth > 0.
    3. Inspection & Bug Fix: Developers inspect the payload and stack trace, patch the consumer bug, and deploy the fix.
    4. Replay: Run an automated replay tool that consumes from the DLQ and re-publishes messages back into the primary processing topic.

8. Practical Exercises

  1. Event Storming Model: Conduct an event storming session on an automated hotel room reservation system. Model at least 6 domain events, 3 commands, 2 aggregates, and 1 compensating event.
  2. Idempotent Consumer Implementation: Write pseudocode for an event consumer that receives PaymentCompleted events. Use an idempotency table with unique constraints to ensure that duplicate message delivery does not credit a customer balance twice.
  3. Outbox vs. 2PC Comparison: Explain why a two-phase commit (2PC) between a PostgreSQL database and an Apache Kafka cluster is fragile in cloud deployments, and contrast it with a Transactional Outbox pattern backed by Debezium.
