Step 08 · Intermediate · Asynchronous design

Event-driven architecture

Events let producers publish facts without coordinating every consumer in real time. This enables decoupled workflows and streaming, while introducing eventual consistency, duplicate handling, contract evolution, and operational responsibility.

Messaging patternsKafka · Pulsar · RabbitMQDelivery and retriesSagas and CQRS

1. Event-driven architecture and core patterns

An event is an immutable statement that something happened, such as OrderPlaced. A command requests work (ReserveInventory); a query requests current information. Keep these meanings distinct.

  • Publish/subscribe: multiple subscribers react to an event.
  • Queue / competing consumers: workers share a stream of tasks for load distribution.
  • Event notification: a small fact prompts a consumer to fetch more data.
  • Event-carried state transfer: an event contains enough data for a consumer, with stronger privacy and schema obligations.
  • Stream processing: process ordered records with windows, joins, and state over time.

Event anatomy

Include a stable event type and version, unique event ID, occurrence time, producer/source, aggregate or entity ID, correlation/trace context, and the minimal payload consumers require. Distinguish event time from processing time; avoid secrets and unnecessary personal data.

2. Pub/sub, event sourcing, and CQRS

Pub/sub distributes events; it does not require the producer's state to be event-sourced. Event sourcing uses an append-only event log as the authoritative history from which state can be rebuilt. It is useful for audit-heavy or temporal domains when replay and history justify more complex schema evolution, projections, privacy handling, and operations.

CQRS separates command handling from query models. A read projection can lag behind writes, so APIs must explain consistency and handle stale reads. Combine CQRS with event sourcing only when those independent needs are real.

Transactional outbox

When a database update must produce an event, save both business state and an outbox record in one local transaction. A relay publishes records and marks progress. Consumers remain idempotent because publication and delivery can repeat.

3. Choosing a broker: Kafka, Pulsar, or RabbitMQ

Select based on workload, operational capability, ecosystem, and measured requirements—not brand popularity.

TechnologyCommon fitEvaluate carefully
Apache KafkaDurable partitioned logs, replay, high-throughput streams, broad ecosystemPartition/key design, retention, consumer lag, cluster operations
Apache PulsarMessaging and streaming with multi-tenancy and separated storage/compute optionsOperational model, deployment complexity, ecosystem fit
RabbitMQFlexible routing, task queues, work distribution, conventional broker workflowsQueue topology, persistence/throughput needs, cluster and flow control

Managed service availability, regional recovery, quotas, client maturity, support, and total operating cost may be more decisive than feature comparisons. Prototype the failure and replay paths before standardizing.

4. Contracts, ordering, and delivery guarantees

Schema evolution is a compatibility policy. Add optional fields carefully, preserve field meaning, and test producer/consumer combinations during rolling deployment. Use a schema registry or contract checks when multiple teams publish shared events. CloudEvents offers a common event envelope, but it does not define business semantics.

  • At-most-once: no retry after uncertain processing; loss is possible.
  • At-least-once: retry until acknowledged; duplicates are possible.
  • Effectively-once business effect: use stable event IDs, idempotency, deduplication, and transactional boundaries.

Ordering is usually scoped to a partition, key, queue, or entity—not global. Pick a key that preserves only the ordering your domain requires. Avoid describing a broker's delivery guarantee as an end-to-end business guarantee.

5. Idempotency, retries, and dead-letter handling

Consumers should store processed IDs or use an idempotent state transition. Apply bounded retries with exponential backoff and jitter; classify transient versus permanent failures. A poison message should not block unrelated work unless strict ordering requires it.

Dead-letter queues are quarantine and investigation tools, not automatic success. Include original metadata, failure reason, attempt count, and replay process. Redact sensitive payloads, set retention, alert on growth, and make replay safe.

Saga pattern

A saga coordinates a long-running business workflow through local transactions and explicit compensations or forward recovery. Define timeouts, duplicate messages, compensation failure, manual intervention, and the source of workflow truth. Choose choreography for small, loosely coupled flows; an orchestrator can make complex state more visible.

6. Observability and anti-patterns

Propagate trace and correlation context. Monitor publish errors, consumer lag, processing latency, retry rate, dead-letter volume, throughput, and broker saturation. OpenTelemetry messaging conventions evolve; use the current conventions supported by your instrumentation, and avoid high-cardinality identifiers as metric labels.

  • Do not use a generic event bus as hidden remote procedure calls.
  • Do not publish database rows as public contracts without ownership.
  • Do not promise immediate consistency to clients when projections lag.
  • Do not retry forever or silently discard failures.
  • Do not create a topic/queue per entity without lifecycle governance.

7. Migration roadmap and practice

  1. Choose one integration where asynchronous behavior has clear value.
  2. Define event ownership, schema, privacy, retention, ordering, and consumer obligations.
  3. Implement transactional publication and an idempotent consumer.
  4. Test duplicate, delayed, out-of-order, poison, and unavailable-broker cases.
  5. Add tracing, lag/error metrics, alerts, DLQ review, and replay procedures.
  6. Roll out beside the existing flow, compare outcomes, then retire the old path.
PracticeModel order placed → payment authorized → inventory reserved. Define event payloads, idempotency key, timeout behavior, compensation, and what the customer sees while the workflow is pending.
