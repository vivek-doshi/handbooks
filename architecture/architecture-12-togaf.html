TOGAF: structure enterprise change

The Open Group Architecture Framework (TOGAF Standard 10th Edition) provides a proven, configurable methodology for governing complex enterprise digital transformation across business, data, application, and technology architectures.

1. The Architecture Development Method (ADM) Deep Dive

The ADM is an iterative, closed-loop cycle for developing enterprise architectures. It consists of 10 distinct phases:

ADM PhaseCore Purpose & ActivitiesKey Inputs & Outputs
Preliminary Phase Establish the architecture capability, tailor framework standards, define governance charters and tooling. Input: Business strategic goals.
Output: Architecture Principles, Governance Charter, Tailored Framework.
Phase A: Architecture Vision Define project scope, identify stakeholders, align business objectives, secure executive sponsorship. Input: Request for Architecture Work.
Output: Statement of Architecture Work, Architecture Vision, Stakeholder Map.
Phase B: Business Architecture Model business capabilities, value streams, organizational structures, and business processes (target vs. baseline). Input: Architecture Vision.
Output: Capability Maps, Value Stream Maps, Target Business Architecture, Gap Analysis.
Phase C: Information Systems Model Data and Application architectures: entity lifecycles, data lineage, service boundaries, and system interactions. Input: Business Architecture.
Output: Conceptual/Logical Data Models, Application Communication Topologies, Gap Analysis.
Phase D: Technology Architecture Design infrastructure, cloud landing zones, networks, security zones, hardware platforms, and runtime environments. Input: Application & Data Architectures.
Output: Target Technology Architecture, Deployment Models, Network Topology.
Phase E: Opportunities & Solutions Identify candidate implementation initiatives, transition architectures, build-vs-buy decisions, and migration groupings. Input: Gap analyses from B, C, D.
Output: Transition Architectures (State 1, State 2), Implementation Recommendations.
Phase F: Migration Planning Prioritize projects by business value and risk, sequence dependencies, allocate budget, and finalize implementation roadmap. Input: Transition Architectures.
Output: Architecture Implementation Roadmap, Migration Plan.
Phase G: Implementation Governance Ensure ongoing engineering delivery conforms to architectural designs via automated CI/CD checks and ARB checkpoints. Input: Implementation Roadmap.
Output: Architecture Compliance Reviews, Approved Waivers, Change Requests.
Phase H: Change Management Monitor technology disruptions (e.g., AI/GenAI, cloud cost shifts) and determine when new ADM cycles must trigger. Input: Technology trends, business strategy updates.
Output: New Request for Architecture Work.
Requirements Management Continuous process operating at the center of the ADM, capturing, prioritizing, and validating enterprise requirements. Maintains: Centralized Architecture Requirements Repository.

2. Architecture Building Blocks (ABBs) vs. Solution Building Blocks (SBBs)

TOGAF strictly distinguishes between conceptual requirements and concrete vendor implementations:

AttributeArchitecture Building Block (ABB)Solution Building Block (SBB)
Definition Describes what functional capability is required, independent of vendor or technology. Describes how the capability is realized using a specific physical software product or service.
Phase Created Phases A, B, C, D (Architecture Definition) Phase E (Opportunities and Solutions)
Example 1: Messaging "Durable, partitioned event log with pub/sub and replay capabilities." "Apache Kafka 3.7 cluster on AWS MSK."
Example 2: Identity "OIDC/OAuth 2.0 identity provider with MFA and SAML federation." "Okta Workforce Identity Cloud."
Example 3: Database "ACID-compliant relational database supporting spatial GIS queries." "Amazon Aurora PostgreSQL 16 with PostGIS extension."

3. Developing Architecture Principles

Architecture principles define enduring guardrails that govern all subsequent technology decisions. Every principle must follow the standard 3-part format: Statement, Rationale, Implications.

8 Production Architecture Principles

  1. API-First Integration:
    • Statement: All system capabilities must be exposed through documented, versioned, and authenticated APIs before UI development begins.
    • Rationale: Promotes reuse, decouples frontends, and enables automated partner integrations.
    • Implications: Direct database-to-database integration is prohibited; OpenAPI/Protobuf specifications must be published prior to coding.
  2. Buy Before Build:
    • Statement: Adopt commercial SaaS or mature open-source solutions for non-differentiating commodity business capabilities.
    • Rationale: Directs scarce internal engineering bandwidth strictly toward proprietary market differentiators.
    • Implications: Custom software development requires explicit ARB justification proving competitive advantage.
  3. Zero Trust Security:
    • Statement: Never trust, always verify. Every request must be authenticated, authorized, and encrypted in transit regardless of network location.
    • Rationale: Perimeter network defenses are obsolete in modern distributed and multi-cloud environments.
    • Implications: Internal microservice calls must execute mutual TLS (mTLS); network proximity conveys zero access privileges.

4. ArchiMate Modeling Integration

While TOGAF defines the process, ArchiMate provides the visual modeling language. ArchiMate is organized into 5 primary layers:

  • Strategy Layer: Capabilities, Resources, Courses of Action, Strategic Goals.
  • Business Layer: Business Actors, Business Roles, Business Processes, Business Services.
  • Application Layer: Application Components, Application Interfaces, Application Services, Data Objects.
  • Technology Layer: Nodes (Servers/VMs), System Software (OS/Runtimes), Communication Networks.
  • Implementation & Migration: Work Packages, Deliverables, Plateaus (Transition States), Gaps.

5. Practical Exercises

  1. Drafting an Architecture Principle: Write a comprehensive architecture principle for "Cloud-Native Ephemeral Compute" following the Statement, Rationale, and Implications format. Include implications for local state storage and container startup times.
  2. ABB to SBB Mapping: Create an architecture catalog table identifying 4 core ABBs needed for an enterprise fraud-detection system, and map each to two competing candidate SBBs.
  3. Tailoring the ADM: An agile engineering organization delivers 2-week sprints. How would you tailor the ADM to avoid heavy upfront waterfall documentation while maintaining architectural governance?
