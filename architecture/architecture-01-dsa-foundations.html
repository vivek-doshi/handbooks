Computer science foundations for architects

Architecture decisions become clearer when you can estimate the cost of the work a system performs. This lesson builds practical intuition for data structures, algorithms, memory, and the common problem-solving patterns behind production software.

What you will be able to do

  • Compare algorithm costs as data grows without relying on isolated, unrepresentative benchmarks.
  • Select arrays, lists, queues, maps, trees, heaps, or graphs to fit real production access patterns.
  • Evaluate modern architect-level structures: Tries, Bloom filters, Skip lists, B+ trees, and LSM trees.
  • Recognize sorting, searching, recursion, and dynamic-programming patterns in systems.
  • Explain how CPU cache locality, allocation overhead, and pointer chasing affect real latency.
  • Choose appropriate distributed algorithms and structures for partitioning, rate limiting, and consensus.
Why this belongs in an architecture path Capacity estimates, cache design, search indexes, queues, distributed locks, database indexes, and graph traversals all depend on foundational computational and memory tradeoffs.

1. Complexity, Amortization, and the Memory Model

Big-O describes how resource consumption grows asymptotically with input size, not an exact wall-clock runtime. For an input of n items, common growth rates define whether a feature scales gracefully or triggers cascading outages under load:

Class Name Example in Systems Operations for n = 1,000,000 Growth Intuition
O(1) Constant Hash table lookup, array index, push/pop stack 1 operation Independent of dataset size
O(log n) Logarithmic B-tree index lookup, binary search ≈ 20 operations Each step divides remaining search space by a factor
O(n) Linear Full table scan, unindexed search, string equality 1,000,000 operations Work scales linearly with record volume
O(n log n) Linearithmic Merge sort, heap sort, indexing a bulk load ≈ 20,000,000 operations Divide-and-conquer sorting and tree reconstruction
O(n²) Quadratic Nested loop join without index, all-pairs comparison 1,000,000,000,000 (1 trillion) Doubling input quadruples work; dangerous in web requests

Best, Average, and Worst Case

Architects must design for the worst-case or high-percentile (p99/p99.9) behavior, not just sunny-day averages. A standard hash map offers O(1) average lookup, but degrades to O(n) if hash collisions spike (e.g., hash-collision DoS attacks). Quicksort averages O(n log n), but degrades to O(n²) with poor pivot selection.

Amortized Analysis

An operation has an amortized cost T if a sequence of k operations takes at most k × T total time, even if occasional single operations take significantly longer.

Example: Dynamic Array Appends When appending to a dynamic array (e.g., Python list, Java ArrayList, Go slice), most appends take O(1) time. When the underlying capacity is reached, the array allocates a new buffer of size 2N and copies all N elements, costing O(N). Because doublings occur only at powers of 2 (1, 2, 4, 8, 16...), the total copying cost for N insertions is \(N/2 + N/4 + \dots + 1 < N\). The amortized cost per append remains strictly O(1). However, in low-latency trading or real-time gaming, that single O(N) reallocation pause (p99.99 latency spike) may violate strict SLAs, requiring pre-allocated buffers.

Memory Hierarchy, Cache Locality, and Latency Numbers

Modern CPUs process instructions in fractions of a nanosecond, but fetching data from main memory takes tens to hundreds of nanoseconds. Sequential memory access enables hardware prefetching and maximizes L1/L2/L3 cache line utilization (typically 64 bytes per line). Linked structures (linked lists, uncompacted trees) incur pointer-chasing cache misses, making them 5x to 50x slower in practice than contiguous arrays despite identical Big-O time complexity.

Advanced Structures for Systems Architects

  • Trie (Prefix Tree): Stores strings by shared prefixes. Key lookup takes O(k) where k is key length, independent of total stored items n. Ideal for autocomplete systems, IP routing tables (longest prefix match), and URL routing in web frameworks.
  • Bloom Filter: A space-efficient probabilistic data structure based on bit arrays and multiple hash functions. Tests set membership with zero false negatives (if it says absent, it is definitely absent) and configurable false positive rate (e.g., 1%). Widely used in Cassandra/RocksDB to prevent expensive disk seeks for non-existent row keys, and in CDN web caches.
  • Skip List: A probabilistic layered linked-list hierarchy that achieves O(log n) search, insertion, and deletion without complex tree rebalancing. Used internally by Redis Sorted Sets (ZSET) and LevelDB/RocksDB MemTables for concurrent lock-free reads.
  • B-Tree and B+ Tree: Self-balancing search trees optimized for block storage. Nodes store hundreds or thousands of keys matching disk block sizes (e.g., 4KB-16KB). In a B+ tree, internal nodes store only routing keys, and all records are chained in leaf nodes, providing both O(log n) lookup and high-throughput sequential range scans in PostgreSQL, MySQL InnoDB, and file systems.
  • LSM Tree (Log-Structured Merge-Tree): Transforms random writes into sequential disk writes by appending to an in-memory MemTable (skip list or red-black tree) backed by a write-ahead log (WAL). Periodically flushed to immutable disk SSTables and compacted in background tiers. Powers high-write stores like Apache Cassandra, ScyllaDB, Bigtable, and RocksDB.

3. Sorting, Searching, and Core Problem Patterns

Searching & Binary Search on Monotonic Spaces

Linear search takes O(n). Binary search cuts the search space in half at each step in O(log n). In architecture, binary search is applied not just to arrays, but to monotonic predicates (e.g., capacity sizing, autoscaling thresholds, log timestamp indexing):

// Safe Binary Search avoiding 32-bit integer overflow
function binarySearch(arr, target) {
  let low = 0;
  let high = arr.length - 1;
  while (low <= high) {
    // Avoid (low + high) / 2 which can overflow in 32-bit signed ints
    const mid = low + Math.floor((high - low) / 2);
    if (arr[mid] === target) return mid;
    if (arr[mid] < target) {
      low = mid + 1;
    } else {
      high = mid - 1;
    }
  }
  return -1; // Not found
}

Dynamic Programming: Memoization vs. Tabulation

Dynamic programming applies when a problem exhibits optimal substructure and overlapping subproblems. In system architecture, DP underlies distributed cache eviction policies, rate-limit token bucket accounting, shortest-path calculation, and query execution plan cost optimizers.

// Example: Minimum Coins / Token Allocation Problem
// Memoization (Top-Down): Recursive with caching
function minCoinsMemo(coins, amount, memo = {}) {
  if (amount === 0) return 0;
  if (amount < 0) return Infinity;
  if (memo[amount] !== undefined) return memo[amount];

  let min = Infinity;
  for (const c of coins) {
    const res = minCoinsMemo(coins, amount - c, memo);
    if (res !== Infinity) min = Math.min(min, res + 1);
  }
  memo[amount] = min;
  return min;
}

// Tabulation (Bottom-Up): Iterative table building, avoids call-stack overflow
function minCoinsTab(coins, amount) {
  const dp = new Array(amount + 1).fill(Infinity);
  dp[0] = 0;
  for (let i = 1; i <= amount; i++) {
    for (const c of coins) {
      if (i - c >= 0) {
        dp[i] = Math.min(dp[i], dp[i - c] + 1);
      }
    }
  }
  return dp[amount] === Infinity ? -1 : dp[amount];
}

Core Graph Algorithms in Infrastructure

  • Dijkstra's Algorithm: Finds single-source shortest paths on non-negative weighted graphs using a priority queue in O((V + E) log V). Used in OSPF/IS-IS network routing and transit network cost routing.
  • Topological Sort (Kahn's / DFS): Produces a linear ordering of vertices in a Directed Acyclic Graph (DAG) in O(V + E). Used by task orchestrators (Apache Airflow, GitHub Actions, Terraform execution plans, Kubernetes resource initialization orders).
  • Tarjan's / Kosaraju's Strongly Connected Components: Detects circular dependencies and component islands in microservice dependency graphs.

4. Concurrent and Distributed Data Structures

Single-threaded data structures break down when accessed across multiple CPU cores or independent nodes. Distributed architectures rely on specialized primitives:

  • Compare-And-Swap (CAS) & Lock-Free Queues: Modern multicore engines (e.g., LMAX Disruptor, Java ConcurrentLinkedQueue) eliminate lock contention by executing atomic hardware CPU instructions (e.g., CMPXCHG on x86), achieving millions of ops/second per core.
  • Concurrent Hash Map (Striped Locks): Splits the key space into buckets or segments, allowing concurrent reads without locking and localized locks only on specific segments during writes.
  • Write-Ahead Log (WAL): An append-only disk structure. Because sequential writes are orders of magnitude faster than random database updates, transactions are committed to the WAL first, ensuring crash-recovery durability (ACID) before updating B-trees or memory.
  • Distributed Hash Table (DHT): Partitions keys across independent physical machines using consistent hashing (e.g., Chord, Dynamo, Kademlia in BitTorrent).
  • Merkle Tree (Hash Tree): A tree where every leaf node is labeled with the cryptographic hash of a data block, and every parent is the hash of its children. Allows distributed replicas (Cassandra, Git, blockchain) to detect replica divergence and synchronize large datasets with minimal network transfer.

5. Essential Algorithms for System Architects

  • Consistent Hashing: Traditional modulo hashing (hash(key) % N) remaps nearly all keys when node count N changes, causing cache invalidation storms. Consistent hashing places nodes and keys on a virtual ring (0 to \(2^{32}-1\)). When a node is added or removed, only \(K/N\) keys migrate on average. Virtual nodes balance skew and eliminate hotspots.
  • Rate Limiting Algorithms:
    • Token Bucket: Tokens are added at a fixed rate up to capacity; bursts up to bucket size are accepted. Ideal for API gateways.
    • Leaky Bucket: Enforces smooth, constant egress rate; absorbs bursts up to queue depth.
    • Sliding Window Counter: Combines weighted counts from previous and current time windows to prevent end-of-interval boundary traffic surges.
  • Leader Election & Consensus (Raft / Paxos): Ensures a distributed cluster agrees on a single authoritative state machine leader despite node crashes and network partitions. Raft breaks consensus into leader election, log replication, and safety invariants.
  • HyperLogLog (HLL): A probabilistic algorithm estimating cardinality (e.g., unique daily active users) of billions of items with standard error < 1% using only ~1.5 KB of memory. Used heavily in Redis (PFADD, PFCOUNT) and analytics platforms.

6. Practical Exercises and Architecture Decisions

  1. Membership vs. Scale: For a fraud service checking 500 million blacklisted IP addresses in < 5 ms:
    • Compare an in-memory Hash Set vs. a Bloom Filter paired with an SSD-backed key-value store.
    • Calculate the RAM needed for a raw Hash Set (assume 16 bytes per entry + 24 bytes pointer overhead ≈ 20 GB RAM) vs. an 8-bit-per-key Bloom filter (≈ 500 MB RAM).
  2. Cache with TTL and LRU Eviction: Design a thread-safe in-memory cache supporting get(key), set(key, value, ttl), and maximum capacity eviction in O(1) time. Which two data structures must be combined? (Hint: Doubly linked list for recency + Hash map for fast lookup + Min-heap or bucket wheel for TTL expiration).
  3. Distributed Task Scheduling: A system schedules 100,000 background jobs per minute with millisecond-exact execution times. Compare using a relational database table with ORDER BY execution_time vs. an in-memory Hierarchical Timing Wheel vs. a Redis Sorted Set.
