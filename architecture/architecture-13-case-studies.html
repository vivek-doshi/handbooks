Architecture case studies: from use case to design

There is no universally "correct" architecture in isolation. Good architecture balances specific business requirements, quality attribute scenarios, operational constraints, and failure modes. These 5 comprehensive case studies illustrate how to derive defensible production architectures.

Case Study 1: E-Commerce Checkout When Payment Can Be Slow

1. Problem & Design Drivers

A customer submits an order. The payment gateway may take 10 seconds or time out completely. The system must prevent duplicate charges on retry, ensure zero lost orders, and provide real-time status updates.

2. Capacity & Latency Budget

  • Traffic: 500 orders/sec average; peak = 2,500 orders/sec.
  • Storage: 2 KB per order record × 50M orders/year = 100 GB/year (Aurora PostgreSQL).
  • Latency Budget: API Gateway (5ms) → Order Module & DB Outbox (20ms) → Immediate 202 Accepted returned to client in < 30ms. Background Outbox relay and payment processing take 1–3 seconds asynchronously.

3. Tradeoffs & Failure Modes

  • Outbox Atomicity: Order creation and outbox recording share a single local PostgreSQL transaction, eliminating dual-write loss.
  • Provider Timeout Handling: A timeout does NOT mean payment failed. The payment worker marks the attempt as PENDING_RECONCILIATION and executes an idempotent status poll before retrying.

Case Study 2: Live Multi-Tenant Product Analytics

1. Problem & Design Drivers

Tenants send high-volume user events. Dashboards require sub-5 second freshness with complex aggregations, tenant isolation, and strict data retention controls.

2. Capacity Estimation

  • Volume: 10,000 events/sec average; peak = 50,000 events/sec. 10,000 × 86,400 ≈ 864 Million events/day.
  • Storage: 500 bytes/event = 432 GB/day raw storage. Raw events archived to S3/GCS in Parquet format with Snappy compression (~80 GB/day). Aggregates stored in ClickHouse / BigQuery.

Case Study 3: Real-Time Collaborative Document Editor

1. Problem & Key Requirements

Build a real-time collaborative document platform (like Google Docs or Notion). Multiple users concurrently type, edit, and format documents while offline edits seamlessly merge without data loss upon reconnection.

2. Conflict Resolution: OT vs. CRDT

DimensionOperational Transformation (OT)Conflict-Free Replicated Data Types (CRDT)
ArchitectureServer-centric; central server orders and transforms operations.Decentralized / peer-to-peer; mathematically provable eventual convergence.
Offline SupportComplex multi-step rebasing against server history.Native; local operations merge deterministically upon reconnection.
Memory OverheadLow (stores operation transforms).Moderate (metadata/tombstones tracked per character, e.g., Yjs, Automerge).
Industry AdoptionGoogle Docs (classic), Microsoft Office Online.Figma, Notion, Apple Notes, Zed Editor.

3. Architectural Flow

Client A                    WebSocket Gateway               Document Worker
   │                               │                              │
   │── [Local Edit: Insert "X"] ──>│                              │
   │   (Optimistic UI Render)      │── Forward Op (Doc 101) ─────>│
   │                               │                              │ [CRDT State Merge]
   │                               │                              │ [Persist to Redis/WAL]
   │                               │<── Broadcast Merged Delta ──│
   │<── Broadcast Delta to All ────│
   ▼                               ▼
Client B receives delta and renders character at exact coordinate without locking.

4. Storage & Snapshot Strategy

Appending millions of keystrokes produces giant document logs. Every 100 operations (or 5 minutes), the Document Worker compiles an immutable snapshot stored in S3. New clients load the latest snapshot and apply only recent delta operations.

Case Study 4: Social Media Feed and Notification System

1. Problem & Key Requirements

Build a social media timeline and notification platform (like X/Twitter or Instagram) for 100 Million Daily Active Users (DAU). Users post updates and follow others; feeds must render in < 150 ms.

2. Fan-Out on Write vs. Fan-Out on Read (The Celebrity Problem)

PatternMechanicsProsCons
Fan-Out on Write (Push) When user posts, background workers push the post ID into every follower's Redis timeline. Read queries are O(1) instant Redis reads. Celebrity posting with 50M followers triggers 50M Redis writes (massive write amplification).
Fan-Out on Read (Pull) Timeline generated on-the-fly when user opens app by querying followed accounts. Zero write amplification when posting. Read queries are extremely slow, requiring multi-table SQL joins across thousands of users.
Hybrid Model (Production Standard) Push-on-write for standard users (< 25,000 followers). Pull-on-read for high-follower celebrities. Fast reads for 99% of posts; zero write explosions during celebrity tweets. Timeline generation service must merge cached feeds with pulled celebrity posts at read time.

3. Capacity & Storage Sizing

  • 100M DAU × 2 posts/day = 200M posts/day (≈ 2,300 posts/sec write average).
  • Read traffic: 100M DAU × 10 timeline visits/day = 1 Billion views/day (≈ 12,000 reads/sec).
  • Timeline Cache: Keep 800 recent post IDs in a Redis Sorted Set (ZSET) per user: 100M users × 800 IDs × 8 bytes ≈ 640 GB RAM (distributed across 10 Redis nodes).

Case Study 5: Cloud File Storage and Synchronization

1. Problem & Key Requirements

Design a cloud file storage and synchronization engine (like Google Drive or Dropbox). Supports multi-GB file uploads, cross-device file synchronization, deduplication, and bandwidth-efficient delta syncing.

2. Chunking and Content-Addressable Storage (CAS)

Client File Upload Workflow:
  1. Client slices 1 GB file into deterministic 4 MB chunks.
  2. Computes SHA-256 cryptographic hash per chunk.
  3. Queries Metadata Service: "Do hashes [H1, H2, H3...] already exist in object storage?"
  4. If H1 and H2 already exist (e.g., uploaded by another user), skip upload! (Global Deduplication).
  5. Uploads only missing chunk H3 via pre-signed S3 multi-part upload URL.
  6. Metadata Service saves File Manifest: [H1, H2, H3] linked to user account.

3. Cross-Device Sync Architecture

  • Metadata Service: Stores file hierarchy, folder structures, permissions, and chunk manifests in PostgreSQL.
  • Delta Sync Protocol: When a user edits 1 page in a 200-page document, only the modified 4 MB chunk is uploaded and synchronized to other connected devices via WebSocket push notifications.

6. The Red Team Architectural Challenge

Before approving any production design, subject it to adversarial "Red Team" stress testing:

  • Dependency Latency Multiplication: What happens to the system if your third-party payment provider's latency jumps from 200 ms to 15 seconds without returning an error? (Does it exhaust API gateway thread pools?)
  • Split-Brain Recovery: During a network partition between US-East and US-West, both regions accept writes. What is the deterministic conflict resolution rule when the network heals?
  • Database Failover Data Loss: Under synchronous database replication, primary failover takes 30 seconds. How does the frontend handle customer requests in flight during those 30 seconds?
