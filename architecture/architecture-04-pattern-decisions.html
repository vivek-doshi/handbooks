Step 04 · Beginner · Decision maker's guide

Choose architecture patterns by evidence

Patterns are reusable tradeoff bundles, not maturity levels. This lesson compares the common deployment styles and gives a decision method for selecting a design that fits product needs, team ownership, and operating capability.

1. Ask the right questions first

Write down the problem before naming the pattern. Determine:

  • Which capabilities change together, and which teams need independent ownership?
  • What latency, availability, durability, and data-consistency behavior is required?
  • What needs independent scaling or release, based on evidence?
  • What operational skills, observability, deployment automation, and on-call coverage exist?
  • How reversible is the choice, and what is the cost of migrating later?

Model the required quality attributes and use the smallest design that meets them with room for known change. "Scale" includes people, code, deployment, data, and operations—not only traffic volume.

2. Monolith and modular monolith

A monolith is one deployable application. It can be a sound design when one team can change and release the product coherently. A modular monolith adds explicit domain modules, narrow interfaces, and dependency rules while retaining one process and deployment unit.

Choose this whenthe product is still discovering its domain, transactions span related capabilities, teams are small, or operations simplicity is valuable. Start with module boundaries and ownership so later extraction is based on evidence.

Costs include shared release cadence and the need to enforce boundaries. A "modular" label does not help if every module reaches into every other module's tables or internals.

3. Microservices

A microservice is a boundary of independent ownership and deployment with a clear contract and data responsibility. It is not simply a small code repository or an HTTP endpoint.

Benefits can include independent releases, technology choice, team autonomy, and targeted scaling. Costs include remote-call failure, contract versioning, distributed transactions, cross-service tracing, local development friction, security policy, and higher platform/on-call burden.

Readiness testCan every proposed service have an accountable team, automated deployment, health and dependency telemetry, clear API ownership, and a tested data recovery plan? If not, create fewer, better modules first.

4. Event-driven architecture

Event-driven systems communicate facts about things that already happened. They suit fan-out, independent consumers, workflow integration, and streaming. Commands ask a specific owner to do something; events notify interested parties of a committed fact.

Design for duplicate delivery, replay, schema evolution, consumer lag, and eventual consistency. Use an outbox or equivalent atomic-publish strategy where database state and event delivery must stay aligned. Use a saga or explicit workflow state for long-running business processes; do not imply that a broker provides a global transaction.

5. Serverless and function-as-a-service

Serverless shifts provisioning and scaling responsibilities to a managed platform; it does not remove operations. It can suit event-triggered, bursty, or independently bounded workloads. Assess execution limits, cold-start behavior, local testing, concurrency, observability, state, regional options, pricing, and provider exit cost.

Keep business logic testable outside provider event handlers. Use idempotency keys and durable workflow state for retried invocations. Avoid a maze of tiny functions when one clear service would be easier to reason about.

6. Supporting patterns: BFF, CQRS, event sourcing, and layered design

  • BFF: one API composition layer per distinct client need; keep business policy in its domain owner.
  • CQRS: separate write and read models when access patterns or scale justify projection and consistency costs.
  • Event sourcing: make an append-only event history authoritative when audit/reconstruction requirements justify replay and evolution complexity.
  • Layered architecture: separate responsibilities, but avoid excessive pass-through layers.
  • Hexagonal architecture: isolate policy behind ports and adapters when external dependencies need replaceable/testable boundaries.

These patterns compose; they are not mutually exclusive and should not be added without a requirement.

8. Common pitfalls and a better decision record

Avoid "microservices because Netflix does it," one service per database table, synchronous call chains with no timeout budget, shared databases with hidden ownership, and early event sourcing without replay requirements. Do not equate serverless with cost-free or zero operations.
