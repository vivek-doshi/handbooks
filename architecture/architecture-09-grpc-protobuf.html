Step 09 · Advanced · Service contracts

gRPC and Protocol Buffers

gRPC offers generated, strongly typed remote procedure calls; Protocol Buffers (Protobuf) define compact, language-neutral messages and services. Together they are useful for controlled service-to-service contracts where streaming or generated clients matter.

HTTP/2Four RPC modesSchema evolutionSecurity and telemetry

1. What gRPC is and when to choose it

Define a service and messages in an interface definition language, generate client/server code, and exchange typed messages over a transport. gRPC is a strong fit for internal APIs, low-latency service communication, streaming, and polyglot teams with contract tooling.

REST/JSON may be a simpler public-web contract with broad browser and debugging support. Browser clients may use gRPC-Web through a compatible proxy. Compare compatibility, tooling, observability, load balancing, proxy support, and consumer needs; binary serialization alone does not guarantee faster end-to-end behavior.

2. Protobuf syntax, field types, and binary encoding

syntax = "proto3";

package inventory.v1;

message GetItemRequest {
  string item_id = 1;
}

message Item {
  string item_id = 1;
  string display_name = 2;
  int64 available_quantity = 3;
}

service InventoryService {
  rpc GetItem(GetItemRequest) returns (Item);
}

Messages contain numbered fields with scalar, enum, message, repeated, map, or oneof types. Protobuf encodes field numbers and wire types rather than field names, which keeps the wire format compact. Field numbers are part of the compatibility contract.

Schema evolution ruleNever reuse a deleted field number or name. Mark deleted numbers and names as reserved. Add fields compatibly and test old/new reader-writer combinations. Review the current Protobuf Editions guide as well as proto3: Editions are the current evolution path described by the official documentation.

3. HTTP/2, metadata, and the four RPC modes

gRPC uses HTTP/2 framing in its conventional transport, with headers, streams, and flow control. A single connection can carry multiple RPC streams. Proxies and load balancers must support the relevant HTTP/2 behavior and long-lived streams.

ModeMessage flowExample
UnaryOne request, one responseGet a customer profile
Server streamingOne request, response streamWatch inventory updates
Client streamingRequest stream, one responseUpload a batch or telemetry window
Bidirectional streamingIndependent request and response streamsInteractive session or live feed

Metadata carries cross-cutting values such as authentication credentials, request IDs, or tracing context; do not treat it as an unbounded payload. Set deadlines on calls and propagate cancellation. A client timeout does not guarantee server work stopped unless cancellation is handled.

4. Errors, interceptors, and load balancing

Use canonical gRPC status codes and structured details where appropriate. Define retry policy only for safe, transient failures; set an overall deadline so retries do not multiply latency. Mutating methods need idempotency semantics before automatic retries.

Interceptors implement cross-cutting concerns such as authentication, logging, metrics, and tracing. Keep them predictable and avoid swallowing errors. Load balancing may be client-side or proxy/service-mesh managed; verify name resolution, health checking, endpoint discovery, connection reuse, and streaming behavior in the chosen environment.

5. TLS, authentication, and authorization

Use TLS for transport confidentiality and integrity. Use mutual TLS when workload identity and two-way authentication are required, with managed certificate rotation. Authenticate the caller and authorize each method/resource; network location alone is not authorization. Keep tokens out of logs and metadata dumps.

Apply message-size limits, rate limits, deadlines, and validation. Treat reflection as an operational/debugging feature with access controls; do not expose service inventory unnecessarily on public endpoints.

6. Observability, compatibility, and rollout

Instrument RPC count, status, duration, request/response size, deadlines, retries, and active streams. Propagate W3C trace context or supported metadata across calls. Use OpenTelemetry conventions supported by your language SDK and exporter; avoid sensitive or high-cardinality labels.

  1. Publish contract changes and compatibility policy.
  2. Run breaking-change checks and generate clients in CI.
  3. Deploy servers that accept old and new clients before rolling clients forward.
  4. Monitor error codes and version adoption; remove old fields only after consumers migrate.
  5. Test deadline, cancellation, stream backpressure, and network interruption.
PracticeDefine a unary ReserveStock RPC and a server-streaming WatchStock RPC. Specify idempotency, deadlines, authorization, error mapping, and how an old client behaves after adding a response field.
