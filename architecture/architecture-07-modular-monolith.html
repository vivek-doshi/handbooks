The modular monolith

A modular monolith is one deployable system with explicit internal modules, owned data, and controlled dependencies. It combines local-call simplicity with boundaries that make change and future extraction more deliberate.

Domain boundariesModule contracts.NET and Angular layoutsMigration path

1. What it is and why choose it

Modules are logical units of ownership; the application is built and deployed together. This can be the right choice when a domain is evolving, one team or a small number of teams coordinate releases, transactions span related capabilities, or a distributed platform would add more cost than autonomy.

It is not a "monolith that will automatically become microservices." Most systems can remain modular monoliths successfully. Extraction is a later business and operational decision, not a required destination.

2. E-commerce example: split by domain responsibility

Possible modules include Catalog, Pricing, Orders, Payments, Inventory, and Fulfillment. Orders owns order lifecycle; Inventory owns stock reservations; Payments owns payment status. Other modules request actions through public contracts instead of updating each other's tables.

src/
  Catalog/       public API + domain + persistence
  Pricing/       public API + domain + persistence
  Orders/        public API + domain + persistence
  Inventory/     public API + domain + persistence
  Payments/      public API + domain + persistence
  Host/          composition root, transport, startup

Choose module boundaries based on cohesive business rules and ownership, not a generic "controllers/services/repositories" tree alone. Keep cross-module workflows explicit.

3. Domain-based vs. technical-module splits

A domain-oriented split groups code and data around business capabilities. A technical split groups all controllers, services, and repositories by type; that can make cross-cutting changes easy but often hides ownership. A practical design may use technical subfolders inside each business module while keeping module APIs clear.

Example .NET structure

src/
  Orders/
    Orders.Contracts/
    Orders.Domain/
    Orders.Infrastructure/
  Inventory/
    Inventory.Contracts/
    Inventory.Domain/
    Inventory.Infrastructure/
  AppHost/
tests/
  Orders.Tests/
  Architecture.Tests/

Example Angular structure

src/app/
  orders/
    public-api.ts
    data-access/
    feature-checkout/
    ui/
  catalog/
    public-api.ts
    data-access/
    feature-search/
    ui/
  app.routes.ts

These are examples, not mandatory framework layouts. Keep domain boundaries meaningful in the server and client; avoid leaking internal module paths into consumers.

4. Enforce module boundaries

  • Expose a small public API for each module; keep implementation packages private.
  • Declare allowed dependency direction and prohibit cycles.
  • Give each module one owner for its schema and migrations.
  • Use architecture tests, package visibility, lint rules, or build graph checks to block forbidden references.
  • Inspect dependency graphs in code review and make violations visible.

Use synchronous in-process calls when an immediate answer is required. Use domain events for meaningful decoupled reactions; avoid turning every method call into an event. Module boundaries should improve testability and ownership, not add ceremonial indirection.

5. Shared kernel: keep it intentionally small

A shared kernel contains concepts that truly have the same meaning and evolve together. Good candidates may include carefully governed value types or identity primitives. Avoid a "common" package that becomes the dumping ground for domain rules, database models, and utilities nobody owns.

When two modules need similar concepts with different semantics, duplicate a small value or define a translation at the boundary. Shared code creates shared change and release coupling.

6. Scaling strategy and cost vs. microservices

First optimize queries, indexes, caches, background jobs, connection pools, and horizontal scaling of the whole application. If a distinct workload needs different scaling, isolate the workload or worker before splitting domain ownership. Measure team coordination and bottlenecks rather than inferring them from an architecture diagram.

Modular monolithMicroservices
In-process calls, simpler transactions and local debuggingIndependent deployment and targeted runtime boundaries
One release unit; internal boundaries need enforcementNetwork contracts, partial failures, tracing, and platform ownership
Often lower operational overhead at small/medium scaleCan lower team coupling when autonomy is real and supported

7. Migration path when extraction is justified

  1. Identify a concrete pain: release contention, isolation need, distinct scaling, or clear team ownership.
  2. Strengthen the module contract and remove illegal internal access first.
  3. Assign data ownership and define an integration API or event contract.
  4. Extract with a strangler approach, routing a small slice to the new service.
  5. Measure latency, reliability, delivery, and operational load before expanding.
  6. Keep rollback and data reconciliation possible until the new boundary is proven.
