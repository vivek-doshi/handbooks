Step 07 · Intermediate · Strong boundaries, simple operations

The modular monolith

A modular monolith is a single deployable application with rigorously enforced domain boundaries, encapsulated data ownership, and explicit inter-module contracts. It captures the operational simplicity of in-process communication while preventing architectural rot.

1. Architectural Model and Core Value Proposition

A modular monolith organizes business logic into cohesive, autonomous domain modules compiled into a single deployable unit. Modules interact through strictly defined public API contracts while encapsulating internal domain models, database queries, and private services.

3. Inter-Module Communication Patterns

Communication MechanismCoupling LevelWhen to ChoosePitfall to Avoid
Direct Interface Calls (Sync) Medium (Typed Contract) Caller strictly requires an immediate return value to proceed (e.g., validating customer credit balance). Passing internal domain entity pointers; must use immutable DTOs.
In-Process Mediator (MediatR) Low (Message Contract) Decoupled command dispatching and query pipelines; cross-cutting middleware (validation, logging). Treating mediator commands as magic global events; obscures call graphs.
In-Process Domain Events (Async) Very Low (Event Contract) Side effects where the primary transaction does not require immediate confirmation (e.g., send welcome email). Assuming in-process events survive server crashes; critical events need an Outbox.

4. Data Ownership and Database Partitioning

Modularity in code is useless if every module joins across every other module's database tables. Choose an intentional persistence isolation strategy:

StrategyIsolationTransactionsOperational Cost
Schema-per-Module (Recommended) High (PostgreSQL schemas: orders.*, inventory.*) Local ACID transactions possible if strictly necessary Low (Single database instance to operate and back up)
Table Prefix / Ownership Rules Medium (Single schema: ord_orders, inv_stock) Simple ACID joins Lowest (Enforced strictly via automated linter rules)
Database-per-Module Complete (Separate physical database clusters) Distributed transactions (Sagas required) High (Multiplies connection pools, migrations, and infrastructure cost)

Handling Cross-Module Queries Without Foreign Keys

When the Orders module needs customer name and email, it must never execute a cross-schema SQL JOIN users ON orders.user_id = users.id. Instead, use one of three clean architectural patterns:

  1. API Aggregation: Order module queries User module via public contract userModule.getUserSummary(userId).
  2. Denormalization / Event Subscription: When a user updates their profile, User module emits UserUpdated; Orders module updates its own denormalized order_customer_cache table.
  3. CQRS Read Projections: A dedicated reporting/query module listens to domain events and populates a unified denormalized read-model optimized for UI presentation.

5. Automated Boundary Enforcement

Architecture that depends on developer willpower inevitably degrades into a Big Ball of Mud. Automate boundary tests in CI:

ArchUnit Test Example (Java / Kotlin)

@AnalyzeClasses(packages = "com.enterprise.app")
public class ArchitectureRulesTest {
  @ArchTest
  public static final ArchRule orders_should_not_access_payments_internal =
    noClasses().that().resideInAPackage("..modules.orders..")
      .should().dependOnClassesThat()
      .resideInAPackage("..modules.payments.internal..")
      .because("Orders must interact with Payments exclusively through payments.api!");
}

NetArchTest Example (C# / .NET)

[Fact]
public void Orders_Should_Not_Reference_Inventory_Internal() {
  var result = Types.InNamespace("MyApp.Modules.Orders")
    .ShouldNot()
    .HaveDependencyOn("MyApp.Modules.Inventory.Infrastructure")
    .GetResult();
  Assert.True(result.IsSuccessful);
}

6. The Shared Kernel: Rules and Anti-Patterns

The Shared Kernel contains only universal, cross-cutting primitives (e.g., TenantId, Money, Currency, base Entity). It must be governed strictly.

The "Common Utility" Anti-Pattern

Creating a generic /common or /shared directory is an architectural hazard. Over time, developers deposit domain entities, database models, and helper methods into "common", causing every module to depend on it. When "common" changes, every module re-tests and redeploys. Rule: It is better to duplicate a simple 5-line DTO across two modules than to create a shared coupling dependency.

7. Strangler Extraction: Migrating to a Microservice

Because boundaries are already cleanly enforced in code, extracting a module into an independent microservice requires minimal refactoring:

  1. Validate Seams: Run ArchUnit tests to verify zero illegal dependencies or cross-module database foreign keys exist.
  2. Replace In-Process Contract with Network Client: Swap the in-process interface implementation (OrdersService) with an HTTP/gRPC client implementation that calls an external URL.
  3. Split Database Schema: Migrate the module's private database schema to an independent managed database instance.
  4. Deploy Standalone Service: Deploy the extracted module as an independent container with its own CI/CD pipeline.
  5. Route via Gateway: Update the API Gateway to route traffic directly to the new microservice.

8. Practical Exercises

  1. Module Boundary Design: Take a streaming video platform (like Netflix). Identify 4 core modules (e.g., Billing, Video Catalog, Recommendation, Streaming Session). Define the public contracts and DTOs exchanged between Catalog and Recommendation.
  2. Automated Fitness Function Setup: Configure an automated architecture test using ArchUnit, NetArchTest, or ESLint boundaries that fails if any file in /features/checkout imports directly from /features/inventory/db.
  3. Data Boundary Refactoring: Given a legacy SQL query that joins orders, customers, and shipping_providers across 3 domain boundaries, refactor the flow using domain events and localized data caching.
